# 개발자 로드맵 (상세) — 시안 프로젝트 온전한 오너십

> 개인 목표. sian 코드 repo와 분리. 시작 2026-06-27. 파트타임 6~9개월.
> 목표: **ERP를 혼자 개발·배포·운영하는 개발자.** 1차 학습차량=**시안 ERP2**(Next.js16 + React19 + TS + Prisma + MySQL + Redis + Docker), 2차 적용처=**현대음악(HDM) 출판사 ERP**. 스킬은 공통, 스택 차이는 단계 진행하며 흡수.
> 학습 원칙: ① 70% 손으로(이 프로젝트로) ② 매주 산출물 1개 ③ 막힌 지점이 곧 교재 ④ 항상 "왜"를 같이.
> 짝꿍 문서: `playbook.md` (리스크·문제해결). 진도 기록: `progress.md`.

각 단계는 **목적 → 배울 것 → 실습(시안) → ⚠️리스크 → 🔧문제해결 예시 → ✅통과기준** 으로 구성.

## Phase 0 — 큰 그림 + 도구 (약 1주)

**목적**: 코드 한 줄 안 짜도, 시안이 "어떻게" 돌아가는지 머릿속 지도를 그린다. 이게 없으면 이후 모든 게 암기가 된다.

**배울 것**
- 웹의 3층 구조: **브라우저(화면)** ↔ **서버(두뇌)** ↔ **DB(창고)**. 요청(request)과 응답(response)의 왕복.
- 시안 대입: 로그인 버튼 → 브라우저가 `/api/auth/login`에 아이디/비번을 보냄 → 서버가 DB에서 사용자 확인 → 맞으면 "출입증(쿠키)"을 발급 → 이후 브라우저는 매 요청에 그 출입증을 같이 보냄.
- 도구 3종: **터미널**(명령어로 컴퓨터에 지시), **VS Code**(코드 편집기), **브라우저 F12 개발자도구**(Network·Console 탭).

**실습 (시안)**
1. 시안 로그인하며 F12 → **Network** 탭 열기. `login`, `me` 요청이 오가는 것 직접 보기. 빨간 줄(실패)·초록(200) 구분.
2. **Console** 탭에서 오늘 봤던 `401`, `404` 같은 메시지가 뭔지 눈으로 익히기.
3. 시안 로그인 흐름을 종이에 화살표로 그려보기.

**⚠️ 리스크**
- 없음(읽기 전용). 단, 회사 실서버(prod)에서 이것저것 누르는 건 OK지만 **데이터를 만들거나 지우진 말 것**(연습은 나중에 로컬에서).

**🔧 문제해결 예시**
- *증상*: "로그인 후 화면이 깜박이고 안 넘어감" → *접근*: F12 Network에서 어떤 요청이 빨간색(실패)인지부터 본다. (오늘 우리가 한 게 정확히 이것. `401`/`404`의 위치가 원인을 가리킴.)

**✅ 통과기준**: 시안 로그인 과정을 "브라우저가 ~보내고, 서버가 DB에서 ~확인하고, 쿠키를 ~"로 말로 설명할 수 있다.

## Phase 1 — Git / GitHub (1~2주)

**목적**: 변경을 **안전하게** 저장·되돌리기·공유. 오늘 본 `main` vs `feat` 혼선이 여기서 완전히 풀린다.

**배울 것**
- **저장소(repo)**: 코드 + 모든 변경 이력이 담긴 폴더.
- **commit**: 그 순간의 스냅샷(되돌릴 수 있는 저장점). **메시지**로 "무엇을 왜" 기록.
- **branch**: 코드의 평행우주. `main`(안정본) 건드리지 않고 `feat/...`에서 실험.
- **push/pull**: 내 컴퓨터 ↔ GitHub 업/다운로드.
- **merge / PR(Pull Request)**: "내 브랜치를 main에 합쳐주세요" 요청 + 리뷰.
- **충돌(conflict)**: 같은 줄을 둘이 다르게 고쳤을 때. 무서운 게 아니라 "둘 중 뭘 택할지" 고르는 일.

**실습 (시안)**
1. `git status`, `git log --oneline`으로 현재 상태·이력 읽기.
2. 새 브랜치 `study/내이름-test` 만들고 README에 한 줄 추가 → `add` → `commit` → `push`.
3. GitHub에서 PR 만들어보기(머지는 안 해도 됨).

**⚠️ 리스크**
- `git push --force` / `git reset --hard`: **남의 작업·내 작업을 날릴 수 있음.** 초보 땐 금지. (playbook A 참고)
- 비밀번호·키가 든 파일을 commit하면 → GitHub에 영구 박제될 수 있음. `.env`는 절대 커밋 금지(이미 `.gitignore`로 막혀있는지 확인).
- 엉뚱한 브랜치에서 작업: 항상 `git status`로 **지금 어느 브랜치인지** 확인하고 시작.

**🔧 문제해결 예시**
- *증상*: "내 수정이 사라졌어요" → 대개 안 사라짐. `git reflog`로 거의 모든 과거 상태를 되찾을 수 있음(git의 안전망).
- *증상*: "prod가 main이 아니라 feat 브랜치로 배포돼 있음"(오늘 사례) → *원인*: 기능 브랜치를 main에 머지 안 한 채 배포. *해결*: 적당한 시점에 feat→main 머지해서 "main=prod"로 정렬.

**✅ 통과기준**: 브랜치 만들고 커밋·푸시·PR까지 혼자. "지금 어느 브랜치, 무엇이 staged인지" 항상 말할 수 있다.

## Phase 2 — 코드 읽기 (2~3주)

**목적**: *쓰기 전에 읽기.* 어떤 화면이 어느 파일에서 오는지 추적하는 힘. 디버깅의 8할.

**배울 것**
- **JavaScript → TypeScript** 기초: 변수, 함수, 객체/배열, 조건/반복, `import/export`. TS의 "타입"이 왜 실수를 미리 잡아주는지.
- **HTML + Tailwind CSS** 감각: 화면 구조와 스타일이 코드 어디에 있는지.
- 시안 폴더 지도:
  - `src/app/` = 화면·API (App Router). `(auth)/login` = 로그인 화면, `(dashboard)/` = 로그인 후 영역, `api/` = 서버 endpoint.
  - `src/components/` = 재사용 부품(UI). `src/lib/` = 핵심 로직(`auth.ts`, `prisma.ts`, `redis.ts`).
  - `prisma/schema.prisma` = DB 설계도.

**실습 (시안)**
1. "사용자 목록 화면"이 어느 파일인지 찾기(검색: `grep -r "사용자"` 또는 VS Code 검색).
2. 오늘 고친 `src/app/(auth)/login/page.tsx`를 줄 단위로 읽고, `handleSubmit`이 무슨 일을 하는지 주석 달아보기.
3. 데이터가 화면→API→DB로 흐르는 한 경로를 끝까지 따라가기.

**⚠️ 리스크**
- 읽기는 안전. 단 VS Code에서 **실수로 저장(Cmd+S)하며 파일을 바꾸지 않기** — `git status`로 의도치 않은 변경 확인.
- "다 이해해야 한다"는 압박 금지. 70%만 따라가도 충분. 모르는 건 표시해두고 진행.

**🔧 문제해결 예시**
- *상황*: 코드가 너무 많아 길을 잃음 → *접근*: 화면의 눈에 보이는 글자(예: "로그인")로 검색 → 그 파일에서 시작해 한 단계씩 위로/아래로. ("증상에서 코드로" 역추적)

**✅ 통과기준**: 임의의 화면 1개를 골라 "이 파일 → 이 함수 → 이 API → 이 테이블" 경로를 설명.

## Phase 3 — 로컬에서 돌리기 (약 2주) ← 진짜 개발자 된 느낌

**목적**: 실서버 안 건드리고 **내 노트북에서 시안 전체를 띄워** 마음껏 실험. 모든 연습의 안전한 놀이터.

**배울 것**
- **Node.js / npm**: 자바스크립트 실행기 / 패키지(부품) 설치기. `npm install`, `npm run dev`.
- **Docker / docker-compose**: MySQL·Redis를 "상자"로 띄우기. `docker compose up -d`.
- **.env.local**: 로컬용 비밀 설정(JWT_SECRET, DB 주소 등).
- 시안 셋업 순서(CLAUDE.md): `./setup.sh` → `docker compose up -d` → `npm run db:push`(스키마) → `npm run db:seed`(초기데이터) → `npm run dev`.

**실습 (시안)**
1. 로컬에 클론 → 셋업 → `localhost:3000` 띄우기.
2. 시드된 `admin / admin1234`로 로컬 로그인 성공.
3. `npm run db:studio`로 DB를 눈으로 보기(Prisma Studio).

**⚠️ 리스크**
- 포트 충돌(이미 3000/3306 사용 중) → 흔함. 끄거나 포트 바꾸기.
- Docker 안 켜고 `npm run dev` → DB 연결 실패. 순서 지키기.
- **로컬 .env를 prod 값으로 채우지 말 것** — 로컬에서 실수로 실서버 DB를 건드리면 사고. 로컬은 로컬 DB만.

**🔧 문제해결 예시**
- *증상*: `npm run dev` 했더니 빨간 에러 와르르 → *접근*: **맨 위 에러 메시지부터** 읽기(밑은 대부분 파생). "Cannot connect to MySQL"이면 Docker 안 켜진 것.
- *증상*: 로그인 안 됨(로컬) → DB seed 안 돌렸을 가능성. `npm run db:seed`.

**✅ 통과기준**: 내 컴퓨터에서 시안을 띄우고 로그인 + DB를 Prisma Studio로 확인.

## Phase 4 — 화면 만들기 / React·Next (4~6주)

**목적**: 버튼·화면·폼을 직접 추가. 사용자가 보는 걸 만든다.

**배울 것**
- **컴포넌트**: 화면을 레고 블록처럼 쪼갠 것. props(입력)와 재사용.
- **state(상태)**: 화면이 기억하는 값(입력칸, 열림/닫힘). React `useState`, 전역은 **zustand**(시안의 `auth-store`).
- **데이터 가져오기**: `fetch` + **react-query**(로딩/에러/캐시 자동).
- **폼**: react-hook-form + zod(검증). 시안 로그인폼이 예시.
- **렌더링/하이드레이션**: 서버가 HTML 먼저, 브라우저가 살아나게(JS) — 오늘 "깜박임"의 배경.

**실습 (시안)**
1. 대시보드에 "오늘 날짜" 표시 작은 컴포넌트 추가.
2. 기존 목록 화면에 검색칸 1개 추가(state로 필터).
3. 로컬에서 동작 확인 → 브랜치로 커밋.

**⚠️ 리스크**
- **무한 루프 / 무한 재요청**: `useEffect` 의존성 실수(오늘 본 `use-current-user`의 재요청 가드가 이 주제).
- 화면엔 멀쩡한데 콘솔에 빨간 에러 — 무시 금물. 작은 단위로 자주 확인.
- "전역 상태(store)"는 **새로고침 전까지 남는다** → 로그아웃·사용자 전환 시 꼬일 수 있음(오늘 "다른 사람으로 보임"의 사촌격).

**🔧 문제해결 예시**
- *증상*: 화면이 깜박이며 같은 데이터 계속 부름 → *원인*: useEffect가 매 렌더마다 실행. *해결*: 의존성 배열·가드 점검.
- *증상*: 버튼 눌러도 반응 없음 → Console 에러 먼저, 다음 Network에서 요청이 갔는지.

**✅ 통과기준**: 시안에 작은 기능 1개를 추가하고 로컬에서 동작 + 커밋.

## Phase 5 — 데이터: DB · Prisma · API (3~4주)

**목적**: 새 데이터를 저장·조회. 진짜 기능은 대부분 여기서.

**배울 것**
- **관계형 DB / 테이블 / 행·열 / 관계(FK)** 기초. **SQL** 감(SELECT/INSERT/UPDATE).
- **Prisma**: `schema.prisma`로 테이블을 코드로 설계 → **마이그레이션**으로 실제 DB에 반영(오늘 본 `items`/`board_posts` 추가가 이것).
- **API route**(`src/app/api/.../route.ts`): 화면이 부르는 서버 함수. 권한 체크(`withAuth`/RBAC).
- **트랜잭션·검증**: 잘못된 데이터 막기.

**실습 (시안)**
1. 스키마에 작은 필드 1개 추가 → 마이그레이션 → 화면에 표시.
2. 간단한 GET API 만들어 목록 반환.
3. Prisma Studio로 데이터 변화 확인.

**⚠️ 리스크 (여기가 사고 多)**
- **마이그레이션 = DB 구조 변경.** prod에서 잘못하면 데이터 손상/유실. **반드시 로컬에서 먼저**, prod는 **백업 후**.
- 배포 시 코드만 나가고 DB 마이그레이션 누락 → 신기능 **500 에러**(코드는 새 테이블 찾는데 DB엔 없음). 시안 규칙: 배포에 DB 동기화 포함(`--skip-db` 금지).
- 권한 체크 빠진 API → 아무나 데이터 열람/수정(보안 사고).

**🔧 문제해결 예시**
- *증상*: 새 기능이 prod에서만 500 → *원인*: prod DB에 새 테이블 없음. *해결*: 마이그레이션 적용. (오늘 SI-2~8 배포에서 "DB 마이그레이션 필수"가 이 이유.)
- *증상*: "column does not exist" → 스키마와 실제 DB 불일치. `db:push`/마이그레이션 재확인.

**✅ 통과기준**: 새 필드/테이블 추가 → 마이그레이션 → API → 화면까지 한 줄로 연결.

## Phase 6 — 인증 · 보안 (2~3주)

**목적**: 로그인·권한·비밀값을 이해하고 디버깅. 오늘 사건들의 본진.

**배울 것**
- **쿠키 / 세션 / JWT**: 출입증의 원리. 시안: JWT(jose) + Redis 세션 + httpOnly 쿠키. **한 브라우저 = 출입증 1개**(→ 오늘 "admin인데 안연주로 보임"의 정답).
- **bcrypt / 해시**: 비번을 원문 저장 안 하고 단방향 암호화. 시안의 SHA512→bcrypt 재해시.
- **RBAC(역할 기반 권한)**: ROLE_ADMIN/USER 등으로 화면·API 접근 통제. 시안 사이드바·페이지 가드.
- **시크릿 관리**: JWT_SECRET·ENCRYPTION_KEY를 코드 밖(.env)에. 유출 시 위험.
- **레이트리밋·감사로그**: 무차별 로그인 차단, 접근 기록.

**실습 (시안)**
1. 로그인 시 `/api/auth/login`→쿠키 발급→`/api/auth/me` 흐름을 F12로 끝까지 추적.
2. 권한 다른 두 계정(admin / 일반)으로 화면 차이 비교.
3. (로컬에서) JWT_SECRET 바꾸면 기존 로그인 다 풀리는 것 확인(왜 그런지 설명).

**⚠️ 리스크 (보안 = 최고 주의)**
- 시크릿을 코드/깃/채팅에 노출 금지. prod 기본값(`...change-in-production`) 그대로 두면 위험 → 실제값으로.
- 인증 endpoint를 캐시하면 **남의 세션이 새어나갈 수 있음**(오늘 nginx 캐시 헤더 점검한 이유).
- 비번 리셋·권한 변경은 **누구 것인지 확인 후**. 오늘 내가 안연주 비번을 진단용으로 바꿨다가 원복한 게 사례 — 항상 되돌릴 수 있게.

**🔧 문제해결 예시**
- *증상*: "admin으로 로그인했는데 다른 사람으로 보임" → *원인*: 같은 브라우저에서 다른 계정으로 로그인 → 쿠키 덮어씀(브라우저당 1개). *해결*: 다시 로그인 or 시크릿창 분리. **서버 버그 아님.**
- *증상*: 로그인 직후 다시 로그인 화면(깜박임) → *후보*: 세션/쿠키 미설정, 캐시된 옛 빌드 404, 비번 오입력. 하나씩 격리.

**✅ 통과기준**: 로그인·권한 흐름을 그림+말로 설명하고, "세션 섞임/401/깜박임" 류를 스스로 진단.

## Phase 7 — 배포 · 운영 / DevOps (3~4주)

**목적**: 만든 걸 실제로 내보내고, 서버를 돌본다. 오늘 막혔던 SSH·배포의 본진.

**배울 것**
- **빌드 → 이미지 → 전송 → 실행** 파이프라인. 시안 `deploy.sh` 한 줄씩 해부(로컬 Docker 빌드 → scp 전송 → 서버 `docker compose up`).
- **SSH 키**: 서버 출입 전자열쇠. 키페어 생성, 공개키 등록.
- **nginx**(앞단 교통정리), **SSL/certbot**(https 자물쇠, 갱신 — SI-10이 이 주제), **서버 로그** 읽기.
- **롤백**: 배포 잘못됐을 때 되돌리기.

**실습 (시안)**
1. `deploy.sh`를 읽으며 각 단계가 뭘 하는지 주석.
2. (강수아한테 SSH 키 받은 뒤) 작은 변경을 **직접 배포** 1회.
3. 배포 후 사이트 정상 확인(헬스체크).

**⚠️ 리스크 (실서버 = 최고 위험)**
- 잘못된 배포 = **모든 사용자 영향**. 항상 ① 로컬 검증 → ② 작은 단위 → ③ 롤백 계획.
- DB 마이그레이션 동반 배포는 **백업 먼저**.
- 디스크 가득/컨테이너 죽음 → 서비스 중단. 로그·디스크 모니터링.
- SSH 키 분실/유출 관리. prod에서 `rm -rf`·`docker compose down` 류는 신중히(playbook A).

**🔧 문제해결 예시**
- *증상*: `./deploy.sh`가 SSH에서 막힘(오늘 사례) → *원인*: 이 컴퓨터에 인가된 키 없음. *해결*: 키페어 생성→공개키 서버 등록, or 담당자 통해 배포.
- *증상*: 배포 후 사용자 화면 404·깜박임 → *원인*: 브라우저가 옛 빌드 캐시. *해결*: 하드리프레시 안내 / 빌드·캐시 정책 점검.

**✅ 통과기준**: 직접 배포 1회 성공 + 문제 시 롤백을 말할 수 있다.

## Phase 8 — 온전한 오너십 (지속)

**목적**: 버그를 처음~끝까지, 작은 기능을 단독으로.

**배울 것 / 실습**
- **디버깅 방법론**(playbook B)을 몸에 익히기: 증상정의→재현→격리→가설→검증→수정→재검증.
- **코드리뷰** 주고받기, **모니터링/알림**, **백업·복구** 연습.
- SI 이슈 1개를 설계→구현→테스트→배포까지 단독.

**✅ 통과기준**: SI 이슈 하나를 혼자 끝내고, 다른 사람에게 그 변경을 설명·방어할 수 있다.
