# 실버톡톡 부보호자 정책

작성일: 2026-04-25 (v5 — 구현 AI 가이드 §9 추가)
참조 문서: `secondary-guardian-spec.md` (코드 정적 분석 명세)

본 문서는 **정책 명세**. 구현(API, DB, 권한 체크 위치)은 별도 spec 문서 참조.

---

## 1. 용어 정의

- **주보호자(Main Guardian, `guardianType=0`)**: 환자 등록 시점에 지정되는 1인 보호자. 환자 1명당 항상 1명 존재.
- **부보호자(Secondary Guardian, `guardianType=1`)**: 주보호자가 초대하여 추가하는 보조 보호자. 환자 1명당 최대 10명(§6.1).
- 코드/UI/SMS 모두 **"부보호자"**로 통일. "대리보호자" 표현은 사용하지 않음.

---

## 2. 부보호자 추가 (주보호자 → 초대)

### 2.1 자격 조건
- **주보호자만** 부보호자를 추가할 수 있다. 부보호자는 다른 부보호자나 주보호자를 초대할 수 없다.
- 주보호자는 가입 완료 상태여야 한다(부보호자 관리 메뉴는 주보호자에게만 노출).

### 2.2 플로우
1. 주보호자 앱: **설정 > 부보호자 관리 > 부보호자 추가**
2. 본인이 주보호자인 환자 중 한 명 선택
3. **휴대폰 연락처에서** 부보호자 후보 선택
4. 차단 조건 검사(§2.4) 통과 시 시스템이 해당 번호로 **6자리 인증코드 SMS 발송**
5. 주보호자 화면 안내:
   > "부보호자를 초대하였습니다. 수락하면 부보호자로 등록됩니다."

### 2.3 SMS 본문
```
[실버톡톡] {환자명} 부보호자 초대코드: {6자리코드}
※ 부보호자 가입 전용 코드
```
- 환자명은 **마스킹 없이 그대로** 노출.

### 2.4 초대 차단 케이스
연락처에서 선택된 번호가 다음에 해당하면 코드 발송 차단 + 안내 표시:

| 케이스 | 안내 메시지 |
|---|---|
| 이미 해당 환자의 부보호자 (가입 완료 또는 미가입 초대 진행 중) | "이미 초대한 부보호자입니다." |
| 본인(주보호자)을 초대 시도 | "주보호자는 같은 환자의 부보호자가 될 수 없습니다." |
| 해당 환자의 부보호자 슬롯이 이미 10명(§6.1) | "부보호자는 환자당 최대 10명까지 등록 가능합니다." |

> 부보호자가 주보호자를 초대하는 케이스는 §2.1에 의해 자동 차단(부보호자에게는 메뉴 자체가 노출되지 않음).

## 3. 부보호자의 가입 및 수락

대상자 상태에 따라 두 케이스. **두 케이스 모두 인증코드 입력으로 본인 동의를 표현**한다.

### 3.1 미가입자
1. SMS로 인증코드 수신
2. 실버톡톡 앱 설치 → 회원가입 진행
3. 가입 과정 중 **부보호자 인증코드 입력** 단계에서 6자리 입력
4. 가입 완료 = 수락 (별도 수락 단계 없음)
5. 가입 완료 직후 부보호자 앱:
   - 환자 목록에 해당 환자 노출
   - 자신은 해당 환자의 **부보호자 신분**

### 3.2 기가입자
이미 실버톡톡을 사용 중인 사용자(다른 환자의 보호자 또는 일반 가입자) 모두 동일 흐름:

1. SMS로 인증코드 수신
2. 실버톡톡 앱 진입 시 **메인 화면에 팝업**:
   > "**{주보호자이름}**님의 부보호자로 초대되었습니다.
   > 문자로 전송된 인증코드를 입력하세요."
3. 6자리 인증코드 입력 → 부보호자로 등록
4. 환자 목록에 해당 환자 추가됨

### 3.3 가입 = 수락 원칙
- 인증코드 입력 = 본인 동의의 표현.
- 별도 "수락/거절" 버튼 없음.
- 동의 없는 즉시 등록은 **하지 않는다**(현재 서버 코드 수정 필요 — 구현 spec 참조).

### 3.4 인증코드의 역할 구분
- 인증코드는 같은 `PatientGuardianCodeTable`을 공유하나, 각 코드 row는 **`guardianType` 컬럼으로 역할이 명시**됨.
  - `guardianType=0`: 주보호자 가입용 코드 (CMS에서 신규 주보호자 등록 시 발급, §5.3.1 (b))
  - `guardianType=1`: 부보호자 초대용 코드 (앱에서 주보호자가 초대 시 발급, §2)
- 가입 시점에 코드의 `guardianType`을 그대로 적용해 등록.

## 4. 주요 정책

### 4.1 등록/삭제 권한
| 권한 | 주보호자 | 부보호자 | 비고 |
|---|---|---|---|
| 부보호자 초대 | ✅ | ❌ | |
| 부보호자 삭제 (타인) | ✅ | ❌ | §5.2 |
| **부보호자 자진 탈퇴 (본인)** | — | ✅ | §5.1 |
| 초대 취소(미가입자) | ✅ | ❌ | |
| 주보호자 권한 이관 | ❌(앱) / **CMS 전용** | ❌ | §5.3 |

### 4.2 가시성 (다른 보호자가 누구인지 보이는가)
- **주보호자**: 자신 + 모든 부보호자 목록을 본다.
- **부보호자**: **주보호자 + 자기 자신**만 본다. 다른 부보호자는 목록에서 보이지 않는다.

### 4.3 면회 권한
| 권한 | 주보호자 | 부보호자 |
|---|---|---|
| 면회 신청 | ✅ | ✅ |
| 자기가 신청한 면회 취소 | ✅ | ✅ |
| **타 보호자 신청 면회 취소** | ✅ (부보호자 신청 포함) | ❌ |
| 환자의 모든 예약 면회 목록 조회 | ✅ | ✅ |

### 4.4 면회 예약 횟수 / 취소 / 노쇼
- **한 환자당 하루 1건의 면회 예약만 허용** (환자 단위, KST 자정 기준).
- 신청자가 누구든(주/부) 동일 환자/같은 날짜 중복 불가.
- **취소 후 재신청 가능** — 취소된 슬롯은 비어있는 것으로 간주.
- **앱 내 노쇼 자동 카운트/제한 없음**.
- CMS(파트너)에서 **노쇼 수동 기록 가능**(통계/CS 용도). 1일 1회 제한에는 영향 없음.

### 4.5 면회 예약 목록 — 신청자 이름 표시
- 주보호자, 부보호자 **모두 환자의 모든 예약 면회 목록을 본다**.
- **신청자 이름 표시 정책**:
  - **주보호자 화면**: 모든 신청자 이름 표시.
  - **부보호자 화면**:
    - 본인이 신청한 row → **"본인 신청" 뱃지** + 취소 버튼
    - 타 보호자(주/부) 신청 row → **"예약됨"** 으로만 표기, 신청자 정보 비공개
- 가시성 정책(§4.2)과 정합성 유지. 부보호자 간 익명성 보장.

### 4.6 면회 외 영역 권한 매트릭스
- 채팅 / 문서 / 사진 등 면회 외 영역은 **현재 시점 정책 미정**.
- 별도 정책이 정의되기 전까지 **주보호자와 부보호자는 동일 권한**을 갖는다.
- 신규 기능 추가 시 본 정책에 권한 차등 항목 추가.

## 5. 라이프사이클

### 5.1 부보호자 자진 탈퇴
- 부보호자 본인이 환자 목록에서 **해당 환자 카드를 눌러 "부보호자 해제"** 가능.
- UX 라벨: **"부보호자 해제"** (또는 "이 환자에서 부보호자 해제"). 확인 다이얼로그에 "본인의 부보호자 권한만 해제됩니다. 환자 정보는 유지됩니다." 명시.
- 효과:
  - 자기 자신의 환자 목록에서 해당 환자 제거.
  - 주보호자에게 **푸시 알림**:
    > "{이름} 부보호자가 {환자명} 환자에서 탈퇴하였습니다."
  - 주보호자의 부보호자 목록에서 해당 부보호자 row 제거.

### 5.2 주보호자에 의한 부보호자 삭제
- 주보호자가 부보호자 관리에서 부보호자 삭제.
- 효과:
  - 부보호자 본인에게 **푸시 알림**:
    > "{환자명} 환자의 부보호자 권한이 해제되었습니다."
  - 부보호자의 환자 목록에서 해당 환자 제거.
  - 주보호자의 부보호자 목록에서 row 제거.

### 5.3 주보호자 변경 / 탈퇴

#### 5.3.1 주보호자 이관 — CMS(파트너) 전용
- **앱에서는 주보호자 이관 불가**. CMS(파트너)에서 환자 카드 수정으로만 주보호자 변경 가능.
- 파트너가 의사 확인된 주보호자로 직접 지정. 본인 동의는 **현재 구두 확인**으로 갈음(앱 내 별도 동의 단계 없음).
- 이관 대상 케이스:
  - **(a) 기존 부보호자 → 주보호자 승격**:
    - CMS에서 환자 카드의 주보호자를 부보호자 중 한 명으로 변경.
    - **DB 처리**: 트랜잭션 내에서 같은 (patientID, uidx) row의 `guardianType`을 1 → 0으로 **UPDATE** (PK 충돌 방지). DELETE 후 INSERT 방식 사용 안 함.
    - 이전 주보호자는 환자 관계 해제(부보호자 row 미생성, 환자 목록에서 제거).
  - **(b) 신규 사용자에게 이관**:
    - CMS에서 신규 사용자(주보호자) 등록 → **주보호자 가입용 인증코드 SMS 발송** (`guardianType=0` 코드, §3.4).
    - 신규 사용자가 가입 시 인증코드 입력 → 자동으로 해당 환자의 주보호자로 등록.
    - 이전 주보호자 처리는 위 (a)와 동일.
- 기존 부보호자들은 **자동으로 새 주보호자에게 승계**됨(부보호자 관계 유지).
- **이관 시점에 진행 중인 면회 정리**: 이전 주보호자가 신청한 면회 row는 CMS 운영자가 이관 시점에 함께 처리(취소 또는 새 주보호자에게 안내). 운영 매뉴얼 항목.
- 이관 후 알림: 부보호자들에게 푸시:
  > "주보호자가 {새 주보호자 이름}으로 변경되었습니다."

#### 5.3.2 CMS 운영 보안 (주보호자 변경 권한)
- 주보호자 변경 권한은 CMS에서 **권한 분리**: SUPER_ADMIN, ADMIN만 가능. VIEWER는 불가.
- CMS의 주보호자 변경 화면에서 **변경 사유 입력 필드 의무화**.
- 감사 로그(§7) `MAIN_TRANSFER` 이벤트에 **운영자 ID + 사유**를 함께 기록.

#### 5.3.3 주보호자 탈퇴 차단
- 환자에 주보호자가 부재해서는 안 됨 — 주보호자는 **단독 탈퇴 불가**.
- 부보호자 N명이 있어도 자동 승격되지 않음(이관은 CMS 전용 액션).
- 사용자 본인 탈퇴 의사가 있을 경우 안내:
  - **부보호자가 0명**: 탈퇴 불가 안내 + **CS 연락 경로 포함**:
    > "주보호자 변경/탈퇴는 고객센터로 문의해주세요. 환자 퇴원 처리 또는 새 주보호자 지정 후에만 탈퇴 가능합니다."
  - **부보호자가 1명 이상**: CS 통해 주보호자 변경 요청 → CMS에서 이관 후 탈퇴 가능.

### 5.4 환자 퇴원 / 사망
- 환자가 퇴원/사망으로 비활성화되는 경우:
  - 주보호자, 부보호자 **모두 해당 환자가 환자 목록에서 자동으로 사라짐**.
  - 별도 사용자 액션 불필요.
  - 주/부보호자에게 **푸시 알림 1회** 발송:
    > "{환자명} 환자가 퇴원 처리되어 보호자 권한이 종료되었습니다."

## 6. 운영 정책

### 6.1 부보호자 인원 상한
- **환자 1명당 부보호자 최대 10명**.
- 카운트 기준: **가입 완료된 부보호자 + 진행 중인 미가입 초대 코드 합산**.
  - 미가입 초대도 슬롯을 차지(어뷰징 방지).
  - 잘못된 초대로 슬롯이 막힌 경우 §6.2의 미가입 초대 목록에서 주보호자가 직접 취소하여 슬롯 회복.
- 11번째 초대 시도 시 §2.4의 안내 메시지 표시 + 차단.

### 6.2 인증코드 만료
- **만료 기한 없음**. 발급된 코드는 사용/취소 전까지 유효.
- 같은 (환자, 휴대폰) 조합으로 재초대 시: 이전 코드 무효화 + 새 코드 발급.
- 주보호자가 초대 취소 시: 해당 코드 무효화 (구현 spec 참조).
- 주보호자는 **부보호자 관리 화면에서 자기 환자의 미가입 초대 목록을 직접 조회 가능**. 의심스러운 초대를 본인이 취소할 수 있다.

### 6.3 SMS 환자명 노출
- **환자명 그대로 노출**(마스킹 없음).
- 잘못된 번호 입력 시 위험은 §2.4 차단 케이스와 §6.2 미가입 초대 목록 가시화로 완화.

### 6.4 부보호자 관리 화면 UI
주보호자의 부보호자 관리 화면에 미가입 초대와 가입 완료 부보호자가 함께 표시될 때 **시각적으로 구분**한다:
- **미가입 행 (초대 중)**: 휴대폰 번호 + **"초대 중" 뱃지** + 취소 버튼.
- **가입 완료 행**: 이름 + 삭제 버튼.

## 7. 감사 로그(Audit Log)

부보호자 관계 변경 이벤트는 별도 감사 로그 테이블에 **append-only**로 기록한다.

### 7.1 기록 대상 이벤트
| 이벤트 | 발생 시점 | 추가 필드 |
|---|---|---|
| `INVITE` | 주보호자가 부보호자 초대 (코드 발급 + SMS 발송) | |
| `INVITE_CANCEL` | 주보호자가 미가입자 초대 취소 | |
| `ACCEPT` | 부보호자 가입/수락 완료 — 관계 등록 | |
| `DELETE_BY_MAIN` | 주보호자가 부보호자 삭제 (§5.2) | |
| `SELF_LEAVE` | 부보호자 자진 탈퇴 (§5.1) | |
| `MAIN_TRANSFER` | CMS에서 주보호자 권한 이관 (§5.3.1) | **operatorId, reason** (§5.3.2) |
| `PATIENT_DEACTIVATE` | 환자 퇴원/사망으로 보호자 관계 종료 (§5.4) | |

### 7.2 기록 필드
- 이벤트 타입, 환자 ID, 행위자 uidx(또는 CMS 운영자 ID), 대상 uidx 또는 phone, guardianType, 코드 ID(있을 시), IP, UA, createdAt.
- `MAIN_TRANSFER`만 추가로: 운영자 ID, 변경 사유.
- 보존 기간: **3~5년** (개인정보 보호법상 기록 보존 의무 고려).

### 7.3 사용자 탈퇴 시 처리 (개인정보 삭제 요청)
- 사용자가 탈퇴/개인정보 삭제 요청 시 감사 로그의 `actorUidx` / `targetUidx`는 **익명화**(`DELETED_USER` 토큰 또는 비가역 해시).
- 이벤트 자체는 보존, 개인 식별성만 제거.

### 7.4 운영 활용
- 분쟁 조회 / CS 대응 / 어뷰징 탐지 / 개인정보위 민원 대응.
- 운영 데이터에서 삭제된 row도 감사 로그에서는 추적 가능.

## 9. 구현 AI 가이드 — 정책 vs 기존 기능 충돌 처리

본 정책 문서를 외부 코드베이스의 구현 AI에게 전달할 때 적용. 코드 접근 권한이 있는 측이 본 가이드에 따라 의사결정.

### 9.1 우선순위
1. **본 정책 문서(policy)가 단일 진실 공급원**.
2. `secondary-guardian-spec.md`(spec)는 **현재 구현 상태**의 기록. policy와 spec이 다르면 **policy 우선**, spec은 갱신 대상.
3. 코드는 spec/policy를 따라 수정 대상. 코드의 현재 동작이 정책과 다르면 **코드를 정책에 맞춤**.

### 9.2 즉시 정지(HALT) 조건 — 사용자 결정 없이 진행 금지
다음 케이스를 발견하면 **코드 변경 멈추고 즉시 보고**:
- 본인 동의 없이 환자 정보가 노출되는 코드 경로
- 가시성 정책(§4.2) 위반: 부보호자가 다른 부보호자를 식별할 수 있는 화면/응답
- §2.4 차단 케이스 누락(중복/본인/10명 한도)
- 감사 로그(§7) 기록 누락
- DDL 변경 / 데이터 마이그레이션 / 백필 필요
- 외부 시스템 변경 (SMS 게이트웨이, FCM 토픽, 결제 등)
- CMS 권한 모델 변경 (§5.3.2 SUPER_ADMIN/ADMIN 분리 외)

### 9.3 자율 진행 가능 영역
- 정책 본문에 **명시된 동작 그대로 구현**.
- 카피/라벨 미세 조정(정책 의도 범위 내).
- 에러 메시지, 로그 포맷.
- 리팩토링, 네이밍, 테스트 추가 (외부 동작 불변).

### 9.4 정책이 침묵하는 영역
- §4.6에 명시: 면회 외 영역(채팅/문서/사진)은 **주/부 동일 권한**이 기본.
- 그 외 정책이 다루지 않는 영역은 **기존 동작 유지**. 새로운 권한 차등을 임의로 도입 금지.
- 새 기능 추가가 부보호자 정책에 영향을 주는 경우 정책 문서 갱신을 먼저 요청.

### 9.5 충돌 발견 시 보고 형식
충돌을 발견하면 코드 수정 전에 다음 형식으로 보고:

```
[POLICY-CONFLICT]
정책 조항: §X.Y
정책 내용: (인용)
현재 코드 동작: (파일:라인 + 동작 요약)
충돌 유형: (정책 위반 / 정책 가정 불일치 / 정책 침묵)
영향 범위: (어떤 사용자/환자/플로우에 영향)
권장 처리: (a) 코드 수정 / (b) 정책 수정 / (c) 추가 결정 필요
```

### 9.6 정책 vs 기존 기능 — 알려진 잠재 충돌
선제적으로 짚어두는 영역. 발견 시 즉시 정지 후 보고:

| 영역 | 잠재 충돌 | 정책 우선순위 |
|---|---|---|
| 면회 1일 1회 (§4.4) | 기존 면회 시스템에 환자/날짜 UNIQUE 제약 없을 수 있음 | 정책 우선. 마이그레이션 필요 시 사전 승인 |
| 주보호자 이관 (§5.3) | 앱 내 이관 코드가 이미 있다면 | 정책 우선(앱 경로 deprecate). 즉시 삭제 금지, 사용 0 확인 후 단계적 제거 |
| 부보호자 즉시 등록 (§3.3) | 현재 서버는 가입자 케이스에서 즉시 등록(spec 5.6) | 정책 우선. 인증코드 단계 추가 필수 |
| SMS 본문 마스킹 (§6.3) | 현재 코드가 마스킹 적용 중일 수 있음 | 정책 우선(원문 노출). spec과 일치시킬 것 |
| 인원 상한 (§6.1) | 현재 코드는 상한 없음 | 정책 우선(10명). 기존 데이터에 11명 이상이 있으면 보고 |
| 자진 탈퇴 (§5.1) | 현재 부보호자 자진 탈퇴 API 부재 | 신규 추가 필요. 사전 승인 |

### 9.7 정책 갱신 요청 경로
구현 중 정책 자체가 비현실적이거나 누락이 발견되면:
- 코드 임의 변경 금지.
- 정책 문서에 **갱신 제안**(어떤 조항을 어떻게 바꿀지) 작성 후 사용자 승인 요청.
- 승인 후 본 정책 문서(`secondary-guardian-policy.md`)를 vN+1로 업데이트하고 변경 이력에 기록.

### 9.8 spec 문서 동기화
- 코드를 정책에 맞게 수정하면 `secondary-guardian-spec.md`도 함께 갱신.
- spec의 ❓ 항목 중 해소된 것은 본 정책 §X.Y 참조로 대체.
- spec과 policy의 §번호는 **상호 참조 가능**하도록 명시.

### 9.9 테스트 의무화
정책 본문의 모든 권한/플로우는 자동 테스트로 보호.

#### 9.9.1 단위 테스트 필수
- §2.4 초대 차단 케이스 (중복/본인/10명 한도) — 각 케이스별 단위 테스트.
- §6.1 인원 카운트 로직 (가입자 + 미가입 합산) — 경계값(9, 10, 11) 테스트.
- §6.3 SMS 본문 생성 — 환자명 원문 노출 검증.
- §3.4 인증코드 `guardianType` 분기 — 0/1 각각 가입 흐름 검증.

#### 9.9.2 통합 테스트 필수
- §3 가입 흐름 — 미가입자/기가입자 두 케이스 각각 E2E.
- §4.1 권한 매트릭스 — 주보호자/부보호자 시각의 모든 액션(허용/거부) 검증.
- §4.2 가시성 — 부보호자 화면 응답에 다른 부보호자 정보가 누락됨 검증.
- §4.5 면회 목록 — 부보호자 화면 응답에 신청자명 마스킹 검증.
- §5.1~5.4 라이프사이클 — 자진 탈퇴 / 주보호자 삭제 / 이관 / 퇴원 각각 E2E.
- §7 감사 로그 — 각 이벤트 타입별 row 생성 + 필드 검증.

#### 9.9.3 회귀 테스트
- 면회 1일 1회 적용으로 **기존 면회 흐름 회귀 가능성** 높음. 기존 면회 신청/취소/조회 시나리오 회귀 테스트 추가 필수.
- SMS 본문 변경 시 기존 SMS 발송 경로(주보호자 가입 등) 회귀 확인.
- 가시성 정책 적용 시 기존 환자 정보 조회 화면 회귀 확인.

#### 9.9.4 테스트 통과 = 배포 가능 조건
- 위 9.9.1~9.9.3 통과 없이는 §9.10의 단계 진행 불가.

### 9.10 단계적 배포 / 롤백 계획
정책 변경은 환자 데이터에 영향. **feature flag 기반 단계 배포**로 안전하게 적용.

#### 9.10.1 Feature Flag
- 환경변수 또는 설정 기반 플래그 사용 (예: `ENABLE_SECONDARY_GUARDIAN_V2=true`).
- 플래그 off = 기존 동작 유지. on = 본 정책 적용.
- 서버, 앱 양쪽에 플래그 동기화.

#### 9.10.2 단계별 롤아웃 (권장 순서)
| 단계 | 변경 | 위험도 | 사전 조건 |
|---|---|---|---|
| 1 | 감사 로그 테이블 신설 (§7) | 낮음 | DDL 사전 승인 |
| 2 | §2.4 차단 케이스 + §6.4 미가입 UI 구분 | 낮음 | 단위 테스트 통과 |
| 3 | §6.3 SMS 본문 변경 (마스킹 제거) | 낮음 | SMS 발송 경로 회귀 통과 |
| 4 | §3 인증코드 단계 도입 (즉시 등록 제거) | 중 | 통합 테스트 통과, 기가입자 흐름 검증 |
| 5 | §6.1 10명 상한 적용 + 카운트 로직 | 중 | 기존 11명+ 환자 사전 조사 |
| 6 | §5.1 부보호자 자진 탈퇴 API 신규 | 중 | API + 푸시 통합 테스트 통과 |
| 7 | §5.3 CMS 주보호자 이관 (CMS 권한 분리 + 사유 입력) | 높음 | CMS 권한 모델 변경 사전 승인 |
| 8 | §4.4 면회 1일 1회 제약 | 높음 | 회귀 테스트 + 데이터 정합성 사전 조사 |

각 단계는 **이전 단계 안정화 확인 후** 진행.

#### 9.10.3 롤백 절차
| 변경 유형 | 롤백 방법 |
|---|---|
| 코드 변경 (로직만) | feature flag off → 즉시 이전 동작 |
| DDL 변경 | down 마이그레이션 스크립트 사전 작성 의무. 데이터 손실 가능성 점검 후 실행 |
| 데이터 백필 | 백업 후 진행. 롤백 시 백업 복원 |
| SMS/푸시 본문 변경 | 코드 revert로 즉시 복구 (외부 영향 없음) |

- 모든 DDL 변경에는 **down 스크립트가 함께 PR에 포함되어야** 머지 가능.

#### 9.10.4 배포 후 모니터링
배포 직후 24~48시간 다음 지표 모니터링:
- `[SECONDARY-GUARDIAN-*]`, `[SMS-SEND-FAIL]` 로그 발생률 (spec §9 참조)
- 부보호자 등록 / 삭제 / 자진 탈퇴 비율 (감사 로그 §7 기반)
- SMS 발송 성공률
- 면회 신청 성공률 (1일 1회 제약 적용 후 거부율 급증 여부)

이상 징후 발견 시 **즉시 feature flag off + 원인 조사**.

#### 9.10.5 비상 정지 권한
운영자가 **언제든 feature flag off로 정책 적용을 중단**할 수 있어야 함. 코드 재배포 없이 즉시 적용 가능한 형태로 구현.
