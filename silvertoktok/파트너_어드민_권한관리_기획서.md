> 대상 시스템: partner.silvertoktok.com  
> 목적: 파트너 어드민 내 계정별 기능 접근 권한을 세분화하여 관리

## 0. 배경 및 대표 사용 시나리오

### 초기 요청

> "면회예약 현황만 볼 수 있고, 다른 메뉴는 보이지 않는 계정이 필요하다."

병원 내에서 면회 업무만 담당하는 직원에게 어드민 계정을 주고 싶지만, 현재는 **모든 계정이 모든 기능에 접근 가능**하여 환자 정보, 운영 설정 등 불필요한 메뉴까지 노출되는 문제가 있다.

### 대표 시나리오: 면회 전용 계정 생성

이 기획의 권한 관리 시스템을 적용하면 다음과 같이 해결된다.

**설정 방법:**

1. 슈퍼관리자가 관리자 목록(`/user/manager`)에서 새 계정 생성
2. 역할: `열람자` (조회만) 또는 `관리자` (면회 일정 수정도 필요한 경우)
3. 권한 설정에서 **`visitation.manage` (면회 관리) 하나만 ON**, 나머지 17개 권한 전부 OFF

**결과:**

| 항목 | 동작 |
|------|------|
| 사이드바 | **면회관리 > 면회 관리** 메뉴만 표시, 나머지 전부 숨김 |
| 로그인 후 메인 | 면회 관리 페이지로 바로 이동 |
| 다른 URL 직접 접근 | "접근 권한이 없습니다" 페이지로 리다이렉트 |
| 서버 API | 면회 관련 API 외 모든 요청 403 차단 |

**이 계정이 보게 되는 화면:**

```
┌─────────────────────────────────────────┐
│ PARTNER                                  │
│ [VIP요양병원 ▾]                          │
│                                          │
│ 면회관리           >                      │
│   면회 관리  ← 이것만 보임                │
│                                          │
│                                          │
│                                          │
│                                          │
│   ──────────                             │
│   김면회담당                              │
│   열람자                                  │
│   [로그아웃]                              │
└─────────────────────────────────────────┘
```

> 이 시나리오를 기본으로, 동일한 방식으로 **운영 업무만 담당하는 계정**, **환자 관리만 담당하는 계정** 등 다양한 조합이 가능하다.

## 2. 권한 관리 시스템 설계

### 2.1 역할(Role) 체계

3단계 역할 체계를 도입한다.

| 역할 | 코드 | 설명 | 비고 |
|------|------|------|------|
| **슈퍼관리자** | `SUPER_ADMIN` | 모든 기능 접근 + 다른 계정의 권한 관리 가능 | 파트너(병원)당 최소 1명 |
| **관리자** | `ADMIN` | 슈퍼관리자가 부여한 권한 범위 내에서 모든 CRUD 가능 | 부서 책임자급 |
| **열람자** | `VIEWER` | 슈퍼관리자가 부여한 권한 범위 내에서 읽기만 가능 | 조회만 필요한 인원 |

#### 역할별 핵심 차이

```
슈퍼관리자: 권한 관리 메뉴 접근 가능 + 모든 기능 접근
관리자:     권한 관리 메뉴 접근 불가 + 허용된 기능 내 CRUD 가능
열람자:     권한 관리 메뉴 접근 불가 + 허용된 기능 내 읽기만 가능
```

### 2.2 권한(Permission) 단위

권한은 **메뉴 단위**로 부여한다. 각 메뉴에 대해 접근 가능 여부를 on/off 할 수 있다.

## 3. 데이터베이스 설계

### 3.1 테이블 설계

#### admin_roles 테이블

관리자 역할 정의 테이블.

```sql
CREATE TABLE admin_roles (
    id          INT PRIMARY KEY AUTO_INCREMENT,
    code        VARCHAR(20) NOT NULL UNIQUE,    -- 'SUPER_ADMIN', 'ADMIN', 'VIEWER'
    name        VARCHAR(50) NOT NULL,            -- '슈퍼관리자', '관리자', '열람자'
    description VARCHAR(200),
    created_at  DATETIME DEFAULT CURRENT_TIMESTAMP
);

-- 초기 데이터
INSERT INTO admin_roles (code, name, description) VALUES
('SUPER_ADMIN', '슈퍼관리자', '모든 기능 접근 및 권한 관리 가능'),
('ADMIN', '관리자', '부여된 권한 범위 내 CRUD 가능'),
('VIEWER', '열람자', '부여된 권한 범위 내 읽기만 가능');
```

#### admin_permissions 테이블

권한 항목 정의 테이블.

```sql
CREATE TABLE admin_permissions (
    id          INT PRIMARY KEY AUTO_INCREMENT,
    code        VARCHAR(50) NOT NULL UNIQUE,     -- 'patient.list', 'ops.push' 등
    name        VARCHAR(100) NOT NULL,            -- '환자 목록', '푸시보내기' 등
    category    VARCHAR(50) NOT NULL,             -- '회원 관리', '면회관리', '제증명', '환자 관리', '운영'
    sort_order  INT DEFAULT 0,                    -- 표시 순서
    created_at  DATETIME DEFAULT CURRENT_TIMESTAMP
);
```

#### 기존 관리자 테이블 수정 (admin_users 또는 managers)

기존 관리자 테이블에 역할 컬럼을 추가한다.

```sql
ALTER TABLE managers ADD COLUMN role_id INT NOT NULL DEFAULT 2
    REFERENCES admin_roles(id);
-- DEFAULT 2 = 'ADMIN' (기존 계정은 관리자로 설정)
```

#### admin_user_permissions 테이블 (핵심)

계정별 권한 매핑 테이블.

```sql
CREATE TABLE admin_user_permissions (
    id              INT PRIMARY KEY AUTO_INCREMENT,
    user_id         INT NOT NULL,                   -- managers 테이블의 ID
    permission_id   INT NOT NULL,                   -- admin_permissions 테이블의 ID
    granted         BOOLEAN NOT NULL DEFAULT TRUE,   -- 권한 부여 여부
    granted_by      INT NOT NULL,                    -- 권한을 부여한 슈퍼관리자 ID
    created_at      DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at      DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    UNIQUE KEY uk_user_permission (user_id, permission_id),
    FOREIGN KEY (user_id) REFERENCES managers(id) ON DELETE CASCADE,
    FOREIGN KEY (permission_id) REFERENCES admin_permissions(id),
    FOREIGN KEY (granted_by) REFERENCES managers(id)
);
```

#### admin_permission_logs 테이블

권한 변경 이력을 기록하는 감사(audit) 테이블.

```sql
CREATE TABLE admin_permission_logs (
    id              INT PRIMARY KEY AUTO_INCREMENT,
    user_id         INT NOT NULL,                    -- 대상 계정
    changed_by      INT NOT NULL,                    -- 변경한 슈퍼관리자
    action          VARCHAR(20) NOT NULL,            -- 'GRANT', 'REVOKE', 'ROLE_CHANGE'
    permission_code VARCHAR(50),                     -- 변경된 권한 코드 (역할 변경 시 NULL)
    old_value       VARCHAR(50),                     -- 이전 값
    new_value       VARCHAR(50),                     -- 새 값
    created_at      DATETIME DEFAULT CURRENT_TIMESTAMP
);
```

### 3.2 ERD 관계도

```
managers (기존)
    ├── 1:1 ── admin_roles (역할)
    ├── 1:N ── admin_user_permissions (계정별 권한)
    └── 1:N ── admin_permission_logs (변경 이력)

admin_permissions (권한 목록)
    └── 1:N ── admin_user_permissions
```

## 4. API 설계

### 4.1 권한 관리 API

| Method | Endpoint | 설명 | 접근 권한 |
|--------|----------|------|----------|
| `GET` | `/api/admin/roles` | 역할 목록 조회 | SUPER_ADMIN |
| `GET` | `/api/admin/permissions` | 전체 권한 목록 조회 | SUPER_ADMIN |
| `GET` | `/api/admin/users/{userId}/permissions` | 특정 계정의 권한 조회 | SUPER_ADMIN |
| `PUT` | `/api/admin/users/{userId}/permissions` | 특정 계정의 권한 수정 | SUPER_ADMIN |
| `PUT` | `/api/admin/users/{userId}/role` | 특정 계정의 역할 변경 | SUPER_ADMIN |
| `GET` | `/api/admin/permissions/logs` | 권한 변경 이력 조회 | SUPER_ADMIN |
| `GET` | `/api/admin/me/permissions` | 내 권한 조회 (로그인 시) | ALL |

## 6. 슈퍼관리자 계정 정책

### 6.1 초기 슈퍼관리자 설정

- 시스템 배포 시, **기존 관리자 중 1명을 슈퍼관리자로 지정** (DB에서 직접 변경)
- 최초 슈퍼관리자는 은톡톡 내부에서 수동 지정

### 6.2 슈퍼관리자 제약사항

| 규칙 | 설명 |
|------|------|
| 최소 1명 유지 | 파트너(병원)당 슈퍼관리자는 최소 1명이어야 한다 |
| 자기 자신 강등 불가 | 마지막 슈퍼관리자는 자신의 역할을 변경할 수 없다 |
| 슈퍼관리자 삭제 불가 | 슈퍼관리자 역할인 계정은 삭제 버튼이 비활성화된다 |
| 권한 전부 부여됨 | 슈퍼관리자는 admin_user_permissions 레코드와 관계없이 모든 권한을 가진다 |

### 6.3 슈퍼관리자만 할 수 있는 것

- 다른 관리자의 역할 변경 (관리자 <-> 열람자)
- 다른 관리자에게 슈퍼관리자 역할 부여
- 다른 관리자의 메뉴별 권한 설정
- 관리자 계정 생성/삭제
- 권한 변경 이력 조회

## 7. 보안 고려사항

### 7.1 백엔드 미들웨어

모든 API 요청에 대해 서버 사이드에서 권한을 검증해야 한다. 프론트엔드의 메뉴 숨김은 UX 편의이며, **실제 접근 제어는 반드시 서버에서 수행**한다.

```
요청 흐름:
[클라이언트] → [인증 미들웨어(JWT 검증)] → [권한 미들웨어(permission 확인)] → [컨트롤러]
```

#### 권한 미들웨어 동작

```javascript
// 미들웨어 예시 (pseudo-code)
function requirePermission(permissionCode) {
    return (req, res, next) => {
        const user = req.user; // JWT에서 파싱된 사용자 정보

        // 슈퍼관리자는 항상 통과
        if (user.role === 'SUPER_ADMIN') return next();

        // DB에서 해당 유저의 권한 확인
        const hasPermission = checkUserPermission(user.id, permissionCode);
        if (!hasPermission) {
            return res.status(403).json({ message: '접근 권한이 없습니다.' });
        }

        // 열람자는 GET 이외의 메서드 차단
        if (user.role === 'VIEWER' && req.method !== 'GET') {
            return res.status(403).json({ message: '읽기 전용 계정입니다.' });
        }

        next();
    };
}
```

### 7.2 추가 보안 사항

| 항목 | 설명 |
|------|------|
| 세션/토큰 갱신 | 권한 변경 시 해당 계정의 기존 토큰을 무효화하고 재로그인 유도 |
| 감사 로그 | 모든 권한 변경은 admin_permission_logs에 기록 |
| API 레이트 리밋 | 권한 관리 API에 레이트 리밋 적용 (분당 30회) |
| 입력값 검증 | permission code는 화이트리스트 방식으로 검증 |

## 8. 마이그레이션 계획

기존 운영 중인 시스템에 권한 관리를 추가하는 단계별 계획이다.

### Phase 1: 데이터베이스 & 백엔드 (우선)

1. `admin_roles`, `admin_permissions`, `admin_user_permissions`, `admin_permission_logs` 테이블 생성
2. `managers` 테이블에 `role_id` 컬럼 추가
3. 기존 관리자 계정에 기본값 설정: 최초 등록자 → `SUPER_ADMIN`, 나머지 → `ADMIN` + 전체 권한
4. 권한 관리 API 개발
5. 기존 API에 권한 미들웨어 추가 (초기에는 로깅만, 차단은 Phase 2에서)

### Phase 2: 프론트엔드

1. 로그인 응답에 권한 정보 포함
2. 사이드바 메뉴 동적 표시/숨김 구현
3. 라우트 가드 구현
4. 관리자 목록 페이지에 역할 컬럼 + 권한관리 버튼 추가
5. 계정 권한 관리 페이지 구현

### Phase 3: 활성화 & 검증

1. 백엔드 권한 미들웨어를 로깅 → 차단 모드로 전환
2. 슈퍼관리자 계정 확인 및 최종 세팅
3. 열람자(VIEWER) 쓰기 제한 활성화
4. 전체 기능 QA

## 부록: 파트너별 고려사항

현재 파트너 선택 드롭다운("VIP요양병원")이 존재하므로, 권한은 **파트너(병원) 단위로 독립**적으로 관리된다.

- 각 파트너(병원)마다 별도의 슈퍼관리자가 존재
- A 병원의 슈퍼관리자가 B 병원의 계정 권한을 관리할 수 없음
- 은톡톡 본사 어드민(별도 시스템)에서 파트너 간 관리가 필요하면 별도 기획 필요
