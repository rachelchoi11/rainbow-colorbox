## 1. 미팅 목표와 우리 포지션

### 1.1 목표
1. 센서가 **무엇을** 보내주는지 확정 (출력 항목·주기·전송 방식)
2. **누가 무엇을 판정하는지** 경계 확정 (센서 엣지 vs 우리 서버)
3. **책임 소재** 합의 (오탐·미탐 시)
4. PoC 범위·일정 합의
5. 인증 트랙 협의

### 1.2 우리 포지션 — 협상에서 강한 카드

> **센서 벤더는 대시보드를 만들지 않는다. 통합 파트너가 만든다.**

글로벌 선도 업체 **Vayyar Care**의 실제 구조 (공식 스펙 문서 확인):
- Vayyar 자체 앱·대시보드·SMS는 **"평가 또는 파일럿 기간에만"** 제공
- **정식 배포 시에는 파트너가 Webhook/MQTT/API로 자사 대시보드를 직접 구축**하는 B2B2C 구조
- 실제로 나스콜 업체(Austco), 관제 업체(Skyresponse)가 통합 파트너로 붙어 있음

**→ 이게 정확히 우리 포지션이다. 그리고 우리는 이미 만들었다.**

말할 문장:
> "센서에서 나오는 신호를 요양병원 현장이 실제로 쓰는 화면으로 만드는 게 저희 역할입니다. 이미 개발해 왔으니 먼저 보여드리겠습니다. 이 화면에 어떤 데이터가 들어와야 하는지를 오늘 맞춰보고 싶습니다."

## 2. 개발 완료 현황 — 실버톡톡 그룹웨어 (시연 자료)

요양병원 **내부 업무용 웹 그룹웨어**. 화면 프로토타입 완성 (mock 데이터 기준, DB/API는 연동 단계에서 구현).

- 스택: Next.js 16 · React 19 · TypeScript · Tailwind · shadcn/ui
- 규모: **4대 모듈 25개 페이지**, 멀티테넌트(병원 3곳), 역할 6종 권한 분기
- 검증: 전 라우트 정상, 타입·린트 에러 0

### 2.1 환자 모니터링 `/mon` — 오늘 미팅의 본체

| 화면 | 내용 |
|---|---|
| **실시간 현황** | 병동·호실 그리드. 환자별 호흡수·심박수·체동지수·수면단계·재실 여부. 5초 갱신 |
| **알림 이력** | 심각도·유형·상태별 필터, 추이 차트, 유형별 분포, **평균 응답시간**, 에스컬레이션 경과 강조 |
| **환자 목록·상세** | 8시간 바이탈 차트, **수면 리포트**(단계별 시간·수면효율·이석 횟수), 알림 이력 |
| **센서 장비** | 장비별 상태·배터리·마지막 통신. 오프라인/배터리부족 상단 고정 |
| **알림 규칙** | 유형별 임계값·지속시간·적용 시간대·수신 역할·에스컬레이션 시간 설정 |

**설계상 이미 반영한 것 (미팅에서 강조할 부분):**
- **오프라인 센서를 "정상"이 아니라 "관측 불가"로 분리** — 센서가 죽었는데 초록불이 켜지는 게 이 도메인 최대 위험이라, 회색 빗금 + "측정치 없음"으로 명시
- **`sustainSeconds`(지속 시간)** — 임계 초과가 N초 이상 지속돼야 알림. 오탐 억제 개념이 이미 들어가 있음
- **`escalateAfterMin`(에스컬레이션)** — 미확인 시 상급자 통보
- **임계값 조정 시 오탐↔놓침 트레이드오프를 UI에 명시**

### 2.2 나머지 3개 모듈 (연동과 무관하나 시연 시 전체 그림)
- **부서 보드** — 인수인계(근무조별), 필독 확인 추적, 부서별 게시판
- **상담** — 보호자 상담 배정·이력, 챗봇 예약 정책
- **전자결재** — 기안~결재, 결재선 자동 구성

### 2.3 ★ 이미 구현된 연동 시나리오 — 시연 하이라이트

> **낙상 알림 → 클릭 → 사고보고서 자동 기안**
> 환자·병실·발생시각·**당시 바이탈(호흡 20.7 / 심박 76)**이 자동으로 채워지고,
> 결재선(수간호사 합의 → 부서장 → 행정실장 → 병원장)이 실시간 구성됨.

**이게 센서 데이터가 병원 업무로 이어지는 그림이다.** IoT 업체에 "우리가 왜 필요한지"를 설명하는 가장 좋은 장면.

## 3. 연동 범위 (Scope)

### 3.1 데이터 흐름

```
[IoT 센서]  ─(①규격 협의)→  [수집/연동 계층]  ─→  [실버톡톡 웹]  ─(②가공)→  [보호자 앱]
 레이더·로봇                   MQTT/Webhook/API      병원 내부용              실버톡톡
                                                    · 실시간 현황            · 요약·리포트
                                                    · 알림/에스컬레이션       · 안심 정보
                                                    · 수면 리포트
                                                    · 사고보고서 연계
```

### 3.2 역할 분담 (제안 — 오늘 합의할 것)

| 영역 | IoT 업체 | 실버톡톡 |
|---|---|---|
| 센서 하드웨어·설치·유지보수 | ● | |
| 원시 신호 처리, **낙상/이석 판정** | ● | |
| 장비 상태(배터리·통신) 신호 제공 | ● | |
| 데이터 전송 규격·API 문서 제공 | ● | |
| **하드웨어 인증**(KC·전자파·의료기기) | ● | |
| 수집·저장·이력 관리 | 협의 | 협의 |
| **화면·대시보드·인사이트** | | ● |
| **알림 규칙·에스컬레이션 정책** | | ● |
| 병원 업무 연계(사고보고서 등) | | ● |
| **보호자 앱 가공·노출** | | ● |
| 병원 현장 운영·교육 | | ● (VIP와 함께) |

### 3.3 범위에서 **빼야** 할 것 (명확히)
- 실버톡톡은 **의학적 판단을 하지 않는다.** 센서가 준 값을 표시하고, 병원이 정한 기준에 따라 알릴 뿐이다.
- 실버톡톡은 **센서 정확도를 보증하지 않는다.** (계약서 명시 필요 — §6.4)

## 5. 내가 말해야 할 부분 (스크립트)

### 5.1 오프닝 — 포지션 선점
> "저희는 요양병원 보호자용 플랫폼을 운영하고 있고, VIP요양병원에서 실증 중입니다.
> 센서에서 나오는 데이터를 **현장이 실제로 쓰는 화면**으로 만드는 게 저희 역할입니다.
> 이미 개발해 왔으니 먼저 보여드리고, 여기 어떤 데이터가 들어와야 하는지 맞춰보고 싶습니다."

→ **바로 시연.** (`/mon/live` → `/mon/alerts` → 낙상 알림에서 사고보고서 기안까지)

### 5.2 시연하며 강조할 3가지
1. **"센서가 죽으면 정상이 아니라 관측 불가로 보여줍니다."**
   → 우리가 이 도메인을 이해하고 있다는 신호. 신뢰 확보.
2. **"알림은 지속시간·에스컬레이션·수신 역할까지 규칙으로 관리합니다."**
   → 우리는 단순 표시기가 아니라 운영 도구다.
3. **"낙상 알림이 사고보고서 기안으로 바로 이어집니다."**
   → 센서 데이터가 병원 업무로 연결되는 그림. 우리가 필요한 이유.

### 5.3 요구할 것 (명확히)
> "저희가 화면을 붙이려면 **데이터 규격 문서와 샘플 페이로드**가 필요합니다.
> 특히 **어떤 항목을 실제로 출력하시는지**, **낙상 판정을 어디서 하시는지**, 이 둘이 확정돼야 일정이 나옵니다."

### 5.4 인증 이야기를 꺼내는 방식 (§7 상세)
- ❌ **"의료기기 인증 받으셔야 합니다"** — **조사 결과 근거가 없다.** 2등급을 따도 수가·평가가점·복지용구·정부사업 어디에도 실익이 없고 비용만 40배다. 이렇게 말했다가 그쪽이 1억 쓰고 아무것도 못 얻으면 우리가 신뢰를 잃는다.
- ✅ **"웰니스 트랙을 같이 지키죠. 사용목적 문구를 서로 맞춥시다."** — 우리 화면 문구는 이미 그 기준으로 정리해뒀다.
- ✅ **"복지용구 「낙상알림시스템」이 2026.1.20 급여 품목으로 신설됐습니다. 1호 등재를 노려볼 만합니다."** ← **선물.** 관계가 "요구"에서 "기여"로 바뀐다.
- ✅ **"식약처 사전 검토를 같이 받으시죠. 무료고 10일이면 공식 회신이 옵니다."**
  → 협력 프레임. 우리가 원문까지 확인해 왔다는 것 자체가 신뢰 자산.

### 5.5 절대 하면 안 되는 말
- **"이걸로 낙상을 줄일 수 있습니다"** — §6.3. 근거가 없고, 아는 사람 앞에서 반박당한다.
- **"정확도 보증합니다"** — 우리가 보증할 수 없다.
- 보호자 앱 노출 범위를 **이 자리에서 확답하지 말 것** — VIP와 먼저 합의해야 한다 (§6.1).

## 6. 주의사항 · 리스크

### 6.1 ★ 최대 리스크 — 보호자 앱에 무엇을 보여줄 것인가

**이 프로젝트에서 가장 위험한 결정이다. 기술이 아니라 정책 문제.**

실시간 바이탈·낙상 알림을 보호자에게 그대로 노출하면:

| 리스크 | 내용 |
|---|---|
| **클레임 전가** | *"새벽에 엄마 심박 110이었는데 왜 아무도 안 갔냐"* — 병원이 아니라 **우리 화면 때문에** 발생 |
| **병원 반발** | 병원이 확인·조치하기 전에 보호자가 먼저 아는 구조. VIP가 받아들이기 어려움 |
| **의학적 해석 전가** | 비전문가인 보호자가 숫자를 해석하게 됨 |
| **규제 리스크** | 우리 앱이 의료적 판단을 제공하는 것으로 해석될 여지 증가 (§7) |

**권고 — 노출 범위를 계층으로 분리:**

| 대상 | 보여줄 것 | 보여주지 말 것 |
|---|---|---|
| **병원 (그룹웨어)** | 실시간 바이탈, 낙상·이석 알림, 센서 상태, 원시 추이 | — |
| **보호자 (앱)** | **가공·요약**: 주간 수면 리포트, "수면 양호/주의", 활동량 추이, 병원이 **확인·조치 완료한 후**의 사고 안내 | 실시간 심박·호흡 숫자, 미확인 낙상 알림, 센서 오류 |

> **이건 IoT 업체가 아니라 VIP요양병원과 먼저 합의할 사안이다.** 내일 미팅에서는 "보호자 노출 범위는 병원과 협의 중"으로 두고 확답하지 말 것.

### 6.2 ★ 오탐 — 전제해야 할 숫자

벤더가 "정확도 95~98%"를 제시할 가능성이 높다. **거의 전부 실험실·빈방 조건이다.**

| 근거 | 수치 |
|---|---|
| 실낙상 데이터로 13개 알고리즘 검증 | **민감도 57.0%** (실험실 시뮬레이션 대비 급락). 1일 오탐 3~85건<br>*Bagalà et al., PMC3353905* |
| mmWave 레이더 다중타겟 | 96.3% → **일상생활동작 추가 시 86.5%**<br>*Sensors 2024, 24(11):3660* |
| 침대이탈 알람 실측 (328일, 119건) | **오탐률 31~32%**, PPV 68%<br>*Subermaniam et al., Front Public Health 2017* |
| 지역사회 파일럿 | 낙상 알람 84건 중 **83건이 오탐** (진양성 1건)<br>*Bloch et al., PMC4662041* |
| 문헌의 자기 고백 | "실생활 조건의 민감도·특이도에 대한 지식은 **여전히 부족**" — 레이더 낙상감지의 구조적 공백 |

**→ "초기 배포 시 오탐 30%를 전제로 인력 운영 계획을 세운다"가 현실적 출발점.**

### 6.3 ★ 알림 피로 — 이건 사람을 죽인다

| 근거 | 수치 |
|---|---|
| Joint Commission | 임상 알람의 **85~99%가 실제 개입 불필요** |
| ICU 알람 분석 | **16.9%만 적절히 트리거**. 43.6% 순수 오탐 |
| FDA DB (2005.1~2010.6) | **알람 관련 사망 566건** |
| Joint Commission Sentinel Event (2009.1~2012.6) | 알람 관련 **사망 80건, 영구 기능손상 13건**. 실제 위해의 10% 미만만 포착된 수치로 추정 |

**야간 간호사 1명이 30병상을 본다. 알림이 하룻밤 50건 오면 전부 끈다. 그러면 시스템은 없는 것과 같다.**

→ 우리 `/mon/rules`의 지속시간·시간대 한정·고위험군 한정·에스컬레이션이 전부 이 문제 대응책. 미팅에서 설명할 것.

### 6.4 ★ 책임 소재 — 계약서에 반드시

센서가 낙상을 **놓쳤을 때**, 오탐으로 **인력이 소진됐을 때**, 알림이 늦어 **사고가 커졌을 때** — 누구 책임인가?

**우리는 "표시"만 하는데, 화면이 우리 것이라 클레임은 우리에게 온다.**

명시할 것:
- 센서 정확도·판정 로직의 책임은 **IoT 업체**
- 실버톡톡은 **수신한 데이터를 병원이 설정한 규칙에 따라 표시·전달**할 뿐, 의학적 판단·정확도를 보증하지 않음
- 병원의 임상적 조치 판단은 **병원 책임**
- 장애·오탐 발생 시 통보·대응 절차와 SLA

### 6.5 "낙상 감소"를 세일즈 포인트로 쓸 수 없다

| 근거 | 결론 |
|---|---|
| Shorr et al. 2012 — **27,672명 RCT** | 알람 사용을 **36배**로 늘렸는데 낙상률 변화 없음 (RR 1.09) |
| REFINE — 1,839명 | p=0.51 |
| Cochrane 리뷰 | "효과 불확실" |
| 요양시설 특화 리뷰 | *"bed alarms alone are relatively useless"* |

**→ 근거에 맞는 포지셔닝:**
- ❌ "낙상을 예방합니다"
- ✅ **"낙상 발견 지연을 줄이고, 조치 이력을 남깁니다"**
- ✅ **"인증평가·감사 대응 자료가 자동으로 쌓입니다"**

IoT 업체가 "낙상 30% 감소" 자료를 들고 오면 **근거를 물어야 한다.** 그 자료로 병원에 영업하면 나중에 우리가 같이 책임진다.

### 6.6 개인정보 — 미해결 리스크

- **치매 환자의 동의 주체가 법적 공백이다.** 의사결정능력이 저하된 성인의 개인정보 동의 주체에 대한 명문 조항을 찾지 못했다.
- 보호자 동의로 갈음 가능한지 **개인정보보호위원회 유권해석 질의**를 검토해야 한다.
- 로봇에 카메라·마이크가 포함되면 난이도가 급상승한다 (§4.4-26).

### 6.7 데이터 추상화 — 우리 쪽 숙제

현재 우리 코드는 `readingAt()` / `seriesFor()` 두 함수만 실제 API로 바꾸면 된다고 가정했으나, **이 가정은 틀렸다.**

| 우리 가정 | 현실 |
|---|---|
| 우리가 원시값을 받아 판정 | **센서가 엣지에서 이미 판정해서 이벤트를 올림** |
| 임의 시각 조회 가능 | **실제는 푸시(MQTT/Webhook).** 과거 조회는 우리 DB가 있어야 함 |
| 모든 값이 매 샘플마다 옴 | **벤더마다 출력 집합이 다름** (Vayyar는 호흡·심박 미출력) |
| 샘플링 30초 단일 | 원시 1Hz / Epoch 30초 / Trend 세션 **3계층** |
| 센서 = API | **드라이 콘택트면 접점 신호만 옴** |

→ `VitalsSource` 인터페이스 + `capabilities()`(벤더가 뭘 출력하는지 런타임에 앎) + 벤더 어댑터 **3계층 재설계 필요.** 미팅에서 규격이 확정되면 착수.

## 7. 의료기기 인증 — 컨설팅 자료

> ⚠️ **이 절은 변호사·인허가(RA) 전문가 검토가 아니다.** 법령·지침서 **원문을 직접 추출**해 작성했으나(2차 요약 미사용), 최종 판단은 **RA 전문가 + 의료법 변호사 검토가 필수**다.
> 상세: `~/workspace/silvertoktok-groupware/docs/medical-device-certification.md` (525줄, 1차 출처 링크 포함)

### 7.0 ★ 결론부터 — "인증 받으세요"라고 말하면 안 된다

조사 전 가설은 *"IoT 업체에 의료기기 인증을 제안한다"* 였다. **조사 결과 이 가설은 기각됐다.**

**2등급 의료기기를 취득해도 열리는 시장이 없다** [사실 기반]:

| 기대했던 것 | 실제 |
|---|---|
| 수가를 받을 수 있다 | ❌ **요양병원은 일당정액수가제.** 2등급을 따도 별도 산정 경로가 없다 |
| 평가에서 가점을 받는다 | ❌ **지표 자체가 없다.** 장기요양기관 평가매뉴얼 **218페이지 전문에서 `IoT`·`센서`·`스마트`·`인공지능`·`디지털` 검색 결과 0건** |
| 복지용구 등재에 필요하다 | ❌ 의료기기 허가는 등재 요건이 **아니다** |
| 정부사업에 필요하다 | ❌ 응급안전안심·AI 스마트홈 모두 의료기기 요구 **0회** |
| 병원 납품에 필요하다 | ❌ 법제처 유권해석: *"의료기기 해당 여부는 사용목적에 따라 결정되는 것이지 의료기관이 사용하는 경우만을 의료기기로 보는 것은 아니다"* |

**비용·기간 비교** [사실 — 법정 수수료 기준]:

| | **A. 웰니스 (비의료기기)** | **B. 2등급 의료기기** |
|---|---|---|
| 총 비용 | **약 300~450만원** | **수천만 ~ 1.5억원** |
| 총 기간 | **1~2개월** | **6개월 ~ 2년+** |
| 선행 요건 | 없음 | 제조업 허가 + **GMP 적합인정** + **품질책임자 선임** |
| SW 부담 | 없음 | **IEC 62304 C등급** (식약처 가이드라인이 "환자감시장치 SW = C등급"을 직접 예시) |
| 얻는 것 | — | **"의료기기" 명분 하나** |

> **→ B는 비용 40배·기간 10배를 내고 명분 하나를 사는 것이다. 현 시점에서 투자 대비 회수가 성립하지 않는다.**
>
> **미팅에서 "인증 받으세요"라고 했다가, 그쪽이 1억 쓰고 아무것도 못 얻으면 우리가 신뢰를 잃는다.**

### 7.1 ★ 진짜 경계선 — 질병명이 아니라 "위급상황 탐지 + 경보 + 의료진 전송"

**식약처 「의료기기와 개인용 건강관리(웰니스) 제품 판단기준」 지침서-0091-03 (2026.2 개정) 원문** [사실]

**위해도 판단요소 5개 중 하나라도 걸리면 고위해도:**
> ○ 생체적합성 문제를 야기하는지 / ○ 침습적인지 / ○ 작동 실패 시 상해·질병이 발생하는지
> ○ **심정지, 사망 등 위급한 상황을 탐지하는지 여부** ← 🔴 **우리 제품 정면 해당**
> ○ 기기의 기능·특성을 통제·변경하는지

**의사결정 흐름도 최종 관문:**
> ○ 심정지, 사망 등 위급한 상황을 탐지하는가? → **예 → 개인용 건강관리제품이 아님**

**고위해도로 명시된 예시:**
> ∙ **수면 시 무호흡 등의 측정 기능이 있는 수면 평가 장치** ☞ 위급한 상황을 탐지할 수 있으므로 위해도가 높다 **(개인용 건강관리제품이 아님)**

**반대로 웰니스로 인정된 인접 사례:**
> ○ 수면 중 **움직임 정도를 자가 측정**하는 제품 → 웰니스
> ○ **고령자의 낙상 위험도 측정**을 통해 보행교정이 가능하도록 도와주는 제품 → 웰니스 *(낙상 관련 유일 사례)*
> ↔ **(의료기기)** 위 앱의 데이터를 **진료 등에 사용하기 위해 의료기관(의료진)에 저장·전송하거나 분석하는 소프트웨어** ← 🔴 **우리 대시보드 구조와 유사**

**→ 경계선의 정정:**

| | **웰니스 (허용)** | **고위해도 (탈락)** |
|---|---|---|
| **시점** | **사전** 위험도 평가 | **실시간** 사고·이상 탐지 |
| **출력** | 기록·추이·가이드 | **응급 알림·경보** |
| **수신자** | 본인·가족 | **의료진(진료 목적)** |

**⚠️ 대법원 2008도7688** [사실]:
> 그 기구 등이 위 조항 소정의 목적으로 사용되는 것이면 되고 **객관적으로 그러한 성능을 가지고 있는가를 고려할 필요가 없으며**, … 사용목적은 **구조와 형태, 표시된 사용목적과 효과, 판매할 때의 선전 또는 설명**을 종합적으로 고려하여 결정한다.

**→ 기술이 아니라 문구가 법적 지위를 만든다. 성능이 실제로 없어도 "된다"고 광고하면 의료기기다.**

### 7.2 그런데 시장은 반대로 굴러간다 — 정면 충돌하는 두 사실

| 지침서 문언 | 국가·시장 실무 |
|---|---|
| "위급상황 탐지 → 웰니스 아님" | **복지부 응급안전안심서비스: 60GHz 레이더 + 호흡·심박 측정 + 서맥(40bpm) 알람 규정.** 사업안내서 **219쪽 전체에 "의료기기" 언급 0회** |
| "무호흡 측정 수면평가장치 → 의료기기" | **맥케어 "수면무호흡" 표방 + 요양병원 2만 대 보급** |
| — | **2026.1.20 시행 복지용구 고시: 「낙상알림시스템」**(= *"활동 상태를 관찰하여 **경보를 전하는** 목적의 제품"*)**을 급여 품목으로 신설. 의료기기 허가 요구 없음** |
| — | 스마트레이더시스템 복지부 **10만 대** 공급, 공시에 "의료기기" 0회 |

**[추정] 이 모순의 해소 방식**: 정부·업계는 제품을 **"활동량감지기"로 명명**하고 사용목적을 **"활동 감지·관찰"**로 표방해 흐름도의 "위급상황 탐지" 관문을 **문구상으로** 우회한다. 호흡·심박은 "움직임의 대상에 포함될 수 있는" 부수 항목으로 서술된다.

**⚠️ 반례 하나 — 미리 알고 가야 할 것 [미검증]**

**㈜비트센싱 `Wellune-M1`** — **60GHz FMCW 레이더로 2등급 "인증"을 받은 국내 선례**가 보고됐다 (허가번호 `D제인26-4021호`, 2026-06-05, 디지털의료기기 트랙).
사용목적 문구가 결정적이다:
> *"**의료진이 의료기관 내에서** 수면무호흡 증상이 있는 환자의 수면무호흡을 **선별**하기 위해 … **FMCW 레이더**를 통해 수집된 호흡신호를 …"*

- **함의**: "레이더 = 무조건 웰니스"가 아니다. **수면무호흡을 표방하면 2등급으로 가고, 실제로 통과한 회사가 있다.**
- **단 검증 상태**: 식약처 DB 재조회에 실패했고 언론보도가 없어 **교차검증되지 않았다. [미검증]으로 취급할 것.**
- **미팅 대응**: IoT 업체가 *"비트센싱은 인증받았던데요?"* 라고 하면 → *"맞습니다. 그런데 그쪽은 **수면무호흡 선별**을 사용목적으로 잡아서 갈 수밖에 없었던 겁니다. 우리가 그 문구를 안 쓰면 그 트랙을 탈 이유가 없습니다."*

**⚠️ 그리고 "시장에 깔려 있다"는 것은 적법성의 근거가 아니다:**
- 응급안전안심·복지용구는 **재가(독거노인=개인용)** 맥락. **요양병원 입원환자 모니터링은 법적 맥락이 다르다** [추정]
- 지침서 「Ⅴ. 지도점검」: 비의료기기를 의료용으로 표시·광고하거나 허가 없이 의료용으로 사용하면 **의료기기법 제26조에 따라 고발 또는 행정지도**
- **제26조① 위반(무허가 의료기기 사용) = 5년/5천만원.** 규율 대상에 **제조사와 사용 기관(병원)이 모두 포함**된다

### 7.3 ★ 권고 — "감지·경보 제품"이 아니라 "관찰·기록 제품"으로

**시나리오 A(웰니스) 유지.** 근거:
1. **B가 여는 시장이 없다** (§7.0)
2. **A가 여는 시장은 이미 크다** — 복지용구 「낙상알림시스템」 급여(2026.1.20 신설), 응급안전안심(10만 대 선례), 조달청 혁신제품, 요양병원 직납
3. **비용·기간이 자릿수로 다르다**
4. **국가가 직접 선례를 만들었다** — 복지부 규격서가 60GHz 레이더 + 호흡·심박 + 서맥 알람을 의료기기 요구 없이 규정

#### ✅ 해야 할 것 (제품·UI·마케팅)
1. **"감지·모니터링" → "관찰·기록".** 복지용구 고시가 쓰는 **"관찰알림"**이 국가가 승인한 안전한 어휘다
2. **"낙상 위험도"는 쓸 수 있다** — 지침서가 웰니스로 인정한 유일한 낙상 사례의 어휘. **"낙상 감지"(사후 탐지)와 "낙상 위험도"(사전 평가)를 엄격히 구분**
3. **주의 문구 삽입** (지침서 Ⅴ-3 권고):
   > "본 제품은 의료기기가 아니므로 질병 유무를 판단할 수 없으며, 질병 유무 판단을 위해서는 의사의 검진이 필요합니다."
4. **"낙상을 줄인다"고 말하지 않는다** — §6.5의 RCT 근거와도 일치. 규제·과학 양쪽에서 방어 불가

#### ❌ 영구 금지어
- **"호흡정지 / 심정지 / 무호흡 감지"** ← 지침서가 고위해도로 **명시한 유일한 항목**. 맥케어를 따라하면 안 된다
- "응급상황 **자동 감지**", "생명을 구합니다"
- "**진단**", "질병 **조기 발견**", "위험 **예측**"
- 의료진에게 **"진료 목적으로"** 데이터를 전송한다는 표현

#### ⚠️ 남는 리스크 (정직하게)
**우리 제품의 핵심 가치(실시간 이상 알림)와 웰니스 유지 조건(위급상황 탐지 표방 금지)은 정면 충돌한다.**
문구를 아무리 다듬어도 **실제 기능이 "야간에 환자가 숨을 안 쉬면 간호사를 부른다"라면** 식약처가 실질로 판단할 여지가 있다 [추정].
**이 리스크는 문구로 완전히 제거되지 않는다. 사전 질의(§7.5-1)가 유일한 확실한 방어책이다.**

### 7.4 우리(실버톡톡)가 이미 반영한 것

라벨을 **관측 사실 진술**로 전면 교체 완료:

| 변경 전 | 변경 후 |
|---|---|
| `호흡 저하` | **`호흡수 기준 미만`** |
| `호흡 과다` | **`호흡수 기준 초과`** |
| `심박 이상` | **`심박수 기준 범위 밖`** |
| "심박수가 **정상 범위**를 벗어났습니다" | "심박수가 **설정 범위**를 벗어났습니다" |

- 코드 주석에 근거를 명시하고 **"수면 리포트에 수면무호흡 지표를 절대 추가하지 말 것"** 을 못박음
- 라벨이 단일 원천이라 한 곳 수정으로 전 화면 반영
- **남은 과제**: `FALL: "낙상 감지"` 는 지침서 기준 **위험한 쪽**에 있다. `"낙상 알림"`/`"활동 관찰"` 계열로 재검토 필요 (§8.2)

**→ 미팅에서 이 얘기를 하면 "이 회사는 규제를 이해하고 있다"는 강한 신호가 된다.**

### 7.5 ★ IoT 업체에 제안할 것 — 3가지

**① "인증 받으세요"가 아니라 "웰니스 트랙을 같이 지키자"**

> "저희가 식약처 지침서 원문을 확인해봤는데, 경계선이 **질병명이 아니라 '위급상황 탐지 + 경보'** 에 있더라고요.
> 2등급을 따도 요양병원은 일당정액수가라 수가가 없고, 평가 가점 지표도 **아예 없습니다**. 비용은 40배고요.
> 그래서 **웰니스 트랙을 유지하되, 사용목적 문구를 서로 맞추는 게** 맞다고 봅니다.
> 저희 화면 문구는 이미 그 기준으로 정리해뒀습니다."

**② 🎁 선물 — 복지용구 「낙상알림시스템」 급여 (2026.1.20 신설)**

> "**2026년 1월 20일 시행 고시로 「낙상알림시스템」이 복지용구 급여 품목으로 신설**됐습니다.
> *'활동 상태를 관찰하여 경보를 전하는 목적의 제품'* 으로 정의돼 있고, **의료기기 허가를 요구하지 않습니다.**
> **신설된 지 얼마 안 돼서 1호 등재를 노려볼 수 있습니다.**"

→ 인증 비용을 쓰라는 말보다 **돈이 되는 트랙을 알려주는 것**이 훨씬 강한 카드다. 관계의 성격이 "요구"에서 "기여"로 바뀐다.

**③ 「의료기기 해당 여부 검토」를 같이 받자 — 무료, 10일**

> "「의료기기 허가·신고·심사 등에 관한 규정」 **제60조**에 사전 검토 제도가 있습니다.
> 사용목적 자료를 내면 **식약처장이 10일 내에 공식 회신**을 줍니다. **무료입니다.**
> 사용목적 문구를 **2~3안으로 준비해서 어디서 선이 갈리는지** 공식 회신을 받아두면, 나중에 마케팅·계약 리스크가 사라집니다.
> ☎ 043-719-3758"

→ **이게 이 문서 전체에서 가장 중요한 액션이다.** 이것 없이는 웰니스 트랙 전체가 추정 위에 서 있다.

### 7.6 IoT 업체에 확인할 것 (§4.4 보강)
- 현재 사용목적을 **문서상 어떻게 표기**하고 있나? (카탈로그·제안서·홈페이지 문구)
- **"수면무호흡"·"호흡정지 감지"** 표현을 쓰고 있나? ← 쓰고 있으면 리스크 공유 필요
- 「의료기기 해당 여부 검토」를 받은 적이 있나? 회신 문서가 있나?
- 복지용구·조달청·정부사업 등재 이력이 있나?

### 7.7 ⚠️ 이 절의 한계 (정직하게)
- 요양병원 **인증기준 원문 PDF**는 다운로드 게이팅으로 확보 실패 → §7.0의 "평가 가점 없음"은 장기요양·심평원은 1차 출처, 요양병원 인증은 2차 출처 기반
- **혁신의료기기 지정·규제샌드박스**는 조사 미완 — 별도 확인 필요
- **"의료기기 요구 공고가 없다"는 부존재 증명이 불가능**하다. 정확히는 **"발견하지 못했다"**이다
- 조사 중 한 공고 페이지의 **자동요약이 "주요 자격요건: 의료기기 관련 인증"이라는 허위를 생성**했다(원문에 없는 문구). **이 절의 인용은 전부 원문 직접 추출이며, 2차 요약을 근거로 쓰지 말 것**
