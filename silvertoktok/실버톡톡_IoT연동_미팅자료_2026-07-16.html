0. 한 장 요약

항목 내용
우리 포지션 센서 데이터를 받아 화면·인사이트·모니터링을 만드는 통합 파트너. 대시보드 웹은 이미 개발 완료(시연 가능)
연동 구조 IoT 센서 → (규격 협의) → 실버톡톡 웹(병원용 그룹웨어) → 가공·요약 → 실버톡톡 앱(보호자용)
오늘 확정할 것 ① 데이터 규격·전송 방식 ② 낙상 판정 주체(엣지/클라우드) ③ 학습기간 ④ 역할·책임 경계 ⑤ 인증 트랙
최대 쟁점 보호자 앱 노출 범위 — 실시간 바이탈·낙상 알림을 보호자에게 그대로 주면 안 된다 (§6.1)
⚠️ 인증 제안 — 방향 전환 "의료기기 인증 받으세요"라고 하면 안 된다. 조사 결과 2등급을 따도 열리는 시장이 없다(수가 ❌ / 평가 가점 ❌ / 복지용구 요건 ❌ / 정부사업 요구 ❌). 비용 40배·기간 10배를 내고 "명분" 하나를 사는 셈. 대신 웰니스 트랙을 함께 지키자고 제안하고, 복지용구 「낙상알림시스템」 급여(2026.1.20 신설) 를 기회로 제시 (§7)
전제할 숫자 초기 오탐 30%. 벤더가 "정확도 95%"라 해도 실환경은 다르다 (§6.2)

1. 미팅 목표와 우리 포지션

1.1 목표

  1. 센서가 무엇을 보내주는지 확정 (출력 항목·주기·전송 방식)
  2. 누가 무엇을 판정하는지 경계 확정 (센서 엣지 vs 우리 서버)
  3. 책임 소재 합의 (오탐·미탐 시)
  4. PoC 범위·일정 합의
  5. 인증 트랙 협의

1.2 우리 포지션 — 협상에서 강한 카드

센서 벤더는 대시보드를 만들지 않는다. 통합 파트너가 만든다.

글로벌 선도 업체 Vayyar Care의 실제 구조 (공식 스펙 문서 확인):

  • Vayyar 자체 앱·대시보드·SMS는 "평가 또는 파일럿 기간에만" 제공
  • 정식 배포 시에는 파트너가 Webhook/MQTT/API로 자사 대시보드를 직접 구축하는 B2B2C 구조
  • 실제로 나스콜 업체(Austco), 관제 업체(Skyresponse)가 통합 파트너로 붙어 있음

→ 이게 정확히 우리 포지션이다. 그리고 우리는 이미 만들었다.

말할 문장:

"센서에서 나오는 신호를 요양병원 현장이 실제로 쓰는 화면으로 만드는 게 저희 역할입니다. 이미 개발해 왔으니 먼저 보여드리겠습니다. 이 화면에 어떤 데이터가 들어와야 하는지를 오늘 맞춰보고 싶습니다."

2. 개발 완료 현황 — 실버톡톡 그룹웨어 (시연 자료)

요양병원 내부 업무용 웹 그룹웨어. 화면 프로토타입 완성 (mock 데이터 기준, DB/API는 연동 단계에서 구현).

  • 스택: Next.js 16 · React 19 · TypeScript · Tailwind · shadcn/ui
  • 규모: 4대 모듈 25개 페이지, 멀티테넌트(병원 3곳), 역할 6종 권한 분기
  • 검증: 전 라우트 정상, 타입·린트 에러 0

2.1 환자 모니터링 /mon — 오늘 미팅의 본체

화면 내용
실시간 현황 병동·호실 그리드. 환자별 호흡수·심박수·체동지수·수면단계·재실 여부. 5초 갱신
알림 이력 심각도·유형·상태별 필터, 추이 차트, 유형별 분포, 평균 응답시간, 에스컬레이션 경과 강조
환자 목록·상세 8시간 바이탈 차트, 수면 리포트(단계별 시간·수면효율·이석 횟수), 알림 이력
센서 장비 장비별 상태·배터리·마지막 통신. 오프라인/배터리부족 상단 고정
알림 규칙 유형별 임계값·지속시간·적용 시간대·수신 역할·에스컬레이션 시간 설정

설계상 이미 반영한 것 (미팅에서 강조할 부분):

  • 오프라인 센서를 "정상"이 아니라 "관측 불가"로 분리 — 센서가 죽었는데 초록불이 켜지는 게 이 도메인 최대 위험이라, 회색 빗금 + "측정치 없음"으로 명시
  • sustainSeconds(지속 시간) — 임계 초과가 N초 이상 지속돼야 알림. 오탐 억제 개념이 이미 들어가 있음
  • escalateAfterMin(에스컬레이션) — 미확인 시 상급자 통보
  • 임계값 조정 시 오탐↔놓침 트레이드오프를 UI에 명시

2.2 나머지 3개 모듈 (연동과 무관하나 시연 시 전체 그림)

  • 부서 보드 — 인수인계(근무조별), 필독 확인 추적, 부서별 게시판
  • 상담 — 보호자 상담 배정·이력, 챗봇 예약 정책
  • 전자결재 — 기안~결재, 결재선 자동 구성

2.3 ★ 이미 구현된 연동 시나리오 — 시연 하이라이트

낙상 알림 → 클릭 → 사고보고서 자동 기안 환자·병실·발생시각·**당시 바이탈(호흡 20.7 / 심박 76)**이 자동으로 채워지고, 결재선(수간호사 합의 → 부서장 → 행정실장 → 병원장)이 실시간 구성됨.

이게 센서 데이터가 병원 업무로 이어지는 그림이다. IoT 업체에 "우리가 왜 필요한지"를 설명하는 가장 좋은 장면.

                                                    · 수면 리포트

3.3 범위에서 빼야 할 것 (명확히)

  • 실버톡톡은 의학적 판단을 하지 않는다. 센서가 준 값을 표시하고, 병원이 정한 기준에 따라 알릴 뿐이다.
  • 실버톡톡은 센서 정확도를 보증하지 않는다. (계약서 명시 필요 — §6.4)

4. IoT 업체에 확인해야 할 사항 ✅

이 표를 그대로 들고 가서 채우면 된다. 답이 안 나오는 항목이 곧 리스크다.

4.1 센서·출력 항목 [최우선]

# 질문 왜 중요한가 답변
1 센서 종류·주파수 (UWB / mmWave / 도플러 / 열화상 / 카메라) 측정 가능 항목이 여기서 갈림
2 실제 출력 항목: 재실 / 낙상 / 호흡수 / 심박수 / 수면단계 / 자세 / 위치좌표 / 활동량 중 무엇? Vayyar는 호흡·심박·수면단계를 아예 출력하지 않는다. 우리 화면은 이 값들을 전제로 만들었음
3 항목별 유효 거리·조건 맥케어는 호흡 5m인데 심박은 2m. 천장 설치면 심박은 상시 부정확
4 심박수는 정말 신뢰 가능한가? 검증 최상위 제품(Somnofy)은 심박만은 레이더로 안 재고 별도 심박벨트를 붙인다
5 다인실 간섭 / 커튼·이불 / 금속 침대프레임 / 방문객 영향 요양병원은 2~6인실. 업계에 검증 연구가 없음
6 설치 조건 (천장/벽/스탠드), 전원, 네트워크 현장 공사 범위

4.2 낙상 판정 로직 [최우선]

# 질문 왜 중요한가 답변
7 낙상 판정을 어디서 하나? 센서 엣지 / 자사 클라우드 / 우리가? 우리 규칙 엔진 설계가 여기서 갈림
8 판정 상태머신과 지연 시간은? Vayyar: 의심 50초 → 확인 40초 → 알림 30초 = 총 90초 이상 의도적 지연. 즉시 알림은 업계 표준이 아님
9 "바닥에 오래 누워있음"(fall + no motion) 별도 로직이 있나? Vayyar는 낙상 순간을 놓쳐도 이걸로 잡음(5~12분)
10 타인 입실 시 자동 취소 같은 오탐 억제 로직이 있나?
11 학습 기간(Learning Mode)이 있나? Vayyar 2주, 사이렌케어 최소 2주. 없으면 PoC 첫 주에 오탐 폭탄
12 오탐률 근거를 주실 수 있나? 실험실인가 실환경인가 §6.2 참조. "95% 정확도"는 대개 실험실·빈방

4.3 연동 규격

# 질문 왜 중요한가 답변

14 API 문서·데이터 스키마 샘플을 주실 수 있나? 없으면 일정 산정 불가

5. 내가 말해야 할 부분 (스크립트)

5.1 오프닝 — 포지션 선점

"저희는 요양병원 보호자용 플랫폼을 운영하고 있고, VIP요양병원에서 실증 중입니다. 센서에서 나오는 데이터를 현장이 실제로 쓰는 화면으로 만드는 게 저희 역할입니다. 이미 개발해 왔으니 먼저 보여드리고, 여기 어떤 데이터가 들어와야 하는지 맞춰보고 싶습니다."

→ 바로 시연. (/mon/live → /mon/alerts → 낙상 알림에서 사고보고서 기안까지)

5.2 시연하며 강조할 3가지

  1. "센서가 죽으면 정상이 아니라 관측 불가로 보여줍니다." → 우리가 이 도메인을 이해하고 있다는 신호. 신뢰 확보.
  2. "알림은 지속시간·에스컬레이션·수신 역할까지 규칙으로 관리합니다." → 우리는 단순 표시기가 아니라 운영 도구다.
  3. "낙상 알림이 사고보고서 기안으로 바로 이어집니다." → 센서 데이터가 병원 업무로 연결되는 그림. 우리가 필요한 이유.

5.3 요구할 것 (명확히)

"저희가 화면을 붙이려면 데이터 규격 문서와 샘플 페이로드가 필요합니다. 특히 어떤 항목을 실제로 출력하시는지, 낙상 판정을 어디서 하시는지, 이 둘이 확정돼야 일정이 나옵니다."

5.4 인증 이야기를 꺼내는 방식 (§7 상세)

  • ❌ "의료기기 인증 받으셔야 합니다" — 조사 결과 근거가 없다. 2등급을 따도 수가·평가가점·복지용구·정부사업 어디에도 실익이 없고 비용만 40배다. 이렇게 말했다가 그쪽이 1억 쓰고 아무것도 못 얻으면 우리가 신뢰를 잃는다.
  • ✅ "웰니스 트랙을 같이 지키죠. 사용목적 문구를 서로 맞춥시다." — 우리 화면 문구는 이미 그 기준으로 정리해뒀다.
  • ✅ "복지용구 「낙상알림시스템」이 2026.1.20 급여 품목으로 신설됐습니다. 1호 등재를 노려볼 만합니다." ← 선물. 관계가 "요구"에서 "기여"로 바뀐다.
  • ✅ "식약처 사전 검토를 같이 받으시죠. 무료고 10일이면 공식 회신이 옵니다." → 협력 프레임. 우리가 원문까지 확인해 왔다는 것 자체가 신뢰 자산.

5.5 절대 하면 안 되는 말

  • "이걸로 낙상을 줄일 수 있습니다" — §6.3. 근거가 없고, 아는 사람 앞에서 반박당한다.
  • "정확도 보증합니다" — 우리가 보증할 수 없다.
  • 보호자 앱 노출 범위를 이 자리에서 확답하지 말 것 — VIP와 먼저 합의해야 한다 (§6.1).

6. 주의사항 · 리스크

6.1 ★ 최대 리스크 — 보호자 앱에 무엇을 보여줄 것인가

이 프로젝트에서 가장 위험한 결정이다. 기술이 아니라 정책 문제.

실시간 바이탈·낙상 알림을 보호자에게 그대로 노출하면:

리스크 내용
클레임 전가 "새벽에 엄마 심박 110이었는데 왜 아무도 안 갔냐" — 병원이 아니라 우리 화면 때문에 발생
병원 반발 병원이 확인·조치하기 전에 보호자가 먼저 아는 구조. VIP가 받아들이기 어려움
의학적 해석 전가 비전문가인 보호자가 숫자를 해석하게 됨
규제 리스크 우리 앱이 의료적 판단을 제공하는 것으로 해석될 여지 증가 (§7)

권고 — 노출 범위를 계층으로 분리:

대상 보여줄 것 보여주지 말 것
병원 (그룹웨어) 실시간 바이탈, 낙상·이석 알림, 센서 상태, 원시 추이 —
보호자 (앱) 가공·요약: 주간 수면 리포트, "수면 양호/주의", 활동량 추이, 병원이 확인·조치 완료한 후의 사고 안내 실시간 심박·호흡 숫자, 미확인 낙상 알림, 센서 오류

이건 IoT 업체가 아니라 VIP요양병원과 먼저 합의할 사안이다. 내일 미팅에서는 "보호자 노출 범위는 병원과 협의 중"으로 두고 확답하지 말 것.

6.4 ★ 책임 소재 — 계약서에 반드시

센서가 낙상을 놓쳤을 때, 오탐으로 인력이 소진됐을 때, 알림이 늦어 사고가 커졌을 때 — 누구 책임인가?

우리는 "표시"만 하는데, 화면이 우리 것이라 클레임은 우리에게 온다.

명시할 것:

  • 센서 정확도·판정 로직의 책임은 IoT 업체
  • 실버톡톡은 수신한 데이터를 병원이 설정한 규칙에 따라 표시·전달할 뿐, 의학적 판단·정확도를 보증하지 않음
  • 병원의 임상적 조치 판단은 병원 책임
  • 장애·오탐 발생 시 통보·대응 절차와 SLA

6.5 "낙상 감소"를 세일즈 포인트로 쓸 수 없다

근거 결론
Shorr et al. 2012 — 27,672명 RCT 알람 사용을 36배로 늘렸는데 낙상률 변화 없음 (RR 1.09)
REFINE — 1,839명 p=0.51
Cochrane 리뷰 "효과 불확실"
요양시설 특화 리뷰 "bed alarms alone are relatively useless"

→ 근거에 맞는 포지셔닝:

  • ❌ "낙상을 예방합니다"
  • ✅ "낙상 발견 지연을 줄이고, 조치 이력을 남깁니다"
  • ✅ "인증평가·감사 대응 자료가 자동으로 쌓입니다"

IoT 업체가 "낙상 30% 감소" 자료를 들고 오면 근거를 물어야 한다. 그 자료로 병원에 영업하면 나중에 우리가 같이 책임진다.

6.6 개인정보 — 미해결 리스크

  • 치매 환자의 동의 주체가 법적 공백이다. 의사결정능력이 저하된 성인의 개인정보 동의 주체에 대한 명문 조항을 찾지 못했다.
  • 보호자 동의로 갈음 가능한지 개인정보보호위원회 유권해석 질의를 검토해야 한다.
  • 로봇에 카메라·마이크가 포함되면 난이도가 급상승한다 (§4.4-26).

6.7 데이터 추상화 — 우리 쪽 숙제

현재 우리 코드는 readingAt() / seriesFor() 두 함수만 실제 API로 바꾸면 된다고 가정했으나, 이 가정은 틀렸다.

우리 가정 현실
우리가 원시값을 받아 판정 센서가 엣지에서 이미 판정해서 이벤트를 올림
임의 시각 조회 가능 실제는 푸시(MQTT/Webhook). 과거 조회는 우리 DB가 있어야 함
모든 값이 매 샘플마다 옴 벤더마다 출력 집합이 다름 (Vayyar는 호흡·심박 미출력)
샘플링 30초 단일 원시 1Hz / Epoch 30초 / Trend 세션 3계층
센서 = API 드라이 콘택트면 접점 신호만 옴

→ VitalsSource 인터페이스 + capabilities()(벤더가 뭘 출력하는지 런타임에 앎) + 벤더 어댑터 3계층 재설계 필요. 미팅에서 규격이 확정되면 착수.

7. 의료기기 인증 — 컨설팅 자료

7.0 ★ 결론부터 — "인증 받으세요"라고 말하면 안 된다

조사 전 가설은 "IoT 업체에 의료기기 인증을 제안한다" 였다. 조사 결과 이 가설은 기각됐다.

2등급 의료기기를 취득해도 열리는 시장이 없다 [사실 기반]:

기대했던 것 실제

정부사업에 필요하다 ❌ 응급안전안심·AI 스마트홈 모두 의료기기 요구 0회

7.1 ★ 진짜 경계선 — 질병명이 아니라 "위급상황 탐지 + 경보 + 의료진 전송"

식약처 「의료기기와 개인용 건강관리(웰니스) 제품 판단기준」 지침서-0091-03 (2026.2 개정) 원문 [사실]

위해도 판단요소 5개 중 하나라도 걸리면 고위해도:

○ 생체적합성 문제를 야기하는지 / ○ 침습적인지 / ○ 작동 실패 시 상해·질병이 발생하는지 ○ 심정지, 사망 등 위급한 상황을 탐지하는지 여부 ← 🔴 우리 제품 정면 해당 ○ 기기의 기능·특성을 통제·변경하는지

의사결정 흐름도 최종 관문:

○ 심정지, 사망 등 위급한 상황을 탐지하는가? → 예 → 개인용 건강관리제품이 아님

고위해도로 명시된 예시:

∙ 수면 시 무호흡 등의 측정 기능이 있는 수면 평가 장치 ☞ 위급한 상황을 탐지할 수 있으므로 위해도가 높다 (개인용 건강관리제품이 아님)

반대로 웰니스로 인정된 인접 사례:

○ 수면 중 움직임 정도를 자가 측정하는 제품 → 웰니스 ○ 고령자의 낙상 위험도 측정을 통해 보행교정이 가능하도록 도와주는 제품 → 웰니스 (낙상 관련 유일 사례) ↔ (의료기기) 위 앱의 데이터를 진료 등에 사용하기 위해 의료기관(의료진)에 저장·전송하거나 분석하는 소프트웨어 ← 🔴 우리 대시보드 구조와 유사

→ 경계선의 정정:

웰니스 (허용) 고위해도 (탈락)
시점 사전 위험도 평가 실시간 사고·이상 탐지

  • 미팅 대응: IoT 업체가 "비트센싱은 인증받았던데요?" 라고 하면 → *"맞습니다. 그런데 그쪽은 수면무호흡 선별을 사용목적으로 잡아서 갈 수밖에 없었던 겁니다. 우리가 그 문구를 안 쓰면 그 트랙을 탈 이유가 없습니다."*

⚠️ 그리고 "시장에 깔려 있다"는 것은 적법성의 근거가 아니다:

  • 응급안전안심·복지용구는 재가(독거노인=개인용) 맥락. 요양병원 입원환자 모니터링은 법적 맥락이 다르다 [추정]
  • 지침서 「Ⅴ. 지도점검」: 비의료기기를 의료용으로 표시·광고하거나 허가 없이 의료용으로 사용하면 의료기기법 제26조에 따라 고발 또는 행정지도
  • 제26조① 위반(무허가 의료기기 사용) = 5년/5천만원. 규율 대상에 제조사와 사용 기관(병원)이 모두 포함된다

7.3 ★ 권고 — "감지·경보 제품"이 아니라 "관찰·기록 제품"으로

시나리오 A(웰니스) 유지. 근거:

  1. B가 여는 시장이 없다 (§7.0)
  2. A가 여는 시장은 이미 크다 — 복지용구 「낙상알림시스템」 급여(2026.1.20 신설), 응급안전안심(10만 대 선례), 조달청 혁신제품, 요양병원 직납
  3. 비용·기간이 자릿수로 다르다
  4. 국가가 직접 선례를 만들었다 — 복지부 규격서가 60GHz 레이더 + 호흡·심박 + 서맥 알람을 의료기기 요구 없이 규정

✅ 해야 할 것 (제품·UI·마케팅)

  1. "감지·모니터링" → "관찰·기록". 복지용구 고시가 쓰는 **"관찰알림"**이 국가가 승인한 안전한 어휘다
  2. "낙상 위험도"는 쓸 수 있다 — 지침서가 웰니스로 인정한 유일한 낙상 사례의 어휘. "낙상 감지"(사후 탐지)와 "낙상 위험도"(사전 평가)를 엄격히 구분
  3. 주의 문구 삽입 (지침서 Ⅴ-3 권고):

    "본 제품은 의료기기가 아니므로 질병 유무를 판단할 수 없으며, 질병 유무 판단을 위해서는 의사의 검진이 필요합니다."

  4. "낙상을 줄인다"고 말하지 않는다 — §6.5의 RCT 근거와도 일치. 규제·과학 양쪽에서 방어 불가

❌ 영구 금지어

  • "호흡정지 / 심정지 / 무호흡 감지" ← 지침서가 고위해도로 명시한 유일한 항목. 맥케어를 따라하면 안 된다
  • "응급상황 자동 감지", "생명을 구합니다"
  • "진단", "질병 조기 발견", "위험 예측"
  • 의료진에게 "진료 목적으로" 데이터를 전송한다는 표현

⚠️ 남는 리스크 (정직하게)

우리 제품의 핵심 가치(실시간 이상 알림)와 웰니스 유지 조건(위급상황 탐지 표방 금지)은 정면 충돌한다. 문구를 아무리 다듬어도 실제 기능이 "야간에 환자가 숨을 안 쉬면 간호사를 부른다"라면 식약처가 실질로 판단할 여지가 있다 [추정]. 이 리스크는 문구로 완전히 제거되지 않는다. 사전 질의(§7.5-1)가 유일한 확실한 방어책이다.

7.4 우리(실버톡톡)가 이미 반영한 것

라벨을 관측 사실 진술로 전면 교체 완료:

변경 전 변경 후
호흡 저하 호흡수 기준 미만
호흡 과다 호흡수 기준 초과
심박 이상 심박수 기준 범위 밖
"심박수가 정상 범위를 벗어났습니다" "심박수가 설정 범위를 벗어났습니다"
  • 코드 주석에 근거를 명시하고 "수면 리포트에 수면무호흡 지표를 절대 추가하지 말 것" 을 못박음
  • 라벨이 단일 원천이라 한 곳 수정으로 전 화면 반영
  • 남은 과제: FALL: "낙상 감지" 는 지침서 기준 위험한 쪽에 있다. "낙상 알림"/"활동 관찰" 계열로 재검토 필요 (§8.2)

→ 미팅에서 이 얘기를 하면 "이 회사는 규제를 이해하고 있다"는 강한 신호가 된다.

7.5 ★ IoT 업체에 제안할 것 — 3가지

① "인증 받으세요"가 아니라 "웰니스 트랙을 같이 지키자"

"저희가 식약처 지침서 원문을 확인해봤는데, 경계선이 질병명이 아니라 '위급상황 탐지 + 경보' 에 있더라고요. 2등급을 따도 요양병원은 일당정액수가라 수가가 없고, 평가 가점 지표도 아예 없습니다. 비용은 40배고요. 그래서 웰니스 트랙을 유지하되, 사용목적 문구를 서로 맞추는 게 맞다고 봅니다. 저희 화면 문구는 이미 그 기준으로 정리해뒀습니다."

② 🎁 선물 — 복지용구 「낙상알림시스템」 급여 (2026.1.20 신설)

"2026년 1월 20일 시행 고시로 「낙상알림시스템」이 복지용구 급여 품목으로 신설됐습니다. '활동 상태를 관찰하여 경보를 전하는 목적의 제품' 으로 정의돼 있고, 의료기기 허가를 요구하지 않습니다. 신설된 지 얼마 안 돼서 1호 등재를 노려볼 수 있습니다."

→ 인증 비용을 쓰라는 말보다 돈이 되는 트랙을 알려주는 것이 훨씬 강한 카드다. 관계의 성격이 "요구"에서 "기여"로 바뀐다.

③ 「의료기기 해당 여부 검토」를 같이 받자 — 무료, 10일

"「의료기기 허가·신고·심사 등에 관한 규정」 제60조에 사전 검토 제도가 있습니다. 사용목적 자료를 내면 식약처장이 10일 내에 공식 회신을 줍니다. 무료입니다. 사용목적 문구를 2~3안으로 준비해서 어디서 선이 갈리는지 공식 회신을 받아두면, 나중에 마케팅·계약 리스크가 사라집니다. ☎ 043-719-3758"

→ 이게 이 문서 전체에서 가장 중요한 액션이다. 이것 없이는 웰니스 트랙 전체가 추정 위에 서 있다.

7.6 IoT 업체에 확인할 것 (§4.4 보강)

  • 현재 사용목적을 문서상 어떻게 표기하고 있나? (카탈로그·제안서·홈페이지 문구)
  • "수면무호흡"·"호흡정지 감지" 표현을 쓰고 있나? ← 쓰고 있으면 리스크 공유 필요
  • 「의료기기 해당 여부 검토」를 받은 적이 있나? 회신 문서가 있나?
  • 복지용구·조달청·정부사업 등재 이력이 있나?

7.7 ⚠️ 이 절의 한계 (정직하게)

  • 요양병원 인증기준 원문 PDF는 다운로드 게이팅으로 확보 실패 → §7.0의 "평가 가점 없음"은 장기요양·심평원은 1차 출처, 요양병원 인증은 2차 출처 기반
  • 혁신의료기기 지정·규제샌드박스는 조사 미완 — 별도 확인 필요
  • "의료기기 요구 공고가 없다"는 부존재 증명이 불가능하다. 정확히는 **"발견하지 못했다"**이다
  • 조사 중 한 공고 페이지의 자동요약이 "주요 자격요건: 의료기기 관련 인증"이라는 허위를 생성했다(원문에 없는 문구). 이 절의 인용은 전부 원문 직접 추출이며, 2차 요약을 근거로 쓰지 말 것
