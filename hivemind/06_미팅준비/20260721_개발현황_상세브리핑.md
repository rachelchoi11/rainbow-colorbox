## 3. 서비스영역 ↔ 엔진 동작 (아키텍처)
```
[core · 엔진]  순수·무상태 — 파싱·표준화·매칭·정산 산출·연구소 탐지
     ▲  함수 계약(파일→레코드, df→집계, df+파라미터→정산)
     │  (지금은 라이브러리 호출 · 나중 무거워지면 HTTP 분리)
[service · 서비스]  마스터·워크플로우 — 테넌트·계약·유통사·역할·(후속: 인증·격리·확정)
```
- **엔진(core)**: 계약·테넌트를 *모름*. 정산액은 유통사 제공값(실측 94%)을 쓰고, 원천 인세엔진(정가×수량×율)은 만들지 않음.
- **정산 흐름(2단계)**: ① 유통사 → 출판사 정산액(파일 제공값) ② 출판사 → 작가 = **정산액 × 계약 배분율 − 선인세 상계 − 원천징수**.
- **마스터 3종**은 동일 구조: JSON 영속 + CRUD + 정산 데이터와 read-only 조인(테넌트 labels로 스코프). 세션 없이 관리, 세션 있으면 수치 보강.

## 4. 출판사 · 테넌트 트리
```
하이브마인드 (마스터 · 운영자)
├─ 출판사 테넌트 관리 (등록·구독·상태·유통대행 여부)
├─ 전체 정산 현황(유통대행 뷰)·엔진·연구소·유통사 설정(전역 파서 스펙)
│
├─ 출판사 A (테넌트)  ── labels[](정산 데이터 조인키)
│   ├─ 유통사 관리 (이 출판사 거래 유통사·정산율·수집상태)
│   ├─ 정산서 투입 → 표준화·매칭(엔진) → 정산 결과(유통사별·작가별·작품별)
│   ├─ 계약 (권리자별 배분율·선인세·지급처·계약서 첨부) → 작가 지급액
│   └─ (후속) 작가 포털 · 명세서 · 확정/공개
└─ 출판사 B (테넌트) ── A와 완전 분리(같은 구조)
```
- 원칙: **테넌트 = 출판사 1곳.** 유통사·작가·계약은 각 테넌트에 종속(출판사 간 통합 안 함). 동일 작가가 여러 출판사와 계약해도 별개.

## 5. 시나리오
**A. 운영자 온보딩** — 로그인 → 출판사 관리(업로드 없이) → 출판사 등록 또는 "정산 데이터서 발견 등록"(946곳) → 정산서 투입 → 출판사별 귀속/미귀속/라벨미상(합계 일치).

**B. 출판사 워크스페이스** — [출판사] 토글 + 테넌트 선택 → 대시보드(자기 정산만) → 유통사 관리(정산율 확정) → 정산 결과 → 계약(배분율 입력) → **작가 예상 지급액**.

**C. 연구소(오매칭 검토)** — 자동탐지 8종(미처리만) → 신고(열림) → 검토·진단 → 규칙반영/기각(목록서 빠짐=진행) → E1은 실제 작품키 분리. 되돌리기 가능.

**D. 계약 → 지급액** — 예: 문찐 정산 1.04억 × 배분율 70% − 원천징수 3.3% = **7,034만원**. 계약서 이미지 첨부(최대 3).
