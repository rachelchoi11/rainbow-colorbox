## 1. 본부장 메모 핵심 쟁점 (= 의사결정 안건)

### A. 상품 구성·범위 (정책 이슈)
- **2-Track 상품 이원화 + 2-Track 가격 모델**
  - 라이트: 데이터 취합만 (표준화·집계·통계 — 현 v2가 여기 해당)
  - 정식: 계약 관리 포함 (정산률·선인세·지급정보 등)
- **정산 솔루션 vs CMS 경계** — 콘텐츠·메타·마케팅/프로모션 데이터는 CMS 영역으로 분리 제안됨
- 일부 출판사는 **작가 계약 정보 노출에 부담** → 정식 버전 접근권한 설계 시 고려

### B. 일매출 데이터 트래킹
- 주요 4대 플랫폼(**카카오·네이버·리디·원스토어**) 일 매출 트래킹 필요성 제기
- 용도: **마케팅/프로모션 기간의 매출 추출**
- 예시가 Power BI(.pbix)로 전달됨(신규 샘플) → 본부장이 이미 PoC 수준으로 보유
- **결정 필요: 정산 솔루션에 반영 vs CMS에 반영** / 4개 플랫폼 사전 선택 옵션화

### C. 계정·권한 관리
- 뎁스: **마스터(하이브마인드) > 출판사 > 작가**
- 플랫폼 **직접 로그인 → 정산서 자동 다운로드** 가능 여부 확인 요청 (계정 관리 영역)
  - 가능 시 등록 자동화 → **별도 상품 프로젝트**로 확장 가능

### D. 계약 관리 (정식 버전 전용)
- 작품(작가) 계약 관리 / 레이블명 / **정산률(수익 배분율)**
- **공저 관리**(저자별 정산률 상이) / **선인세 차감**(작가·작품 구분)
- 작품별 카테고리 / 선연재 플랫폼 / **지급정보(계좌)** / 다필명 지급처 관리
- **일괄 등록**: 계약 후 최초 1회 csv 업로드 양식 제공 + 신규 작품 노티

### E. 정산서 취합·등록 관리
- **플랫폼 구분값 문제**: 다운로드 시 플랫폼명 미표기 → 우리가 파일명 변경으로 해결 중. 출판사가 원본 파일명 그대로 넣으면 구분 어떻게? (핵심 난제)
- **거래처별 등록 유무 관리**: 30개 계약 중 29개만 등록 시 누락 노티
- 중복 등록 예외처리 / 수정본 교체 / **롤백** / **월 정산 확정 시기**(확정분 수정 불가, 출판사가 확정 시기 선택)
- 카테고리 분류: 알라딘 메타·리디 정산서 표기 끌어오기 / 리디에 없는 작품은 출판사 직접 입력(범위 한정)

## 3-A. 작가 명세서 목표 포맷 — 작가 정산서 샘플 해부 (★ 정식 버전 산출물)
작가 정산서 샘플(2022.04, 스토리위즈 발행)은 **정식 버전이 발행할 '작가 명세서'의 목표 포맷** 그 자체.

**① 합계 시트** — 플랫폼별 매출 내역: `유통처 | 매출액 | 작가 정산액`
- 작가 정산액 = 플랫폼 매출액 × **작가 정산률(계약)** (샘플 일괄 60%)
- 합계 → **세액 차감(소득세·주민세)** → **작가지급액**
- 예(김민제/파란영): 매출 376,045 → 정산액(60%) 225,627 → 세액 −7,430 → **지급액 218,197**

**② 플랫폼별 상세 시트** — 각 플랫폼 원본 정산내역 중 해당 작가분 (네이버APP/PC·카카오·리디·미스터블루·북큐브·원스토어·하이북·구글북스·문피아·조아라·톡소다·예스24·알라딘·코미코·버프툰·스낵북·한아름·판무림 등 — 작가마다 계약 플랫폼 상이)

**③ 특수 시트 = 계약 관리와 직결**
- **MG차감내역**(미니멈개런티=선인세 차감), 작품별 MG 시트(예: 판무림<로드 오브 머니>MG)
- **공저/필명 분리 시트**(예: `_장유진`, `_청빙` — 한 파일 안에 공저자·다른 필명 별도)
- **웹툰 시트**(예: `<갓 오브 블랙필드>웹툰`, `<회귀의 전설>웹툰` — 2차 IP)

### 메모 요구사항 ↔ 명세서 포맷 매핑 (추상 요구가 실제 산출물로 확인됨)
| 본부장 메모(계약관리) | 샘플에서 실증 |
|---|---|
| 정산률(수익 배분율) | 합계 시트 매출→정산액 60% |
| 선인세 차감(작가/작품) | MG차감내역·작품별 MG 시트 |
| 공저·저자별 정산률 | `_장유진` 등 공저 분리 시트 |
| 다필명 지급처 관리 | `_청빙` 등 필명별 시트 |
| 웹툰/웹소설 구분 | 웹툰 별도 시트 |
| 지급정보·세액 | 소득세·주민세 → 작가지급액 |

### 우리 v2와의 갭
- **이미 있음**: 작가별 정산·플랫폼별 상세·유통대행(출판사) 뷰 → 명세서 ①②의 기반
- **정식 버전에 필요(신규)**: ⓐ계약별 **정산률** 적용 ⓑ**선인세(MG) 차감** ⓒ**세액 차감→지급액** ⓓ공저·필명 **분배** ⓔ웹툰 IP 구분 ⓕ**작가별 xlsx 명세서 자동 발행**
- 갭 대부분 = **계약 데이터(정산률·선인세·지급정보) 입력이 전제** → 정식 버전 계약관리 모듈 선행 필요

> 회의 활용: "메모의 추상 요구 → 이 샘플이 곧 목표물 → **우리 v2 위에 계약관리 데이터만 얹으면 명세서 발행 완성**"이라는 로드맵을 한 장으로 보여줄 수 있음.

## 3-B. 신규 데이터 심층 진단 (파서 갭 · 일매출)

### 11~12월 정산서 파서 갭 (정산서 샘플 3 = 163파일, 전부 스토린랩 유통대행분)
| 플랫폼 | 상태 | 필요 조치 |
|---|---|---|
| **예스24** ★최대 리스크 | 1종 → **3종 신양식** + 파일명 불일치 | 파일명이 `B2B_List`·`B2C_List`·`SerialWorkStatisticsList`로 **"예스24" 미포함 → 현 파서 인식 실패**. B2B(납품기관·ISBN·출판사정산액), B2C(출판사판매가·원가율·출판사정산액), 연재(일자별 판매금액·정산금액·선인세) **3종 스펙 신규 필요**. 정산액 직접 제공 → 기존 ÷0.7 산식 폐기 |

> 결론: **11~12월 커버리지 = 예스24 3종 + 카카오 구양식 파서 개발이 선결**. 예스24는 파일명 인식부터 새로 잡아야 함.

### 일매출 트래킹 데이터 스펙 (일매출 pbix ×6: 네이버·리디·무툰·미스터블루·원스토리·카카오)
- 데이터 성격: **일(日) 단위 판매·매출** — 월 정산서와 granularity가 다름(정산서=월 확정 집계 / 일매출=일별 원천).
- **핵심 함의**: 일매출 트래킹은 **월 정산서 파이프라인으로는 만들 수 없다** — 별도 일별 데이터 소스·수집 체계가 필요.
  → "정산 솔루션 내재화 vs CMS" 판단의 결정적 근거: **데이터 소스·성격이 다름**(정산=월 확정/근거, 일매출=운영·마케팅 성격) → 무게중심은 CMS 쪽.
- (pbix 내부는 VertiPaq 압축이라 정확한 컬럼은 Power BI로 열어야 확인. 최소 축: 일자 × 플랫폼 × 작품/시리즈 × 판매량 × 매출.)

## 4. PM 제안 포지션 (준비된 인상 포인트)
1. **범위 경계 원칙 제시**: "정산 솔루션 = 돈이 어떻게 흐르는가(취합·표준화·정산·명세)". 콘텐츠/메타/마케팅 트래킹은 CMS. 단, **일매출 트래킹은 '정산 근거 데이터'로 볼 여지**가 있어 라이트/정식 어디에 둘지 별도 판단.
2. **티어 매핑 제안**: 라이트=현 v2(취합·표준화·통계·명세 열람) / 정식=계약관리(정산률·선인세·지급)+등록관리(확정·롤백·노티)+작가 명세서 발행.
3. **이미 확보한 자산 강조**: 표준화 파이프라인(31유통사·43만행·99.5%), 매칭 연구소, 유통대행 모드(출판사별 정산), 감사추적 — 정식 버전의 계약관리가 얹힐 **토대가 이미 있음**.
4. **난제 선제 정리**: 플랫폼 구분값(원본 파일명 문제)은 ①업로드 시 플랫폼 수동지정 UI ②파일 내용 기반 자동판별(현 매직바이트·헤더 방식 확장) 2안 제시.
