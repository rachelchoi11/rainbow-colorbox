# 본부장 추가자료 반영 진단 (7/2 · 7/6 · 7/9 · 7/20)

- 작성: 2026-07-20 (7/21 개발리뷰 회의용)
- 대상 자료: AI 활용 지점 v3(7/2) · 마케팅 내역 관리(7/6) · 2차적저작물 정산(7/9) · 아카이빙 센터 초안(7/20) [+ 정산솔루션 메모 v1(6/24)]

## 0. 총평 — 자료의 정체
- 본부장 자료 4건은 **개별 기능 요청이 아니라 "웹소설 출판 CMS 생태계 전체 청사진"** 이다. AI 활용 지점(7/2)이 상위 지도이고, 마케팅·2차저작물·아카이빙은 그 하위 가지의 상세.
- **정산 솔루션은 이 생태계의 한 모듈.** 본부장 스스로 문서 곳곳에서 "이건 CMS 영역", "정산 솔루션에 넣을지 CMS에 넣을지 정책 결정 필요"로 구분하고 있음.
- 따라서 판단 기준 = **"전부 정산 솔루션에 넣는가"가 아니라 "무엇이 정산 코어이고, 무엇이 별도 모듈인가"**. 이는 우리가 잡아둔 모듈 경계(솔루션=계산·판정 / 서비스=마스터·계약·워크플로우 / 그 외 CMS 모듈)와 정확히 맞물린다.
- 결론 선요약: **다 반영할 필요 없다. 정산 코어와 정식버전(계약관리)까지가 우리 1차 범위, 나머지는 단계적 별도 모듈로.**

## 2. 즉시 반영 가능 — 현 버전 피드백 (Quick wins)
6/24 "현 버전 문의·의견"은 대부분 정산 코어 UX 개선이라 지금 솔루션 안에서 바로 처리 가능:
- 유통사·기간 **다중 선택** (현재 단일 → 다중)
- 유통사별 **원본 정산서 뷰잉** (연구소 원본내역을 정식 뷰로 승격)
- 통계 화면 **상세 드릴다운 확대** + 통합검색 **옵션(기간·플랫폼)**
- **레이블 미상 작품 보강 동선** (오늘 출판사별 화면 '레이블 미상' KPI에서 바로 미매칭/보강으로)
- 작가별 분류 기준 재검토(작품-출판사-레이블-작가) — 유통대행 모드와 연계해 설계

→ 이 묶음은 며칠 내 반영 가능. 회의에서 "이미 일부 반영(드릴다운·출판사별·레이블미상 가시화)" 보고하고 나머지 확정.

## 3. 정산 코어 확장 — 정식(F/P) 버전 = 계약 관리
- 6/24·7/2가 요구하는 정식버전의 핵심 = **작가·작품 계약 마스터**: 레이블명, 작품별 정산률, 공저 저자별 정산률, 작가/작품 선인세(MG) 차감, 지급처(필명별 계좌), 카테고리, 선연재 플랫폼.
- **이건 정산 코어가 아니라 서비스 계층**(마스터·워크플로우). 이미 07_서비스설계 v1.0에 설계됨(레이블마스터·글로벌작가·MG원장·정산률 시간차원·CalcSnapshot freeze).
- 여기에 월 확정 freeze(7)·거래처 등록유무 노티(8)가 붙는다. → **M2~M3 서비스 계층 착수 시 한 덩어리**. 강수아와 API 계약 합의 지점.
- 라이트/정식 2track(5)은 이 경계로 자연 분리: **라이트=정산 코어(취합·표준화·산출) / 정식=서비스(계약·확정·발행)**.

## 4. 별도 모듈로 — 억지로 정산에 넣지 말 것
- **일 매출 + 마케팅 히스토리(14·15)**: 성격이 다름(월 정산=정산, 일매출=운영 모니터링). 본부장도 "CMS 영역/정책결정"으로 표기. → **마케팅 모듈** 별도. 파서의 일별 스펙(네이버·미스터블루·노벨피아 일매출)만 재활용. 캘린더·프로모션 아카이빙은 마케팅 모듈에서.
- **2차적저작물 정산(16)**: 본부장 결론이 타당 — **웹소설 정산과 분리 별도 관리**. 무한히 늘어나는 양식을 전수 대응하지 말 것. 대응은 본부장 3안 중 **①템플릿 제공 + ③미매칭 예외 입력** 조합이 우리 구조와 맞음(미매칭 보드가 이미 ③ 방식). 계약도 배타적발행권과 **분리 관리**(2차저작물 이용허락 계약).
- **아카이빙 센터(17)**: 계약서+콘텐츠(원고·메타·서비스파일·2차자료) DAM. **대규모 별도 프로젝트, 후순위 확정**. 본부장 상품화 순위에서도 뒤.
- **웹툰 정산(18)**: 최상위 웹툰/웹소설 구분 + 웹툰 제작사 정산서(국내/해외 분리·선후차감). 정산 코어의 **다음 버전 확장**(웹소설 안정화 후).
- **자동 다운로드/계정관리(19·20)**: 정부과제 RPA와 동일 선상. **별도 상품**. 계정 뎁스(마스터>출판사>작가)는 우리 멀티테넌트 설계와 정합 → 서비스 계층 인증·RBAC로 흡수.

## 5. 피드백 (아닌 것·재고할 것)
1. **전부 정산 솔루션에 넣지 말 것**: 마케팅·아카이빙·콘텐츠·IP는 CMS 모듈. 정산에 다 넣으면 앞서 말한 "무거워짐" 그대로 발생. 본부장 문서의 모듈 구분을 **그대로 따르는 게 맞음**(본부장도 이미 그렇게 나눠둠).
2. **2차저작물 전수 양식 대응 금지**: ROI 없음. 템플릿+예외입력 light 대응. 본부장도 "현실적으로 어렵다"고 인정.
3. **일매출 트래킹을 월정산 화면에 억지로 합치지 말 것**: 데이터 주기·목적이 다름. 별도 대시보드.
4. **파일명 의존 플랫폼 식별 리스크(6/24)**: 출판사가 파일명 안 바꾸고 올리면 플랫폼 구분 실패. → 업로드 시 **플랫폼 명시 선택 UI** 필요(현재 파일명 접두 매칭에만 의존). 회의 확인사항.
5. **라이트/정식 경계를 상품·가격과 함께 정책 결정**: 개발보다 정책이 선행(본부장도 강조). PM이 경계 제안, 대표·본부장 승인.

## 회의 상정 결정사항
1. 정산 솔루션 범위 확정: **어디까지가 정산, 어디부터 별도 모듈인가** (본부장 모듈 구분 승인)
2. 라이트/정식 경계 + 2track 가격 모델 (정책 — 대표·본부장)
3. 계약 마스터를 서비스 계층에 두는 것 확정 + 엔진 연결 방식(HTTP API vs 라이브러리) — 강수아
4. 2차저작물·일매출은 별도 모듈·후단계로 합의 (지금 정산에 안 넣음)
5. 업로드 시 플랫폼 명시 UI (파일명 의존 해소)
