## 1. 계약 넘버링 체계 — 완료

### 무엇인가 (쉽게)
계약마다 **주민번호 같은 고유 번호**를 붙이는 규칙. 번호만 보면 "어느 출판사의, 어떤 원작의, 웹소설인지 웹툰인지, 무슨 권리 계약인지, 무슨 형태인지"가 한눈에 읽힘.

### 번호 구조
```
0001 - AA001 - N - 1 - 00
 │      │      │   │    └ 콘텐츠유형 2자리 (웹소설/웹툰·계약유형에 따라 목록이 다름)
 │      │      │   └ 계약유형 1자리 (1 배타적발행권 / 2 2차적저작물작성권 / 3 외주)
 │      │      └ 웹소설(N) / 웹툰(T)
 │      └ 콘텐츠 고유번호 (원작 1개당 하나. AA001~ZZ999)
 └ 출판사 구분값 4자리 (계약을 맺는 순서대로 0001부터 자동 부여)
```

### 핵심 아이디어: "원작 하나 = 콘텐츠 번호 하나, 파생은 그 아래로"
- 원작 웹소설 배타적발행권 계약: `0001-AA001-N-1-00`
- 그 원작의 웹툰화(2차적저작물): `0001-AA001-N-2-01` ← **콘텐츠번호 AA001 그대로**, 계약유형만 2, 형태는 웹툰(01)
- 그 원작의 표지 외주: `0001-AA001-N-3-01`
즉 **같은 원작에서 뻗어나온 계약들은 콘텐츠 번호(AA001)를 공유**하고, 뒤 세 자리(N/T·유형·형태)로 구분됨.

### 콘텐츠유형 목록 (본부장 xmind 그대로 반영)
- 웹소설(N) · 배타적발행권(1): 웹소설(00)
- 웹소설(N) · 2차적저작물(2): 웹툰01 / 번역02 / 영상03 / 굿즈04 / 오디오북05 / 오디오드라마06 / 애니메이션07 / 채팅소설08 / 이모티콘09 / 기타1 10 / 기타2 11
- 웹소설(N) · 외주(3): 표지01 / 웹소설 교정·교열02 / 웹소설 서비스 파일 제작03
- 웹툰(T) · 배타적발행권(1): 웹툰01
- 웹툰(T) · 2차적저작물(2): 번역02 / 영상03 / 굿즈04 / 오디오북05 / 오디오드라마06 / 애니메이션07 / 채팅소설08 / 이모티콘09 / 기타1 10 / 기타2 11
- 웹툰(T) · 외주(3): 표지01 / 메인작화가04 / 각색05 / 콘티06 / 선화07 / 채색08 / 배경09 / 후보정10

### 어떻게 구현했나
- **출판사 구분값(4자리)**: 그 출판사가 첫 계약을 등록하는 순간 자동으로 다음 번호(0001, 0002…)를 부여. 이미 번호가 있으면 유지.
- **콘텐츠 고유번호**: 계약 등록 화면에서 다음 빈 번호(AA001→AA002…)를 자동 제안. 기존 원작의 파생 계약이면 그 원작의 번호를 그대로 골라 입력(자동완성 목록 제공).
- **계약번호 자동 조합**: 네 요소를 고르면 화면에서 실시간으로 `0001-AA001-N-2-01` 형태가 미리보기로 뜨고, 저장 시 확정.
- **수정 시 재계산**: 계약유형이나 형태를 바꾸면 번호가 자동으로 다시 만들어지고, 변경 이력(시간·이전값→새값)에 남음.
- 계약 목록 표 맨 앞에 **계약번호 열**을 추가. 아직 구성요소를 안 채운 계약은 "미부여"로 표시.

### 구현 시 내가 정한 가정
1. **출판사 구분값은 "첫 계약 등록 시점"에 부여** — 문서의 "계약순서에 따라 자동부여" 해석. (대안: 출판사 등록 시점에 부여)
2. **콘텐츠 고유번호는 출판사 안에서 순번** — 0001 출판사의 AA001, 0002 출판사의 AA001은 서로 다른 원작. (전역 유일번호가 아니라 출판사별)
3. ~~콘텐츠 번호 부여 시점(신규만? 소급?)~~ → **확정됨(2026-07-31, Rachel):** 출판사가 온보딩하면 **기존 정산 데이터 + 기존 계약서를 소급 등록**한다. 즉 신규 한 건씩이 아니라 **기존 계약 일괄 등록**이 기본 시나리오. → 아래 1-B 구현.

## 1-B. 기존 계약 소급 일괄 등록 — 완료

### 배경
출판사가 하이브마인드에 합류하면 과거 정산서와 **기존 계약서 다수**를 한꺼번에 올린다. 계약을 한 건씩 손으로 넣는 방식은 온보딩에 비현실적. 그런데 그 출판사의 **정산 데이터에는 이미 작품·작가가 다 들어 있음** → 이걸 계약 초안의 소스로 재활용.

### 무엇을 만들었나
계약 관리 화면에 **"정산 데이터에서 일괄 등록"** 버튼 추가(정산 로드 상태에서 노출).
- 그 출판사 정산 데이터의 **미계약 작품 목록**을 정산액 큰 순으로 제시(이미 계약된 작가+작품은 자동 제외).
- 기본 배분율·웹소설/웹툰만 정하고 작품 체크 → **배타적발행권 계약 초안 일괄 생성**.
- 각 계약에 **콘텐츠 고유번호 자동 연번**(AA001, AA002…) + 계약번호 자동 부여.
- 생성 후 각 계약을 열어 **정확 배분율·선인세·계약서 첨부**를 개별 보정(계약서 이미지는 계약별 최대 3개 첨부 기존 기능 사용).

### 흐름 요약
1. 정산서 업로드(기존) → 2. 출판사(테넌트) 확인 → 3. "정산 데이터에서 일괄 등록"으로 작품 목록에서 계약 초안 대량 생성 → 4. 계약별로 배분율·계약서 보정.

### 검증
- 유닛/E2E: 스토린랩 정산 데이터에서 상위 작품 일괄 생성 → `0001-AA001-N-1-00`, `0001-AA002-N-1-00`, `0001-AA003-N-1-00` 연번 부여, 배분율 70% 일괄 적용 확인. 재호출 시 생성분은 후보에서 제외(중복 방지) 확인.

### 검증
- 유닛 테스트: 문서 예시 3종(`0001-AA001-N-1-00`, `-N-2-01`, `-N-3-01`)과 정확히 일치.
- E2E: 실제 서버에 계약 생성 → `0001-AA001-N-2-01` 생성, 출판사 구분값 0001 부여 확인.
- 정산 계산식 무변경 → 회귀 불변식(431,296행·99.50%·검증86) 영향 없음.

## 2. 유통대행 3계층 — 완료

문서 결론: **"작가 – 출판사 – 관리자(하이브마인드)"** 3계층.
- 사용자가 출판사(CP)면: 유통대행사도 "플랫폼 하나"처럼 취급.
- 사용자가 유통대행사면: 각 출판사를 "작가 하나"처럼 취급하고, **지급처를 작가가 아니라 출판사로 표시**.
- 하이브마인드가 직접 유통대행을 하면: CP 계정 1개를 분리해서 관리.

### 어떻게 구현했나 (기존 계약 메커니즘 재사용)
문서가 "출판사가 한 명의 작가와 동일"이라고 했으므로, **계약 시스템을 그대로 쓰되 지급 대상만 바꿈**.
- **테넌트 유형** 추가: `출판사(CP)`(기본) / `유통대행사`. 출판사 등록·수정 화면에서 선택.
- **계약의 지급 대상** 추가: `작가`(기본) / `출판사`. 계약 화면에서 토글. 유통대행사 테넌트면 기본이 `출판사`.
- 지급 대상이 **출판사**이면, 정산 매칭을 작가명이 아니라 **출판사명(레이블→출판사 해석으로 산하 레이블 정산액을 합산)**으로. 지급액 = 그 출판사 정산액 × 배분율 − 선인세 − 세금 (계산식 동일, 매칭 키만 다름).
- 계약 목록에서 지급 대상=출판사인 계약에 "출판사" 배지 표시. 중복 경고도 지급 대상(작가/출판사)별로 분리 판정.

### 왜 이 방식인가
"출판사=작가와 동일"이라는 문서 결론을 가장 곧게 반영. 계약 번호·첨부·이력·중복경고 등 기존 기능을 그대로 재사용하고, **정산 계산식은 안 건드림**(매칭 대상만 작가↔출판사). 회귀 위험 없음.

### 가정 (확인 필요)
- 유통대행사 테넌트의 **정산 범위 = 그 테넌트의 레이블 집합**. 외부 출판사를 대행하면 그 출판사들의 레이블을 유통대행사 테넌트의 산하 레이블로 넣어 커버. (대안: 유통대행사는 레이블 무관 전체 정산에서 출판사별로 지급 — 이건 다중 유통대행사 시 중복 위험이 있어 채택 안 함.)

### 검증
- payee=출판사 계약(스토린랩, 배분율 10%) → base 604,388,622(스토린랩 산하 레이블 합산과 일치) → 지급액 58,444,380 정확.
- payee=작가(기존) 계약 결과 불변(회귀 안전). 정산 계산식 무변경.

## 3. 플랫폼 계약 마스터 + 플랫폼 MG — 마지막 단계 (예정, 확인 필요)

문서 내용:
- 플랫폼(유통사) 계약 필드: 계약번호·계약기간(체결/시작/만료/자동연장)·서비스 범위(B2C/B2B/B2BC/기타)·기본 수익 배분율(기준수익=플랫폼수익 또는 순매출 × 율)·특약.
- 특별계약(MG류): 네이버(정식연재MG·브랜드MG), 카카오(블럭딜·작가MG), 리디(선독점).
- **핵심 난제 — 플랫폼 MG는 정산 계산을 바꿈**:
  - 플랫폼 MG ≠ 출판사가 작가에게 주는 선인세. **둘을 구분**해야 함.
  - 플랫폼이 MG를 주면, 출판사 선인세를 **먼저** 차감하고 작가에게 지급.
  - MG 차감이 끝나는 시점에 **플랫폼–출판사 정산률이 바뀜(예: 70%→60%)** → 정산 기준 금액이 달라짐.
  - 실제 작가 지급이 발생하므로 **차감 진행/완료 트래킹** 필요.

왜 마지막인가: 이건 지금 정산식(제공 정산액 × 배분율 − 선인세 − 세금)에 **플랫폼 MG·정산률 변경**이라는 새 축을 더하는 것이라, 잘못 넣으면 검증된 정산 결과가 흔들림. **선행 확인 필요**:
- (Q1) 우리가 받는 정산서 금액은 플랫폼 MG 차감이 **이미 반영된 값**인가, 아닌가?
- (Q2) 정산률 변경(70→60)은 정산서에 이미 반영돼 오는가, 우리가 별도로 적용해야 하나?
- (Q3) 플랫폼 MG를 계약 마스터의 어느 계약(플랫폼 계약)에 매달지 — 콘텐츠 단위인가 계정 단위인가.

이 세 가지가 정리되면 그때 계산식에 안전하게 반영.
