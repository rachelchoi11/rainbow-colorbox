# 정산 데이터 표준화 설계서 v1

- 대상: 2026년 2월·3월 플랫폼 정산서 (총 103개 파일 / 플랫폼 25종)
- 근거 자료: ① 유통사 정산서별 유의 사항 문서, ② 정산서 다운로드 원본 2개월분, ③ 26년 2월 일부 수정본(필수 필드 배경색 표시), 2022년 통합 작업(v11) 스키마
- 작성일: 2026-06-04 | 상태: 내부 검토용 초안

---

## 1. 결론 요약

1. **원본 다운로드 파일만으로 데이터 산출 100% 가능** — 103개 전 파일 자동 파싱 성공. 수기 변환(확장자 수정 등) 불필요.
2. 단, 표면 확장자와 실제 형식이 다른 파일이 다수(아래 2장)이므로 **확장자가 아닌 파일 내용(매직바이트) 기준의 형식 판별 계층**이 파이프라인 최하단에 필요.
3. 필수 6요소(작품명·저자명·레이블·총매출·정산금액·단행본/연재) 기준으로 **완전 제공 플랫폼은 일부**이며, 나머지는 (a) 계산식 보완, (b) 마스터 작품 대조 테이블 보완의 2단계 보강이 필요(4·5장).
4. 신규/변경 양식 대응은 **헤더 시그니처(핑거프린트) 등록제**로 해결 가능(6장).

## 2. 입력 파일 현황 및 제한 요소 (질의 ① 답변 근거)

### 2.1 실제 파일 형식 매트릭스

| 실제 형식 | 플랫폼 | 비고 |
|---|---|---|
| 정상 xlsx | 문피아, 미스터블루, 올툰, 원스토리, 카카오페이지(2종), 판무림(2종), 피우리 | 그대로 파싱 |
| **비표준 xlsx** (스타일시트 XML 깨짐) | 북큐브, 애니툰 | 일반 라이브러리에서 오류 → 스타일 무시 관용 파서로 해결 (검증 완료) |
| 구형 xls (OLE2) | 예스24 | xls 전용 리더로 파싱 |
| **HTML 위장 xls** (실제는 HTML 테이블) | 네이버(2종), 노벨피아(2종), 로망띠끄(2종), 무툰, 미노벨, 미소설, 밀리의서재(2종), 블라이스, 신영미디어, 에피루스, 큐툰, 피플앤스토리, 하이북 | **16종 — 전체의 절반.** 엑셀에선 열리지만 데이터 파이프라인에선 HTML 파서 필요 |
| CSV | 에이블리, 구루컴퍼니(2종), 알라딘, 조아라 | 전부 utf-8-sig |
| ZIP | 리디 | 압축 해제 → 내부 CSV |

### 2.2 인코딩 현황

- CSV·HTML 대부분: `utf-8-sig`
- **cp949(EUC-KR) HTML**: 로망띠끄, 신영미디어, 에피루스 — 유의사항 문서의 "Mac에서 글씨 깨짐" 현상의 원인. **인코딩 자동 감지 후 디코딩하면 정상 복원** (깨진 데이터가 아님 → 데이터 손실 없음)

### 2.3 input 제한 요소 정리 (클라이언트 보고용)

| # | 제한 요소 | 영향 | 해소 방안 |
|---|---|---|---|
| 1 | 확장자 ≠ 실제 형식 (xls→HTML 16종) | 단순 엑셀 리더로는 실패 | 매직바이트 기반 형식 판별 후 형식별 파서 라우팅 |
| 2 | 비표준 xlsx (북큐브·애니툰) | 표준 라이브러리 로드 오류 | 스타일 무시 관용 로더 (구현·검증 완료) |
| 3 | cp949 인코딩 3종 | Mac/일반 텍스트 처리 시 한글 깨짐 | 인코딩 자동 감지 |
| 4 | zip 내 CSV (리디) | 1단계 추가 처리 | 자동 압축 해제 |
| 5 | 헤더 위치 제각각 (1행~5행, 다단 헤더) | 일률 처리 불가 | 플랫폼별 헤더 행 좌표 정의 (4장 매핑 테이블) |
| 6 | 합계/SUM 행 혼입 | 집계 중복 오류 | 플랫폼별 제거 규칙 (4장) |
| 7 | 동일 플랫폼 복수 계정 파일 (네이버·노벨피아·구루컴퍼니·밀리·카카오 등 `(1)` 파일) | 계정 구분 누락 위험 | 파일명 → 계정 식별자 매핑 규칙 |
| 8 | 취합 불가 플랫폼 7종 (교보·한아름·키다리·북팔·짱만화·모픽·구글북스) | 자동 수집 범위 밖 | 수동 업로드 채널 + 양식 등록제(6장)로 수용 |

## 3. 표준 스키마 정의

2022년 통합 작업(v11: 책·작가·raw 책명·출판사·정산액 5컬럼)을 필수 6요소 기준으로 확장.

### 3.1 표준 레코드 (1행 = 플랫폼 × 월 × 작품 단위)

| 필드 | 설명 | 출처 |
|---|---|---|
| `platform` | 플랫폼 식별자 (코드화) | 파일명/매핑 |
| `account` | 동일 플랫폼 복수 계정 구분 | 파일명 |
| `period` | 정산 대상 월 (YYYY-MM) | 파일명/데이터 |
| `title_raw` | 작품명 원문 (회차·[단행본]·[e북] 등 표기 포함) | 정산서 |
| `title_norm` | 정규화 작품명 (매칭 키) — 괄호 태그·회차·권수 제거 | 가공 |
| `author` | 저자명 | 정산서 or 대조 테이블 |
| `label` | 레이블(출판사)명 | 정산서 or 대조 테이블 |
| `book_type` | 단행본 / 연재 / 구분불가(구독제) | 정산서 or 규칙 |
| `gross_sales` | 총매출 (소비자 지불금액 합계) | 정산서 or 계산 |
| `settlement` | 정산금액 | 정산서 or 계산 |
| `gross_basis` | 총매출 산출 근거: `제공값` / `계산값` / `미제공` | 가공 |
| `settle_basis` | 정산금액 산출 근거: `제공값` / `계산값(산식명)` | 가공 |
| `source_file` | 원본 파일명 (추적성) | 시스템 |

> **설계 원칙**: 제공값과 계산값을 같은 컬럼에 섞되 `*_basis` 플래그로 구분 → 집계는 단순하게, 감사(audit)는 가능하게.

### 3.2 총매출 개념 주의

플랫폼마다 "매출"의 기준이 다름 — 표준화 시 동일 컬럼에 넣되 `gross_basis`에 명시:

- **소비자 지불액 그대로**: 네이버(BS합계), 에이블리, 미소설·미노벨(전체매출) 등
- **결제수수료 차감 후**: 문피아(판매골드), 구루컴퍼니(정산대상금액 별도), 카카오페이지(IAP 제외)
- **산출 불가(구독제)**: 밀리의서재 → 공란 + `미제공`

**각주 (클라이언트 확인 필요 사항)**
1. 리디·미스터블루·애니툰·원스토리·카카오페이지·판무림: 매출/정산이 다수 컬럼(판매유형별)로 분산 — 합산 대상 컬럼 확정 필요 (구현 단계에서 샘플 합계와 대사하여 검증 예정)
2. 문피아: 유의사항 문서엔 "타이틀명 [단행본] 표기"로 기재되어 있으나 실제 컬럼명은 '작품명' — 표기 위치 동일 여부 확인
3. 유의사항 문서의 두 번째 '구루컴퍼니' 항목(정가 100원+화수 표기=연재)은 문맥상(가나다순 위치, CSV 형식) **알라딘**에 대한 내용으로 추정 — 확인 필요
4. 올툰: 문서엔 "'타입' 항목으로 구분"이나 실제 정산서에 타입 컬럼 없음 — 작품명 접두 태그([BL소설]/[소설] 등)로 구분하는지 확인 필요
5. 판무림: 문서엔 "단행본만"이나 데이터에 카테고리 '단행본' 구분값 존재 — 전수 단행본인지 확인
6. 피우리: 유의사항 문서에 항목 자체가 없음 — 특이사항 유무 확인 필요

## 5. 누락 필드 처리: 마스터 작품 대조 테이블 (질의 ③ 답변)

### 5.1 문제

- 레이블 미제공: 무툰·문피아·큐툰·조아라·올툰·예스24·피플앤스토리·블라이스 + 구루컴퍼니(단일CP)·카카오(일부)
- 저자 미제공: 예스24·올툰
- 정산액/총매출 미제공: 네이버·블라이스(계산식으로 해소), 예스24(총매출 — 해소 불가), 밀리(구독제 — 공란 처리), 조아라(단가×건수로 계산)

### 5.2 설계: 작품 마스터 테이블

```
작품마스터: title_norm(키) | 정식 작품명 | 저자 | 레이블 | 시리즈명 | 비고
별칭테이블: title_alias(플랫폼별 표기) → title_norm   (다대일)
```

- **정규화 키 규칙**: 원문 작품명에서 `[단행본]`, `[e북]`, `[독점]`, `[연재]`, `[BL]`, `(개정판)`, 권/화수, `[세트]`, 공백 변형 제거 → `title_norm` 생성
- 1차 시드: 매출 정리 파일(노란색 필수 요소) + 레이블 제공 플랫폼(리디·알라딘·카카오 등)의 작품-저자-레이블 조합에서 자동 구축
- 레이블 미제공 플랫폼의 레코드는 `title_norm`(+저자) 매칭으로 레이블 보강

### 5.3 신작 처리 (구두 논의된 "대조군의 신작 문제")

1. 매칭 실패 레코드는 **`미매칭 검토 큐`**로 분리 (2022년 통합 작업의 `_미매칭_검토필요` 시트 방식 계승)
2. 월 정산 처리 시 미매칭 목록을 관리자에게 노출 → 확인·등록(별칭 등록 or 신작 등록) → 차월부터 자동 매칭
3. 레이블 제공 플랫폼에 동월 신작이 있으면 그 조합을 자동 신작 후보로 제안 → 운영자는 승인만

> 효과: 대조군을 "사전에 완성해야 하는 정적 자료"가 아니라 **매월 정산 운영 중 자연 증분되는 자산**으로 운영 — 신작 문제의 구조적 해소.

### 5.4 검증 실험: 기존 수작업 대조 결과(22년 12월 매출 정리, 38,063행) 기반

기존 수작업 파일의 `콘텐츠명(유통사 원문) → 시리즈명(정규명)` 쌍을 정답지로 삼아 정규화 규칙의 자동 매칭률을 측정.

| 단계 | 자동 일치율 | 비고 |
|---|---|---|
| 원문 그대로 비교 | 15.8% | 유통사별 표기 차이가 대부분 (84.2% 불일치) |
| 정규화 규칙 v1 (괄호병기·태그·권수·공백 제거) | 65.6% | |
| 정규화 규칙 v2 (+세트구매·외전·N부·시즌·상중하) | **78.8%** | 잔여 8,054행 |
| 잔여 분석 | — | **고유 시리즈 48개로 수렴** → 시리즈 단위 별칭 등록 48건이면 사실상 전량 해소 |

**관찰된 표기 변형 유형**: 띄어쓰기 차이(보스 오빠↔보스오빠) · 권/화/부 접미(21세기 대마법사 10) · 복합 접미(3부 1222화) · 괄호 병기(술탄(Sultan), 퇴마사(巫堂)↔(巫者)) · 태그([e북]·(개정판)·\*세트구매\*) · 외전/특별외전 · 정규명이 괄호 안 영문인 경우(온 디 에어(On the air)→On the air, 규칙으로 판별 불가 → 별칭 필수)

**기존 수작업 파일의 매칭 한계 실측**: 브랜드명 컬럼의 70.3%가 `#N/A`(VLOOKUP 실패값 잔존) — 수작업 대조 방식의 커버리지 한계를 보여주는 직접 증거.

**시사점**: ① 규칙 엔진이 약 8할을 자동 처리, ② 잔여는 행 단위가 아닌 **시리즈 단위 별칭 등록**으로 수렴(수십 건 규모), ③ 기존 수작업 파일 38,063행 자체가 별칭 테이블의 **1차 시드 데이터로 즉시 전환 가능** — 수년간의 수작업 결과가 시스템 초기 자산이 됨.
