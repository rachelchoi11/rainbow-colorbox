## 1. 로그인 · 회원 · 권한

**무엇**: 사람마다 계정으로 로그인하고, 역할에 따라 할 수 있는 일이 다름.

**지금 이렇게 동작**
- 두 종류의 조직: **운영사(하이브마인드)** 와 **계약사(출판사·유통대행사)**.
- 운영사 역할 3개: **최고관리자**(전부) / **운영자**(출판사·계약·정산 운영, 계정 발급) / **뷰어**(조회만).
- 계약사 역할 2개: **출판사관리자**(자사 관리+자사 사용자 관리) / **담당자**(자사 조회).
- 첫 가입자는 자동으로 최고관리자. 이후 운영사 가입자는 **최고관리자 승인**을 받아야 로그인됨.

**왜**: 여러 출판사가 한 시스템을 쓰되, 서로 남의 것을 못 보게 하고, 하이브마인드 내부에서도 권한을 나누기 위해.

**⚠️ 당신이 정할 것**

| 항목 | 현재 기본값 | 결정 |
| --- | --- | --- |
| 운영사 역할 이름·범위(최고관리자/운영자/뷰어) | 위와 같음 | |
| 계약사 역할(출판사관리자/담당자) — 더 세분할지 | 2단계 | |
| 가입 시 승인 필요(운영사) | 필요(최초만 자동) | |

## 2. 계약사 계정 발급 · 최초 접속(동의·정보 입력)

**무엇**: 출판사에게 계정을 주고, 처음 들어올 때 동의받고 정보를 입력받음.

**지금 이렇게 동작**
- 운영자가 "계약사 계정 발급" → 이메일과 출판사를 지정 → **초대 링크**가 생성됨(현재는 링크를 복사해 수동 전달; 자동 이메일 발송은 미구현).
- 초대 링크로 들어온 담당자가 이름·비밀번호 설정 → 계정 활성화. 그 출판사의 **첫 계정은 자동으로 출판사관리자**.
- 첫 로그인 시: **동의 화면**(약관 3줄) → **정보 입력**(담당자 이름·연락처) → 워크스페이스 진입.
- 초대는 **14일** 후 만료. 취소·재발송 가능.

**왜**: 출판사가 스스로 계정을 세팅하고, 동의·담당자 정보를 확보하기 위해.

**⚠️ 당신이 정할 것**

| 항목 | 현재 기본값 | 결정 |
| --- | --- | --- |
| 초대 만료 기간 | 14일 | |
| 약관 내용 | **임시 3줄**(실제 약관·개인정보 처리방침 전문 필요) | |
| 최초 수집 정보 범위(현재 이름·연락처만) | 확대 필요(→ 8절 회사정보) | |
| 자동 이메일 발송 | 미구현(링크 수동) | |

## 3. 출판사 · 레이블(임프린트) 관리와 매핑

**무엇**: 정산 데이터의 최소 단위인 "레이블"을 그 위 "출판사"로 묶는 것.

**지금 이렇게 동작**
- 예: 매드햇·브랜디 등 레이블 → 출판사 "스토린랩". 통합 매핑표로 **458 레이블 → 158 출판사** 정리됨. 현재 테넌트(출판사) **128곳**.
- 정산 데이터를 올리면 레이블을 자동으로 출판사에 귀속(매핑+정규화로 표기 변형 흡수).
- 특수 사례: 유통사 "에피루스"는 정산서에 출판사 칸이 없어 작품 제목이 레이블로 잘못 들어왔던 것 → "에피루스=블루마운틴소프트"로 교정.

**왜**: 한 출판사가 여러 임프린트를 두고, 유통사마다 표기가 달라서.

**⚠️ 당신이 정할 것**

| 항목 | 현재 | 결정 |
| --- | --- | --- |
| 미매핑 레이블(본부장 추가 회신분) 계속 반영 | 수시 반영 | |
| 매핑 편집을 화면에서(현재 파일 관리) | 화면 UI 없음 | |

## 4. 계약 관리 (핵심)

### 4-1. 계약 번호
**무엇**: 계약마다 고유번호. 번호만 보면 출판사·원작·매체·권리·형태를 알 수 있음.
**지금**: `0001-AA001-N-1-00` = 출판사(4자리)-콘텐츠(AA001)-웹소설N/웹툰T-계약유형(1배타적발행권/2차저작물/3외주)-콘텐츠유형(2자리). 파생 계약(웹툰화 등)은 원작 번호(AA001)를 공유.
**⚠️ 정할 것**: 콘텐츠 번호를 자동 연번(현재)으로 둘지, 실제 작품 코드에 맞춰 부여할지 / 단건 계약에서 번호 요소 미입력 시 "미부여"로 두는 현재 방식.

### 4-2. 계약 상태 (초안 / 확정 / 종료)
**지금**: 정산 데이터로 **일괄 생성한 계약은 "초안"** → **초안은 예상 지급액에 반영 안 됨** → 검토 후 "확정"해야 반영. 수동으로 만든 계약은 기본 "확정".
**왜**: 미검토 기본값(배분율 70% 등)이 지급액을 부풀리지 않게.
**⚠️ 정할 것**: 초안→확정 단계를 유지할지, 수동 계약도 초안부터 시작할지.

### 4-3. 유효기간
**지금**: 계약에 시작/종료(월)를 넣으면 **그 기간 정산에만** 배분율 적용. 비우면 전 기간.
**왜**: 서명 이전 과거 정산까지 소급 적용되는 것을 막기 위해.

### 4-4. 지급 대상 (작가 / 출판사)
**지금**: 보통은 작가에게 지급. **유통대행사**는 "출판사에게 지급"으로 설정 → 그 출판사 산하 레이블 정산액을 합쳐 배분.
**왜**: 유통대행 구조(작가-출판사-관리자)에서 지급 상대가 출판사인 경우.

### 4-5. 작품 범위 · 중복 경고
**지금**: 계약에 특정 작품 여러 개 지정 가능(하나라도 포함되면 매칭, 권차·외전 자동 포함). 같은 대상 계약이 **같은 작품 정산액을 겹치게** 잡으면 "⚠ 중복" 경고(이중 지급 방지).

### 4-6. 선인세(MG) · 원천징수
**지금**: 지급액 = 정산액 × 배분율 − 선인세(MG) − 원천징수(기본 3.3%). MG는 **한 번만 차감**되도록 원장으로 이월 관리(→ 6절).

### 4-7. 계약서 첨부 · 변경 이력 · 소급 일괄 등록
**지금**: 계약당 계약서 이미지/PDF 최대 3개. 모든 수정은 시간·변경내용·작성자 이력이 남음. 온보딩 시 정산 데이터의 작품으로 **계약 초안을 대량 생성** 후 개별 보정.

**⚠️ 4장 전체에서 정할 것**

| 항목 | 현재 기본값 | 결정 |
| --- | --- | --- |
| 원천징수율 | 3.3% | |
| 배분율 기본값(일괄 생성 시) | 70% | |
| 계약서 첨부 개수 | 최대 3개 | |
| 초안 자동 반영 여부 | 미반영(확정 후) | |

## 5. 정산 분석 (조회)

**무엇**: 올린 정산서를 표준화해 유통사별·작가별·작품별로 보고, 미매칭을 검토.
**지금**: 정산 요약(완전매칭 99.50%), 유통사/작가/작품/통계/검색, 미매칭 보드·연구소(오류 탐지)·유통사 설정. 계약사는 **자기 데이터만** 보임(서버에서 강제).
**⚠️ 정할 것**: 계약사가 볼 수 있는 범위(현재 자사 전체). 특별히 뺄 화면 있는지.

## 6. 정산 마감 (새로 추가 — 중요)

**무엇**: 그 달 지급액을 **확정해서 고정(스냅샷)**. 지금까지는 화면에 뜨는 "예상"이었는데, 마감하면 근거로 남는 "확정"이 됨.

**지금 이렇게 동작**
- "정산 마감 생성"(초안) → 확정 계약들의 지급액을 계산해 라인별로 저장 → **확정**하면 금액 고정 → **지급 완료** 표시.
- 확정 시 그 달 선인세(MG) 회수액이 **원장에 기록**되어, 다음 달에 같은 MG를 또 까지 않음.
- 예: 1차 마감에서 MG 5천만 상계 → 확정 → 2차 마감엔 MG 이미 회수돼 상계 0.

**왜**: "정산 시스템"이 되려면 지급 금액이 재현 가능·불변이어야 함(매번 다시 계산되는 추정치는 지급 근거가 못 됨).

**⚠️ 당신이 정할 것**

| 항목 | 현재 기본값 | 결정 |
| --- | --- | --- |
| 마감 단위(월별/전체) | 선택 가능 | |
| 확정 후 정정 허용 여부 | 확정=고정(재마감 정책 미정) | |
| 지급 처리(계좌이체·세금계산서 연동) | 상태 표시만(연동 미구현) | |

## 7. 보안 — 남의 데이터 차단

**무엇**: 계약사가 다른 출판사의 매출·계약·계좌를 못 보게 서버가 막음.
**지금 이렇게 동작**(실측 확인)
- 계약사는 로그인해도 **자기 출판사 데이터만** 조회/내보내기(요청을 조작해도 서버가 자기 레이블로 강제).
- 남의 계약·유통사·계약서 첨부 접근 → 차단(403). 전역 매칭 변경은 운영자만.
- 초대로 운영사 최고관리자를 몰래 만드는 구멍 → 차단(초대는 계약사 계정만).
- 동의·정보 입력 전에는 데이터 API 차단.

**왜**: 여러 출판사가 한 시스템을 쓰는데, 화면에서 안 보이는 것만으론 부족(요청 조작 가능) → **서버에서 강제**.

**⚠️ 정할 것**: 운영자/뷰어가 전 출판사를 보는 현재 정책(내부는 전부 열람) 유지 여부.

**지금**
- 계약사 "회사 정보" 화면에서 자사 프로필·정산 계좌를 스스로 저장(자사만).
- 운영자는 회원/출판사를 **삭제** 가능(본인·마지막 최고관리자는 삭제 불가). 보존하려면 삭제 대신 "정지".
**⚠️ 정할 것**

| 항목 | 현재 | 결정 |
| --- | --- | --- |
| 수집 항목(사업자번호·계좌·세금계산서 이메일) | 위 5종 | |

## 9. 데이터가 어디에 저장되나 (안심 포인트)

**지금**: 예전엔 JSON 파일에 저장돼 **재시작하면 사라지거나 동시에 쓰면 깨질** 위험이 있었음. 지금은 **SQLite(작은 DB 파일)**로 바꿔서, 저장이 **한 번에 안전하게(원자적) 반영**되고 손상되지 않음.
**⚠️ 아직 남은 것(인프라)**: 배포 서버(Railway)에 **영속 볼륨**을 붙여야 재배포 후에도 이 DB 파일이 유지됨(코드는 준비됨, 설정만 남음). 이걸 안 하면 배포 시 데이터가 날아갈 수 있음 → **정식 오픈 전 필수**.
