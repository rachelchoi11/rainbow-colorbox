## 2. 기능 변경 기획 (무엇을 / 어떻게)

### WS-A. 데이터 커버리지 확대

**A-1. 신규 플랫폼 파서 추가** (`pipeline/specs.py` — SPECS dict 추가형)
- **모픽** (난이도 하): 깨끗한 xlsx. `작품명·작가명·출판사(label)·총매출액·정산액` 전부 제공. `[단행본]` 태그로 book_type. `제공사=스토린랩` → **WS-B 유통대행 신호로 활용**. → spec 1건 추가.
- **교보문고** (난이도 중): 헤더 2행·합계 3행. `상품명·저자·출판사·정산대상판매가총액(gross)·정산액(settle)` 제공. **특이점 2가지**: ① B2B 기관납품(`납품처`=강남대·삼성 등)으로 **한 상품이 기관별 다중행 → 상품+저자 단위 합산 규칙** 필요. ② **ISBN 컬럼 다수 보유**(epub/종이책 ISBN) → 작품 마스터 매칭의 **유일키로 승격**.
- **에이블리**: 기존 spec 존재 — 1·4월 양식 동일 여부만 회귀검증.

**A-2. 기간 확대 (2·3월 → 1·2·3·4월)**
- `pipeline/run.py`의 `MONTHS`·`SRC` 경로 일반화 → 월 폴더 자동 스캔(파라미터화). 현재 `02. 정산서 다운로드 원본` 하드코딩 → 입력 디렉터리 인자화.
- 4개월 통합본 산출 + 월별 합계 대사 전수 재검증.

**A-3. 각주 1~6 확정 반영** (설계서 4장)
- 본부장 회신 필요 항목: ①다중 매출컬럼 합산 대상(리디·미스터블루·애니툰·원스토리·카카오·판무림) ②문피아 표기 ③구루/알라딘 혼동 ④올툰 타입 ⑤판무림 단행본 ⑥피우리 + **네이버 마켓수수료 추정 기준**.
- 데이터로 검증 가능한 것은 선검증(샘플 합계 대사) → 회신 항목만 추려 **클라이언트 확인 1장**으로 발송.

**산출물**: 표준 스키마 **v2**(필드 추가: `isbn`, `supplier`(제공사), `is_distribution`(유통대행 여부)), 4개월 통합본, 검증보고서 업데이트.

### WS-B. 유통대행 vs 솔루션-only 모드 분리 ★비즈니스 핵심

- **문제**(메모리): 카카오/네이버 입장에선 공급자가 "스토린랩(우리)" 하나 → raw에 출판사 정보 없음. 유통대행받는 출판사 책은 우리 계정으로 흘러 데이터 꼬임.
- **설계**:
  - 모드 1 **유통대행(우리=유통사)**: 책↔출판사 **마스터를 우리가 관리**. raw의 `출판사/label`은 신뢰 불가 가정. 모픽 `제공사`·교보 `출판사`처럼 신호 있는 플랫폼으로 보강.
  - 모드 2 **솔루션-only**: 출판사 본인이 로그인 → 본인 데이터만. 우리는 흐름 바깥.
  - **책↔출판사 마스터 테이블** 신설(작품마스터 확장): `title_norm/isbn → 출판사·계약관계(유통대행 Y/N)`.
- **담당**: 데이터 모델·매칭 규칙 = 나 / 테넌트 경계·접근제어 구현 = 강수아(WS-C와 연결).

### WS-C. 운영화 (강수아 메인)

| 항목 | 현재 | 목표 |
|---|---|---|
| 테넌트 | 전역 `SESSIONS={}`·전역 `aliases.json` | **출판사별 테넌트 분리** (데이터·별칭·권한 격리) |
| 인증 | 단일 `APP_PASSWORD` + 세션 12h | 계정·역할(운영자/출판사/뷰어) **RBAC** |
| 저장소 | 인메모리(휘발) | **영속 DB**(별칭·결정 히스토리·마스터·업로드 이력) |
| 배포 | Railway 수동 | CI/CD + 환경분리(stage/prod) + 시크릿 관리 |
| 모니터링 | 없음(과거 OOM 사후대응) | 로깅·에러알림·헬스체크·메모리 가드(LRU 이미 적용) |

- **인터페이스 계약**: 표준 레코드 스키마 + `app.py` API 시그니처를 고정 → 나(도메인 로직)와 강(인프라)이 병렬 작업 가능.

### WS-D. 도메인 정확도 자산화 (나)

- 미매칭 큐 → 승인/별칭등록 → **차월 자동매칭** 루프를 운영 기능으로 정식화(설계서 5.3).
- ISBN(교보 등) 도입으로 매칭 신뢰도 상향. AI제안·알라딘조회 유지(근거 있는 것만, 자동적용 금지, 감사추적).
- 정산서 발행 고도화(원천징수·작가요율 입력·기간/유통사 선택).

## 3. R&R — 강수아 이사 ↔ 나

> 원칙: **도메인 판단이 필요한 코드 = 나 / 도메인 무관 플랫폼·인프라 코드 = 강수아.** 경계는 표준 스키마·API 계약으로 고정해 충돌 없이 병렬.

| 영역 | 나 (최혜윤) | 강수아 이사 | 공동 |
|---|---|---|---|
| 기획·PO·요구사항 | ◎ 주도 | 검토 | 우선순위 합의 |
| 클라이언트 커뮤니케이션(본부장·대표) | ◎ | — | — |
| 파서/매핑(specs)·정규화·매칭 엔진 | ◎ | — | — |
| 검증(합계 대사)·미매칭·AI/알라딘 | ◎ | — | — |
| 유통대행 데이터 모델·책↔출판사 마스터 | ◎ 설계 | 구현 | 스키마 계약 |
| 멀티테넌트·인증/RBAC·영속 DB | — | ◎ | 데이터 경계 정의 |
| 배포·CI/CD·인프라·시크릿 | 협의 | ◎ | — |
| 모니터링·로깅·성능·보안 | — | ◎ | 사고 대응 |
| 프론트(정산 화면 UX) | ◎ | API 연동 | — |
| 표준 스키마·API 계약 | 공동 | 공동 | ◎ **변경은 합의 필수** |
| 테스트/QA | 도메인 케이스 | 인프라/부하 | 회귀 스위트 |

- **face-saving 포인트**: 강수아 이사에게 운영화(WS-C)라는 **독립 오너십이 큰 엔지니어링 영역**을 부여 — 도메인 깊이 없이도 임팩트 큰 일. 정산 정확도(틀리면 신뢰 붕괴)는 도메인 ground truth인 내가 보유.
- **연결고리**: WS-B는 내가 데이터 모델을, 강이 테넌트 경계를 — 한 화면에서 만나므로 **스키마 합의가 선행**.

## 4. 마일스톤 (12월까지 단계적 · 라이프사이클 매핑)

각 마일스톤은 `기획→요구사항→디자인→개발→배포→모니터링` 사이클을 포함.

| MS | 시기 | 게이트(완료기준) | 주요 산출 | 담당 |
|---|---|---|---|---|
| **M0** | ~6월 말 | 본 기획·R&R 합의 + 각주 1~6 회신 요청 발송 + 신규 데이터 1차 파싱 OK | 본 문서 컨펌, 클라이언트 확인서, 모픽·교보 파서 PoC | 나 |
| **M1** | 7월 | **데이터 커버리지 완성** — 신규 플랫폼 + 1~4월 통합 + 각주 반영 + 스키마 v2 | 4개월 통합본·검증보고서, specs 추가 | 나 |
| **M2** | 8월 | **유통대행/솔루션 모드 분리 1차** — 데이터 모델·책↔출판사 마스터 | 모드 설계서, 마스터 테이블, 모드별 집계 | 나(설계)+강 |
| **M3** | 9~10월 | **운영화** — 멀티테넌트·RBAC·영속 DB·CI/CD·모니터링 | 테넌트 분리 배포, 인증, DB 마이그레이션 | 강수아 |
| **M4** | 11월 | **통합·안정화** — 실데이터 운영 리허설·성능·보안·QA | 부하/보안 리포트, 정산서 발행 고도화 | 공동 |
| **M5** | 12월 | **정식 운영 전환** — 모니터링 정상화·문서화·인수인계 | 운영 가이드, 재계약 판단 자료 | 공동 |

- 병행 트랙: 노션 운영체계 롤아웃(대표 피드백→배포→임시운영)은 M0~M1과 병행.
- 게이트마다 **본부장·대표 피드백 수렴** 후 다음 MS 착수.
