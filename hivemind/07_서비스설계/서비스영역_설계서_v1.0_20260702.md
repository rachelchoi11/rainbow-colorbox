# 정산 솔루션 — 서비스 영역 설계서 (v1.0)

> v0.1(초안) → v1.0: **자체 적대 검토로 9개 치명적 꼬임을 잡아 데이터 모델을 재설계**.
> 성격: 공동 합의용 도메인 설계 + API/스키마 계약. (인프라=강수아 이사 / 도메인=최혜윤 / 스키마·API=공동)
> 원칙: 꼬임을 문장이 아니라 **스키마와 불변식(invariant)** 으로 못박는다.

---

## 0. 한 장 요약
- 엔진(31유통사 표준화·매칭·연구소·유통대행·감사추적)은 검증됨. 서비스 영역 = 그 위의 **멀티테넌트·영속·워크플로우·발행** 계층.
- 사용자: **운영사(하이브마인드)** / **출판사(구독 고객)** / **작가(열람)**.
- 핵심 루프: 업로드 → 표준화·매칭(엔진) → **레이블→출판사 귀속** → **계약기반 정산 계산** → **월 확정(계산입력 freeze·잠금)** → **작가 명세서 발행** → 작가 포털.
- v1.0의 핵심 교정: ① 레이블 마스터(레이블→출판사) 신설 ② 작가는 **글로벌 아이덴티티** ③ 확정 시 **계산입력 스냅샷 freeze** ④ 선인세 **MG 원장** ⑤ 정산률 **시간차원** ⑥ 매칭 마스터는 **규칙만 전역·매핑은 테넌트** ⑦ 엔진 in-memory ↔ DB 임피던스 명시.

## A. 적대 검토 반영 (v0.1의 9개 꼬임 → 교정)
| # | v0.1의 문제 | v1.0 교정 |
|---|---|---|
| C1 | **정산 귀속의 순환**: Record를 어느 출판사에 귀속? 계약이 있어야 아는데 계약은 출판사 소유 | 귀속은 계약이 아니라 **레이블 마스터(LabelMaster: 레이블→출판사)** 로 결정. 계약(정산률)과 분리 |
| C2 | **레이블→출판사 매핑 부재** | `LabelMaster` 엔티티 신설(운영사/유통대행 스코프). 한 출판사=여러 레이블 |
| C3 | **한 작가가 여러 출판사** → Author를 tenant에 묶으면 파편화 | 작가 **글로벌 아이덴티티**(`Person`) + 테넌트별 계약관계 분리. 지급처·필명은 Person에 |
| C4 | **확정 후 매칭/율 변경이 확정분을 흔듦** | 확정 시 **계산입력 전부 스냅샷 freeze**(매칭·정산률·MG잔액·세율·환율) → 명세서 근거 불변 |
| C5 | **선인세를 단순 '차감'** | **MG 원장(ledger)**: 선지급 잔액을 매출로 상계, 월별 잔액 이월 (샘플의 'MG차감내역'=원장) |
| C6 | **정산률 시점 모호** | Contract에 유효기간 + **정산월 기준 유효 계약 선택**(시간차원) |
| C7 | **공저·세액 계산 순서 모호** | 작품매출 → 저자별 정산률 분배 → **저자(지급처) 합산** → 저자별 세액 → 지급액 (순서 고정) |
| C8 | **매칭 마스터 전역 공유 = 경쟁 출판사 데이터 누출** | 전역은 **정규화 규칙만**, 실제 작품-작가-레이블 매핑은 **테넌트 격리**. 연구소도 동일 |
| C9 | **엔진 in-memory pandas ↔ DB 영속 임피던스** | 집계는 **DB(SQL)로 재구현**, 엔진은 파싱·매칭·산식 단계만 재사용(§9) |
| C10 | **플랫폼 구분값 자동판별을 있는 것처럼 씀**(현 파서는 파일명 기반) | 업로드 시 **플랫폼 필수 선택 or 헤더 지문 매칭**(신규) — 미구현임을 명시 |
| C11 | **확정 후 정정(delta) 실무 미정** | 수정본 재파싱 → (수정본−원본) **차액을 정정 정산기간에 기록**. 원본 불변 |

## 2. 액터·역할 (RBAC)
| 역할 | 정체 | 범위 |
|---|---|---|
| `operator` | 하이브마인드 운영 | 전 테넌트 관리·마스터데이터·구독. cross-tenant 접근은 **전부 감사** |
| `distributor_admin` | 하이브마인드 유통대행(스토린랩류) | 자기 취합 파일 보유·정산, 출판사별 분배 뷰 |
| `pub_admin` / `pub_staff` | 출판사(테넌트) | 자기 테넌트 데이터. 업로드·정산·계약·발행 (staff는 발행/확정 제외) |
| `author` | 작가(글로벌) | 자기 명세서·정산내역 **읽기전용**, 계약조건 비노출 |

## 3. 테넌시 & 귀속 (★ 핵심)
### 3-1. 테넌트
- 테넌트 = 출판사 또는 유통대행. 운영사는 시스템 역할(테넌트 무관, 감사).
- 모든 매출·정산 데이터는 `tenant_id` + **RLS(row-level security)** 로 격리.

### 3-2. 하이브마인드 이중정체
- 운영사(시스템 관리) ↔ 유통대행(type=`distributor` 테넌트) **분리**.

### 3-3. 파일 소유 vs 정산 귀속 (불변식)
> **소유(owner_tenant)=업로드 주체** / **귀속(publisher_tenant)=레이블 마스터가 정한 출판사**.
- Record는 `owner_tenant`(파일 소유) + `publisher_tenant`(정산 귀속, 레이블→출판사) 둘 다 보유.
- 유통대행 시나리오: owner=유통대행, publisher=각 출판사. 출판사는 자기 귀속 Record만 열람(RLS), 유통대행 파일 전체는 불가.
- 직거래 시나리오: owner=publisher=출판사.

### 3-4. 레이블 마스터 (신설)
- `LabelMaster`: 레이블명 → 출판사(테넌트). 정규화 포함(정산서 레이블 표기 변형 흡수).
- 유통대행/운영사가 관리(한 출판사=여러 레이블). **정산 귀속의 단일 진실원천**.
- ※ 이미 실데이터에 "출판사별 레이블명" 엑셀 존재 → 시드로 활용.

## 4. 데이터 모델 (v1.0)
```
Tenant        (id, name, type[operator|publisher|distributor], plan, status, settings)
User          (id, tenant_id?, role, email, auth)            # operator/author는 tenant_id null 가능
Person        (id, 대표명, 필명[]·별칭, is_author)            # ★ 글로벌 작가 아이덴티티(테넌트 초월)
Payee         (id, person_id, 계좌·세무정보, 유효기간)         # 다필명 → 단일 지급처
LabelMaster   (id, 레이블명·정규화, publisher_tenant_id)      # ★ 레이블 → 출판사(귀속)
Work          (id, publisher_tenant_id, 제목·정규화키, 웹툰/웹소설, 카테고리, ISBN[], 선연재플랫폼)
Contract      (id, work_id, [person_id·정산률·역할]···,       # 공저=다중
                 선인세유형, 유효_from, 유효_to)              # ★ 시간차원
MGLedger      (id, person_id|work_id, 초기선인세, 월별상계, 잔액)  # ★ 선인세 원장
UploadFile    (id, owner_tenant_id, platform, period, 상태, 원본해시, uploader)
Record        (id, file_id, owner_tenant_id, publisher_tenant_id,   # ★ 소유·귀속 분리
                 work_id?, person_id?, gross, settle, basis, 매칭상태)
SettlePeriod  (id, tenant_id, period, 상태[draft|review|confirmed|published],
                 확정일·확정자, calc_snapshot_id?)             # ★ 확정시 freeze
CalcSnapshot  (id, period_id, 매칭·정산률·MG잔액·세율·환율 동결본)  # ★ 명세서 불변 근거
AuthorStmt    (id, period_id, person_id, 플랫폼별내역, 정산액, MG상계, 세액, 지급액, 발행일)
Adjustment    (id, period_id, 원본_record, 수정본_record, 차액, 사유)  # ★ 확정후 정정
NormRule      (scope=global, 규칙)                            # ★ 전역=규칙만
MatchMap      (scope=tenant, tenant_id, title_norm→work/person, 근거)  # ★ 매핑=테넌트격리
Flag/Lab      (tenant_id, 연구소 신고·동명이작)
AuditLog      (actor, tenant, action, before/after, ts)
```
불변식(DB 제약): Record.publisher_tenant = LabelMaster(Record.label) / 확정 SettlePeriod는 CalcSnapshot 필수 / AuthorStmt는 CalcSnapshot 참조.

## 5. 워크플로우 & 상태머신
### 5-1. 파이프라인
```
① 업로드(+플랫폼 지정) → ② 표준화(엔진) → ③ 레이블→출판사 귀속(LabelMaster)
→ ④ 작품·작가 매칭(엔진+테넌트 MatchMap+연구소) → ⑤ 미매칭 검토
→ ⑥ 정산 계산(정산월 유효계약 정산률 × 매출, MG 상계, 공저 분배, 세액)
→ ⑦ 월 확정(CalcSnapshot freeze·잠금) → ⑧ 명세서 발행 → ⑨ 작가 포털
```
### 5-2. 상태머신 (freeze 명시)
```
draft ──▶ review ──확정(CalcSnapshot 생성·계산입력 동결)──▶ confirmed(잠금) ──▶ published
  ▲  │                                                        │
  └──┘ 확정 전만 수정                                          └─▶ Adjustment(정정 정산기간, 원본 불변)
```
- 확정 = **그 순간의 매칭·정산률·MG잔액·세율을 CalcSnapshot에 동결**. 이후 마스터가 바뀌어도 확정 명세서 불변.
- 확정 후 유통사 수정본 → 재파싱 → 차액을 다음 정정 정산기간에 기록.

## 6. 정산 계산 (명세서 산식 · 순서 고정)
작가 정산서 샘플 기준, **순서가 결과를 바꾸므로 고정**:
```
1) 작품별 플랫폼 매출 집계 (Record.settle, 정산월 귀속)
2) 작품 → 저자별 분배 (Contract 정산률·공저 비율, 정산월 유효계약)
3) 저자(Person) 합산 (다필명·다작품 → 단일 지급처)
4) MG 상계 (MGLedger 잔액에서 차감, 잔액 이월)
5) 세액 (지급처별 소득세·주민세)
6) 지급액 = 정산액 − MG상계 − 세액
```
- 계약 미비 작품 = 노티 + '계약미확정' 플래그(기본율 임시 적용, 발행 보류 가능).

## 7. 작가 포털 (P3)
- 글로벌 작가 계정(여러 출판사 소속 가능) → 각 출판사별 명세서 통합 열람.
- 계약조건 비노출, 결과 금액만. xlsx/PDF 다운로드. 이의제기(선택).

---

## 8. 보안·격리
- **RLS**: 모든 매출 테이블에 tenant 필터 강제. 출판사 간 완전 격리.
- 운영사 cross-tenant 접근 = 전부 AuditLog(실데이터 접근은 민감).
- 매칭 마스터: **전역은 정규화 규칙만**(작품-작가 실매핑 아님) → 경쟁 출판사 데이터 누출 차단.
- 작가 개인정보(계좌·주민세) = Payee 암호화 저장.

---

## 9. 엔진 ↔ 서비스 경계 (임피던스 해소)
- 엔진(pandas in-memory)은 **파싱·매칭·산식 단계만** 서비스가 호출(파일→표준 Record 리스트).
- **집계·통계·명세서는 DB(SQL)로 재구현**(대량·멀티테넌트·영속). 현 engine.summary/build_dataframe의 pandas 집계를 SQL 뷰/쿼리로 이식.
- 즉 엔진 = "파일 1개 → 표준 Record[]" 순수 변환기로 축소. 나머지는 서비스/DB.

## 10. Phase 로드맵
| Phase | 범위 | 티어 |
|---|---|---|
| P1 | 멀티테넌트 기반(테넌트·계정·인증·DB) + 업로드·귀속·정산·통계·명세서 **열람** | 라이트 |

## 11. 열린 결정 (합의 필요)
1. 유통대행 분배 우선순위(P1 vs P4).
2. 매칭 마스터: 규칙 전역화 범위(운영사 자산화 vs 프라이버시).
3. 구독/과금 연동 시점.
4. DB·인증 스택(강수아 이사) + 엔진↔서비스 API 계약.
5. 플랫폼 자동 다운로드(계정 위임)의 법적·보안 → 범위/제외.
6. 통화: 현재 KRW 고정, 오로라 글로벌 확장 시 통화 필드.
