## 0. 가장 중요 — 정산 흐름 교정 (도메인 사실, 절대 뒤집지 말 것)

**우리는 원천 인세 엔진(정가×수량×인세율)을 만들지 않는다.** 유통사가 정산액을 이미 계산해 준다.

### 증거 (실측)
- `settle_basis` 분포: **94%가 '제공값'**(405,753/431,296행). 유통사 파일이 정산액을 직접 제공.
- 산식 계산(×0.7)은 예스24·판무림 등 **소수(~19K행)**의 폴백뿐.
- 원칙(메모리 `feedback_parser_latest_format_wins`): **"제공값 우선, 산식은 폴백. 값만 인식."**

### 실제 2단계 흐름
1. **유통사 → 출판사** : `settle`(정산액) = **파일에 주어짐**. 우리가 계산 안 함.
2. **출판사 → 작가(권리자)** : `작가 정산액 = 출판사 수취 정산액 × 계약 배분율 − 공제(선인세 상계·원천징수)`.
   - **계약관리가 적용되는 지점은 여기(2단계)뿐.**
   - 현재 코드(`api_statement`)가 이미 골격 보유: `author_amt = settle_total × rate/100`, 원천징수 3.3% 차감. `rate`가 현재 flat(기본 100%) → **계약 계층이 작품·권리자별 배분율로 대체**할 자리.

### 그래서 계약/정산 모델은
- `calculation_basis_amount` = **유통사 제공 정산액**(default). 정가×수량 아님.
- `royalty_rate` = **작가 배분율(share)**. 인세율(정가기준) 아님.
- 유연성은 남기되(정가 기준 인세 = 종이책·단행본 소수 케이스), **기본 경로 = 정산액 기준 배분**.

> ⚠️ **경고**: 이 교정을 모르면 GPT 스펙대로 "정가×수량×인세율 원천 엔진"을 만들게 된다. 우리 유통 데이터엔 그게 불필요·부정확. 계약 계층 구현 전 필독.

## 2. 채택한 테넌트 데이터 모델 (목표)

### 소속 원칙
- **테넌트 = 출판사 1곳.** 유통사는 테넌트 아님(출판사에 소속된 거래처).
- 권리자·작가포털계정·계약·정산은 **전부 특정 tenant에 종속.**
- 동일 인물이 여러 출판사와 계약해도 **출판사별 별개 계정·데이터**(연결·통합 안 함).

### tenant_id 부여 대상 (모든 업무 데이터)
출판사 직원·권리자·작가포털계정·유통사·작품·상품·계약·인세규칙·정산배치·원본파일·원본행·표준화데이터·정산계산·정산서·지급·원천징수·전자결재·감사로그.

### 테넌트 접근 통제 (강수아 영역 · 필수)
- **서버가 로그인 사용자 → 소속 테넌트 → 역할/권한 → tenant_id 강제** 순으로 처리.
- URL·본문·쿼리의 tenant_id를 바꿔도 타 출판사 데이터 접근 불가.
- 파일 다운로드·백그라운드/배치/파싱 작업·캐시키·파일경로에도 tenant_id 강제.
  - 경로: `/tenants/{tenant_id}/settlements/{batch_id}/...` · 캐시키: `tenant:{tenant_id}:settlement:{batch_id}`

### 권한(RBAC, 출판사 직원)
tenant_admin / settlement_manager / settlement_staff / approver / accounting / viewer.
→ 메뉴뿐 아니라 **API·데이터 조회 범위**에 적용.

### 작가 포털
- 계정 = (tenant_id, rights_holder_id) 종속. 로그인 식별 = `tenant_slug + email` 또는 `UNIQUE(tenant_id,email)`.
- 접근 경로(경로 방식 우선): `/service/{tenant_slug}/author/...`. URL의 tenant_slug와 계정 tenant_id 일치 강제.
- 공개 범위: **본인 + published 상태만.** 조회 강제조건 = `tenant_id=계정 tenant AND rights_holder_id=본인 AND publication_status='published'`.
- 확정 전 계산·내부 결재·타 권리자·출판사 전체매출·유통사 전체정산액 = **불가.**

### confirmed vs published (핵심)
- `confirmed` = 출판사 내부 확정(freeze, 계산입력 동결).
- `published` = 작가 포털 공개.
- **확정돼도 공개 전까지 작가에게 안 보임.** 공개 취소 시 즉시 비노출.

### SettlementBatch 상태
draft → file_uploaded → parsing → mapping_required → validation_required → calculation_completed → under_review → approval_pending → confirmed → payment_pending → paid → published.
