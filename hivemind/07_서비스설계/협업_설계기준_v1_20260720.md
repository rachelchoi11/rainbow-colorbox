# 협업 설계 기준 v1 — core / service 경계

- 작성: 2026-07-20 (7/21 강수아 개발리뷰 회의용)
- 상위 문서: `서비스영역_설계서_v1.0_20260702.md` (서비스 도메인 설계) — 본 문서는 그 위에 **2인 협업을 위한 코드/모듈 경계·소유권·계약**을 정의
- 배경: 솔로 구현 → 강수아와 공동 구축 전환. 지금 경계를 못 박아야 (a) 시스템이 커져도 Rachel이 전체를 손에 쥘 수 있고 (b) 본부장 스코프가 커져도 core가 안 무거워짐

## 0. 역할 (전제 — 오해 방지)
- **Rachel = 전체 기획·아키텍처·오너 + 개발자(성장 중).** 양쪽(core·service) 다 기획하고, 전체를 유지·수정할 책임과 권한을 가짐. git 소유.
- **강수아 = 순수 실행 개발자.** 무거운 구현을 담당하는 실행자. 기획·아키텍처 결정권자가 아님.
- **불변 조건**: Rachel이 모든 부분을 ① 읽고 이해하며 성장, ② 로컬에서 재현·모니터링, ③ 문제 시 직접 수정할 수 있어야 한다. **어떤 부분도 Rachel에게 블랙박스가 되면 안 된다.**
- 따라서 경계(core/service)의 목적 = **소유권 분할이 아니라 가독성**. Rachel이 각 부분을 머릿속에 담고 유지할 수 있게 나누는 것.

## 1. 한 문장 설계
엔진(core)을 **순수·무상태 패키지**로 고정하고, 그 위에 **서비스 계층**을 쌓는다 — 강수아가 무거운 구현을 맡되 **전체는 Rachel이 기획·리뷰·유지**하며, 어디든 직접 고칠 수 있게 legible하게. 만나는 지점은 **core 공개 함수 계약 + 표준 스키마**.

## 2. 현재 코드 = 이미 80% 이 구조
- 도메인: `engine.py`(표준화·매칭·집계·연구소) · `specs.py`(유통사 스펙) · `run.py`·`normalize.py`·`loaders.py`(파싱)
- 웹: `app.py`(FastAPI 라우트·세션·상태) · `static/`(프론트)
- → 새로 짜는 게 아니라 **경계를 선언**하고, 웹에 섞인 service 성격 코드를 분리하는 작업. 리라이트 아님.

## 3. 모듈 구조 (모노레포, 단일 repo)
```
core/        도메인 엔진 — 파싱·매칭·정산·검증·연구소. 순수함수. DB/테넌트/계약 모름   [라헬]
service/     멀티테넌트·인증·RBAC·DB·워크플로우·월확정(freeze). 마스터 소유. core 호출  [강수아]
apps/web/    프론트 셸 (현재 static/)                                              [강수아 소유, 도메인 화면은 라헬]
modules/     확장 — marketing/ · secondary-rights/ · webtoon/ · archive/            [후단계]
```
※ 지금은 물리적 폴더 분리보다 **패키지 경계·소유권 규칙**을 먼저 확정. 폴더 재배치는 점진.

## 4. 못 박을 원칙 6
1. **core 순수·무상태** — 입력=파일/레코드/파라미터, 출력=레코드/df/정산결과. 계약·정산률·테넌트를 모름. "정산률 X%·공저 분배·MG 상계" 등은 **파라미터로 수신**, 자체 저장 안 함.
2. **service가 마스터·상태 소유** — 계약(작가·작품별 정산률·공저·선인세·지급처), 출판사/작가 마스터, 확정 스냅샷(CalcSnapshot), 사용자·권한, 유통사 설정. core 결과를 DB에 저장·freeze.
3. **경계 = 함수 계약** — core 공개 함수 목록·시그니처를 문서로 고정. 변경은 **PR 합의 필수**. 표준 스키마(레코드·정산결과·스냅샷)도 공동 소유.
4. **연결은 라이브러리(import) → HTTP 승격 가능하게** — 지금은 in-process 호출(같은 repo, 모노레포). 이유 = 스케일 절약뿐 아니라 **Rachel이 전체를 한 곳에서 실행·디버그·수정**할 수 있어야 하기 때문(HTTP 마이크로서비스는 전체를 혼자 굴리기 어려움). core를 순수·무상태로 유지하면 나중에 무거워질 때 HTTP로 떼어내기 쉬움(래핑, 리라이트 아님).
5. **스택은 Rachel이 로컬에서 실행·디버그·수정 가능한 것으로** — 강수아가 추천하되, 선정 제약 = "Rachel이 여기서 돌리고 고칠 수 있는가". 표준·문서화된 것 우선(예: Postgres/SQLite + 읽히는 마이그레이션), 특이·마법 인프라 지양. **블랙박스 금지.**
6. **관측성 내장** — 로그·에러·상태를 Rachel이 프로덕션에서 보고 진단할 수 있게(모니터링은 Rachel의 상시 역할).
7. **확장 모듈은 modules/로 독립** — 본부장 스코프(계약관리·마케팅·2차저작물·아카이빙·웹툰)는 core/service 계약을 통해서만 결합. core/service 오염 금지.

## 5. core 공개 계약 초안 (회의에서 합의)
| 함수 | 입력 | 출력 | 소유 |
|---|---|---|---|
| `parse(files)` | 원본 파일 | 표준 레코드[] | core |
| `match(records)` | 레코드[] | 매칭된 df (완전/작가만/미매칭) | core |
| `settle(df, params)` | df + 정산 파라미터(정산률·공저·MG·세율) | 작가/출판사별 정산결과 | core |
| `verify(df, metas)` | df | 합계 대사 결과 | core |
| `lab_suspects(df, detector)` | df | 오매칭 후보(E1~E9) | core |
- **핵심**: `settle`이 **계약 파라미터를 인자로 받음** = service가 계약을 소유하고 계산만 core에 위임. core는 계약을 저장/판단하지 않음.
- service는 이 결과를 받아 확정 시 **freeze(스냅샷)** → 명세서 근거 불변.
- ⚠️ **정산 산식 사실(절대 뒤집지 말 것)**: `settle`(유통사→출판사 정산액)은 **파일에 주어진 값**(실측 94% 제공값). 원천 인세 엔진(정가×수량×인세율) **만들지 않음**. 작가 정산액 = **제공 정산액 × 계약 배분율 − 공제(선인세·원천징수)**. 즉 `settle(df, params)`의 params = 배분율(share)이지 정가기준 인세율이 아님. 상세: [[테넌트_정산모델_반영_v1_20260720]]

## 7. 협업 방식 (Rachel이 전체를 쥐는 흐름)
- **강수아 작업은 PR로 → Rachel 리뷰(이해·학습·게이트) → 머지.** 강수아 코드가 Rachel을 거치지 않고 들어오지 않음. 리뷰가 Rachel의 성장 + 통제 지점.
- 강수아는 **선택 근거를 문서화**(왜 이 스택·이 구조). Rachel이 나중에 혼자 유지할 수 있게.
- 코드는 **관례적·읽히게**(영리함보다 가독성). Rachel이 6개월 뒤 혼자 고칠 수 있는 수준.
- Rachel은 **로컬에서 전체를 실행**(core+service 한 번에)하고, 프로덕션을 모니터링. 문제 시 여기서 직접 수정.
- 원칙: "강수아=무거운 구현의 손 / Rachel=전체 기획·리뷰·유지의 머리. **어떤 부분도 Rachel에게 블랙박스가 되지 않는다.**"

## 8. 오늘 작업분 인계 노트
- **출판사별 정산** = core 결과 뷰 → 유지(라헬).
- **유통사 관리(정산율 확정·수집상태·유통대행 구분)** = service 마스터 성격. 지금은 `data/distributors.json`(런타임)로 솔루션에 있으나, **소유권을 service로 이관** 대상. core는 정산률을 파라미터로 수신. → 경계를 가르는 **첫 실제 사례**로 강수아에게 인계.

## 9. 회의 결정사항 (Rachel이 아키텍처를 정하고, 강수아는 구현 관점 조언)
1. 모듈 구조(core/service/modules, 모노레포) — **Rachel 결정, 강수아 동의 확인**
2. core 공개 계약 초안 — `settle(df, params)`의 파라미터 형태(정산률·공저·MG·세율) 합의
3. 연결 = 라이브러리(now) + 순수 유지(→HTTP 가능) — **Rachel 제안, 강수아 운영 관점 검증**
4. 마스터/상태는 service가 구현(계약·확정·유통사 설정) — Rachel이 스키마·흐름 기획
5. DB 스택 = **강수아 추천, 제약 = "Rachel이 로컬 실행·디버그·수정 가능"** (표준·문서화)
6. 협업 방식 = **PR 리뷰 흐름**(강수아 push → Rachel 리뷰·머지) + 근거 문서화 합의
7. 표준 스키마(레코드·정산결과·스냅샷) 공동 소유·변경 합의 프로세스
