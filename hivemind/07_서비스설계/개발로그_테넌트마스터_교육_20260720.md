# 개발 로그 (교육용) — 출판사 테넌트 마스터: "분석 도구"에서 "서비스"로

> 2026-07-20 · 작업자 Rachel(+Claude) · 목적: 내가 개발자로 성장하도록, 오늘 한 작업을 "왜/무엇을/어떻게"까지 남긴다. 커밋 메시지는 짧게, 배움은 여기에.

---

## 0. 오늘 한 일 한 문장
로그인하면 **정산서 업로드 없이도 출판사(고객)를 관리**할 수 있게, "출판사=영속 마스터"를 정산 데이터에서 분리해 신설했다. 그 위에 정산 수치를 **안전하게 조인**해서 출판사별 귀속/미귀속을 보여줬다.

---

## 1. 문제를 어떻게 발견했나 (진단 사고법)
증상: "하이브마인드로 로그인했는데 정산서를 안 올리면 출판사 관리조차 안 된다."

왜? 코드를 보면 원인이 나온다:
- `app.py`의 `SESSIONS`(메모리 딕셔너리)에 업로드한 정산 데이터(pandas DataFrame)가 담긴다.
- 모든 화면 API가 `session` 파라미터를 받아 `get_df(session)`을 호출 → 세션 없으면 **404**.
- 프론트 `go()`가 "세션 없으면 무조건 업로드 화면으로" 강제.
- 출판사·유통사·작가 목록이 **전부 그 정산 데이터에서 파생**(예: `by_publisher`는 `label_resolved`를 groupby).

**배운 것**: 증상("업로드 안 하면 관리 안 됨") → 코드에서 원인(모든 게 세션 파생, 영속 마스터 없음) → **구조적 진단**("이건 분석 도구지 서비스가 아니다"). 증상만 고치지 말고 *왜 그런 구조인지*를 먼저 본다.

---

## 2. 아키텍처 결정: 영속 마스터를 세션에서 분리
서비스라면 **출판사(=고객=테넌트)**는 정산 데이터와 무관하게 *항상 존재*해야 한다. 정산은 그 위에 얹는 것.

- **마스터(영속)**: 출판사·(후속: 유통사·권리자·계약). 로그인만으로 관리.
- **정산(배치)**: 특정 출판사의 특정 기간 데이터. 마스터 위에 얹힘.

이게 우리가 앞서 정한 **core/service 분리**의 실제 첫 구현이다. 마스터=service 성격, 엔진=core.

---

## 3. 외부 검증(적대적 리뷰)이 가르쳐준 것 ★핵심 교육
구현 전에 **독립 리뷰어**(Claude 서브에이전트)에게 "내 계획의 함정을 찾아라"고 시켰다. codex는 계정 제약으로 불가. 리뷰가 계획을 크게 바꿨다 — 여기서 배울 게 많다.

### 3-1. "슬라이스를 쪼개라" (slicing)
내 원래 계획 = 마스터 + CRUD + 정산 조인 + 발견등록을 한 번에. 리뷰: **위험도가 다른 걸 묶지 마라.**
- **Sub-slice A** = 마스터 저장 + CRUD + 화면 (파이프라인 안 건드림 = **무위험**).
- **Sub-slice B** = 정산 데이터와 조인 (df를 만짐 = **회귀 위험**).
→ A 먼저 안전하게, B는 조인 규칙 확정 후. **배운 것**: 큰 변경은 *위험도로 쪼갠다*. 무위험은 빨리, 위험은 신중히.

### 3-2. 이름으로 조인하면 안 되는 이유 (키 vs 값)
"출판사명(`label_resolved`)으로 마스터랑 정산 데이터를 이으면 되지?" → **위험**. 왜?
- `label_resolved`는 **계산된 값**이다(4단계 폴백: 원천→당월대조→사용자별칭→과거시드). 매칭이 바뀌면 *같은 출판사인데 표기가 달라진다*.
- 코드가 이미 안다: `detect_label_variants`(연구소 E3)가 존재하는 이유가 "한 출판사가 여러 표기로 흩어짐"(로즈벨벳 vs 로즈벨벳(주)).
- 빈 라벨(`""`)도 많다(정산액 0.54%).

→ 해결: 테넌트에 **`labels[]` 조인 별칭 배열**을 저장(유통사 설정의 `aliases`와 동형). 이름이 아니라 *명시적 매핑*으로 잇는다. **배운 것**: **계산되는 값은 키가 될 수 없다.** 조인은 안정적인 명시 키로.

### 3-3. 회귀를 막는 4가지 규칙 (기존 431,296행 분석을 안 깨기)
지켜야 할 불변: `정산총액 = df["settle"].sum()` (빈 라벨 포함 전 행).
1. **left-join만** — 행을 버리지 않는다. inner-join으로 빈 라벨을 떨구면 총액이 준다(가장 흔한 조용한 버그).
2. **df에 저장하지 마라** — `rebuild()`가 매 별칭 결정마다 df를 다시 만든다. df에 쓴 컬럼은 사라진다 → **요청마다 재계산**(순수 함수로).
3. **매칭에 관여하지 마라** — 마스터가 매칭 입력이 되면 `_regress.py`(회귀 기준선)와 어긋난다. 마스터는 **read-only 조회 계층**으로만.
4. **SESSIONS 밖에 둬라** — 세션은 LRU로 3개까지만 유지(오래된 건 제거). 마스터를 세션에 넣으면 사라진다 → **모듈 전역 파일 저장**.

**배운 것**: "기능 추가"가 "기존 것 파괴"가 되지 않게 하는 건, *불변식을 정하고(총액) 그걸 깨는 경로를 하나씩 차단*하는 일이다.

### 3-4. JSON vs SQLite — 지금은 JSON
리뷰 권고: 지금은 **JSON 파일**. 이유 = 코드에 이미 같은 관용구가 있다(`aliases.json`·`distributors.json`·`flags.json`). 테넌트 스토어는 `save_dist_cfg`의 **구조적 복제**. 새 인프라 0. 볼륨도 수백 건(43만 아님). SQLite는 *동시 다중 사용자*가 생길 때의 이주 트리거지 지금 미리 하면 과설계.

**배운 것**: 기술 선택은 "최신/멋짐"이 아니라 *지금 코드가 이미 하는 것과 맞물리는가 + 지금 진짜 필요한가*.

## 4. 실제 코드 — 함수별로 무엇을·왜

### engine.py (마스터 저장 + 조인)
- `load_tenants()` / `_save_tenants()` — `tenants.json` 읽기/쓰기. `load_dist_cfg` 패턴 복제. 파일 없으면 `[]`.
- `_slugify(name, existing)` — URL용 슬러그(예: "매드햇"→"madhat"), 중복이면 `-2` 접미. 슬러그 = URL·식별용 짧은 이름.
- `create_tenant(...)` — 새 테넌트 1건. `id`=기존 최대+1, `labels`=기본 [이름]. 저장 후 반환.
- `update_tenant(id, patch)` — 부분 갱신(None은 무시). `save_dist_cfg`와 같은 패치 방식.
- `register_discovered_tenants(names)` — 정산 데이터서 발견된 라벨 중 **미등록분만** 일괄 생성(1회 저장). 이미 아는 라벨(`known` set)은 스킵.
- `tenant_settlement(df, tenants)` ★ — 조인의 핵심.
  - `label → tenant_id` 맵을 만든다(한 라벨이 여러 테넌트에 있으면 **먼저 등록 쪽**=first-wins, 중복은 `dup`에 기록).
  - `df["label_resolved"].map(lab2t)`로 각 행에 테넌트 id를 붙인다(안 붙으면 NaN=미귀속/미상).
  - 테넌트별 `settle/works/authors` 집계.
  - **리마인더**: `귀속(claimed) + 미귀속(unclaimed, 라벨은 있으나 미등록) + 라벨미상(unlabeled, label="") = 총액`. 이 셋을 다 보여줘서 **합계가 정산 총액과 정확히 맞게** 한다.

### app.py (API)
- `GET /api/tenants?session=` — 세션 **없어도** 마스터 반환(핵심). 세션이 *있으면* `tenant_settlement`로 수치 보강. `get_df`(404 던짐) 대신 `session in SESSIONS`로 **부드럽게** 처리.
- `POST /api/tenants` / `/update` / `/register_discovered` — 등록/수정/발견등록. 앞 둘은 세션 불요.

### static/app.js (프론트)
- `renderTenants()` — 출판사 관리 화면. `/api/tenants`(세션 있으면 붙여서) 호출. 빈 상태 안내 + 등록 버튼. 정산 데이터 있으면 **정산액·작품 컬럼 + 리마인더 배너**(귀속/미귀속/라벨미상/중복).
- `openTenant()/saveTenant()` — 등록·수정 드로어.
- `NO_SESSION_TABS = ['upload','tenants']` + `init()`가 `go('tenants')` — **진입점을 출판사 관리로**, 세션 없이 진입 가능. (리뷰 지적: 이 진입 전환은 3곳 연동 편집 — 라우트·게이트·init. 하나라도 빠지면 여전히 업로드로 튕김.)

## 5. 핵심 개념 사전 (오늘 나온 것)
- **테넌트(tenant)**: 멀티테넌트 시스템에서 데이터가 격리되는 고객 단위. 우리 = 출판사 1곳.
- **마스터 데이터**: 거래·이벤트와 무관하게 영속하는 기준 정보(출판사·유통사·계약). ↔ 트랜잭션 데이터(정산 배치).
- **left-join**: 왼쪽(정산 행) 전부를 남기고 오른쪽(테넌트)을 갖다 붙임. 짝 없으면 빈칸. → *행이 안 준다*(총액 보존).
- **리마인더/reconciliation(대사)**: 부분합(귀속+미귀속+미상)이 전체(총액)와 맞는지 맞춰보는 것. 회계의 "합이 맞나" 확인.
- **read-side enrichment(조회측 보강)**: 원본을 안 바꾸고, *조회할 때만* 계산해서 살 붙이기. 원본 불변 → 안전.
- **first-wins**: 충돌 시 먼저 온 것을 채택하는 단순 규칙.
- **적대적 리뷰(adversarial review)**: "이게 왜 틀렸는지 찾아라"로 시키는 검토. 확증 편향을 깬다.
- **슬라이싱**: 큰 변경을 *독립적으로 배포 가능한* 작은 조각으로. 위험도로 가른다.
- **불변식(invariant)**: 변경 전후로 항상 참이어야 하는 것(예: 정산총액). 회귀 판단의 기준.

## 6. 검증을 어떻게 했나
- **회귀**: `_regress.py`로 431,296행·완전매칭 99.50%·검증 86/86이 **변함없음** 확인(마스터는 read-only라 당연히 불변이어야 하고, 실제로 불변).
- **조인 정확성**: TestClient로 매드햇 테넌트 조인 = 정산 357,531,058·작품 312·작가 123 → 기존 파생뷰와 **정확히 일치**.
- **합계 일치**: 총액 11.97억 = 귀속 3.57억 + 미귀속 8.33억 + 라벨미상 651만 → **딱 맞음**. 발견등록 946곳 후에도 맞음.
- **한계**: 보강뷰 육안 캡처는 헤드리스 브라우저가 43만 행 렌더에서 크래시(도구 한계)라 실패 → 실 Chrome에서 확인. **배운 것**: 자동 검증(TestClient)이 브라우저 캡처보다 신뢰도 높고 빠르다.

## 7. 정직한 한계 (지금 안 되는 것 + 왜)
- **라벨미상 651만(0.54%)**은 이름-마스터로 귀속 불가 — 애초에 정산 데이터에 출판사 표기가 없음. 구조적. 배너에 명시.
- **작가 지급액(payout)**은 아직 못 보여줌 — `payout=정산액×계약배분율−세금`인데 계약 계층이 없음. "정산액 합계"까지만.
- **서버측 테넌트 격리 없음** — 지금 출판사 스코프(`label`)는 *클라이언트가 보내는 값*이라, 서버가 "이 사람이 이 출판사 맞나"를 검증하지 않음. = **보안 아님**. 인증·RBAC는 강수아 영역 후속.
