# 개발 로그 3 (교육용) — 연구소 흐름 일원화

> 2026-07-20 (이어서) · 목적: 성장용 상세 기록. 커밋 짧게, 배움 여기.

## 0. 한 문장
연구소(오매칭 검토)에서 "처리한 의심이 자동탐지 목록에 계속 남던" 흐름 단절을 고쳐, **처리하면 목록서 빠지게**(진행이 보이게) 일원화했다.

## 1. 문제 — 자동탐지와 신고함이 따로 놀았다
연구소는 두 부분이다: **자동탐지**(8종 탐지기, df에서 매번 계산) + **신고함**(사람이 검토·상태 관리). 문제는 이 둘이 분리돼 있었다.
- 운영자가 booktype 의심 200건 중 하나를 "규칙반영"으로 처리해도, 자동탐지는 df에서 매번 새로 계산하니 **여전히 200건**. 목록이 안 줄어 "얼마나 했는지" 안 보임.
- E1(동명이작)만 예외였다 — E1은 승인 시 실제 작품키를 분리해서 데이터가 바뀌니 자동탐지서 빠졌다.

## 2. 고침 — "처리된 키는 자동탐지서 제외"
- `handled_flag_keys()`: 신고함에서 상태가 **규칙반영 또는 기각**인 신고의 key 집합.
- `/api/lab/suspects`: 탐지 결과에서 그 key에 해당하는 의심을 **필터로 제외**.
- 결과: 규칙반영/기각 → 목록서 빠짐(줄어듦=진행). 진행중(열림/검토중) → 계속 노출. 되돌리면(열림으로) 재노출.
- 검증: labelvar 41→40, volume 200→199, backfill 12→11 (처리 시 −1), 검토중은 유지. 회귀 0.

## 3. 왜 이 방식인가 (설계 판단)
두 선택지가 있었다:
1. **실제 규칙 액션 구현** — E3 레이블 통합·E7 시리즈 통합을 데이터에 실제 반영(진짜 사라지게). 큰 도메인 작업.
2. **처리 표시로 제외** — 상태(규칙반영/기각)를 "처리됨"으로 보고 목록서 숨김. 작고 흐름 완결.

지금은 **2번**을 택했다. 흐름(운영자가 진행을 보는 경험)을 먼저 완결하고, 실제 규칙 통합(E3/E7 자동 별칭 저장)은 다음 도메인 작업으로. **E1만 지금 데이터 실변경(분리)**.

**배운 것**: "완결된 경험"과 "완전한 구현"은 다르다. 목록이 줄어드는 경험은 상태 필터만으로 완결되고, 데이터를 진짜 바꾸는 건 별개(더 큰) 작업. 순서상 경험을 먼저 잇는 게 맞다.

## 4. 개념 사전
- **자동탐지(stateless detector)**: 저장된 상태 없이 매 요청마다 df에서 계산하는 탐지기. 장점=항상 최신, 단점=처리 이력을 스스로 모름(그래서 신고함과 연결 필요).
- **신고함(flag registry)**: 사람의 검토·판정 이력(열림→검토중→규칙반영/기각). 상태 = 처리의 진실.
- **흐름 일원화**: 탐지(기계)와 판정(사람)을 하나의 루프로 — 판정이 탐지 목록에 반영되게.

## 5. 연구소 현재 상태 (점검 결과)
- 탐지기 8종 정상(합계 618건: E1 96·E6 200·E8 65·E9 3·E3 41·E4 12·E5 1·E7 200).
- 신고함 워크플로우 정상, E1 실제 분리 정상, 원본 내역(판단 근거) 정상.

- ⏳ 남음: E3/E7 실제 규칙 통합(자동 별칭 저장) — E1 외엔 아직 "처리 표시"까지.
