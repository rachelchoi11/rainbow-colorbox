# 정산 솔루션 — 서비스 영역 설계서 (v0.1 초안)

> 목적: 도메인 엔진(표준화·매칭·연구소·정산계산) 위에 얹을 **멀티테넌트 SaaS 서비스 계층**을 사전 설계. 계정·권한·워크플로우·발행.
> 성격: 공동 합의용 **도메인 설계 + API/스키마 계약 초안**. (인프라 구현=강수아 이사, 도메인=최혜윤, 표준스키마·API 계약=공동)
> 원칙: "꼬이기 쉬운 지점"(유통대행 이중구조·플랫폼 구분값·확정/롤백·계약기반 계산)을 데이터 모델에서 먼저 못박는다.

---

## 0. 한 장 요약
- **엔진은 이미 있다**(31유통사 표준화·매칭·연구소·유통대행 모드·감사추적, 완전매칭 99.5%). 서비스 영역 = 그 위의 **껍데기**: 테넌트·계정·권한·정산 워크플로우·명세서 발행·영속 DB.
- 핵심 사용자: **운영사(하이브마인드)** / **출판사(고객·구독)** / **작가(열람)**.
- 핵심 루프: 출판사가 유통사 파일 업로드 → 엔진 표준화·매칭 → 계약 기반 정산 계산 → **월 정산 확정(잠금)** → **작가 명세서 발행** → 작가 포털 열람.
- 가장 꼬이는 지점 = **하이브마인드의 이중 정체(운영사 ∧ 유통사)** 와 **파일 소유 vs 정산 귀속의 분리**. 이걸 데이터 모델에서 분리해 해결한다.

## 1. 설계 원칙 (관심사 분리)
| 계층 | 책임 | 현 상태 |
|---|---|---|
| **도메인 엔진** | 형식판별·표준화·매칭·연구소·정산 산식·합계대사 | ✅ 존재(specs/run/engine), 검증됨 |
| **서비스 계층** | 테넌트·계정·권한(RBAC)·정산 워크플로우·상태머신·명세서 발행·노티 | 🔲 신규(본 설계) |
| **데이터 계층** | 영속 DB·테넌트 격리·감사추적 | 🔲 신규(현재는 세션 메모리) |

- 현 v2 = 단일 세션·메모리(재시작 시 소멸). 서비스 영역 = **영속 DB + 멀티테넌트 + 인증**으로 전환.
- 엔진은 순수 함수적으로 유지(테넌트 무지). 서비스 계층이 **테넌트 컨텍스트**를 주입.

## 2. 액터 · 역할
| 액터 | 정체 | 권한 범위 |
|---|---|---|
| **운영사** (하이브마인드) | 슈퍼 관리자 | 전 테넌트 관리·지원, 마스터 데이터(플랫폼 스펙·매칭 마스터·연구소), 구독 관리 |
| **↳ 유통사 겸업** | 하이브마인드가 운영하는 **유통대행**(스토린랩류) | 자신이 취합한 정산서 보유·정산, 출판사별 분배 뷰 |
| **출판사** (테넌트=고객) | 구독자 | 자기 테넌트 데이터만. 파일 업로드·정산·계약관리·명세서 발행 |
| **작가** | 출판사 소속 | 자기 정산내역·명세서 **읽기전용** |

- 계정 뎁스: **운영사 > 출판사 > 작가** (본부장 메모와 일치).
- 출판사 내부 세부역할(관리자/실무자)은 Phase 2+ (RBAC 확장 여지만 남김).
- ⚠️ 작가 계약정보 노출을 꺼리는 출판사 존재 → 작가 포털은 **계약 조건 비노출, 결과(정산액)만** 노출.

## 3. 테넌시 모델 (★ 가장 중요)
- **테넌트 = 출판사** (또는 유통대행). 모든 도메인 데이터는 `tenant_id`로 격리.
- 운영사(하이브마인드)는 cross-tenant 접근권(관리·지원 목적, 감사로그 남김).

### 3-1. 하이브마인드 이중 정체 해소
하이브마인드는 (a) **운영사**(플랫폼 제공자) 이면서 (b) **유통사**(스토린랩처럼 여러 출판사 정산을 대행)일 수 있다. 이 둘을 **다른 테넌트/역할로 분리**한다:
- 운영사 역할 = 시스템 관리 권한(테넌트 무관).
- 유통대행 = **하나의 테넌트**(type=`distributor`)로 존재. 자기가 취합한 파일을 보유하고, 정산 결과를 **출판사 테넌트로 귀속·분배**.

### 3-2. 두 정산 시나리오 (데이터 모델이 둘 다 지원)
| 시나리오 | 흐름 | 파일 소유 | 정산 귀속 |
|---|---|---|---|
| **A. 출판사 직거래** | 출판사가 유통사에서 직접 받은 파일 업로드 | 출판사 테넌트 | 자기 작품→작가 |
| **B. 유통대행 취합** | 하이브마인드 유통대행이 플랫폼서 취합 → 출판사별 분배 | 유통대행 테넌트 | 작품→출판사→작가 (2단 분배) |

### 3-3. 핵심 분리 원칙
> **파일의 소유(누가 업로드했나) ≠ 정산의 귀속(그 작품·작가가 누구 것인가).**
- 파일 소유 = 업로드 테넌트(출판사 or 유통대행).
- 정산 귀속 = 작품→출판사 매핑(계약/마스터) + 작품→작가 매핑(매칭).
- 유통대행 케이스는 엔진에 이미 있는 `supplier`/`is_distribution` + '출판사별정산' 뷰를 서비스 계층에서 **테넌트 분배**로 승격.

## 4. 데이터 모델 (핵심 엔티티 초안)
```
Tenant        (id, name, type[operator|publisher|distributor], 구독상태, 설정)
User          (id, tenant_id, role[operator|pub_admin|pub_staff|author], email, auth)
Author        (id, tenant_id, 대표명, 필명[]·별칭, 지급처_id)      # 작가 ≠ 지급처
Payee         (id, tenant_id, 계좌·세무정보)                      # 다필명→단일 지급처
Work/Series   (id, tenant_id, 제목·정규화키, 카테고리, 웹툰/웹소설, ISBN[], 선연재플랫폼)
Contract      (id, tenant_id, work_id, [author_id·정산률·역할]···, 선인세(작가/작품), 유효기간)
UploadFile    (id, owner_tenant_id, platform, period, 상태, 원본해시, 업로더)
Record        (id, file_id, tenant_귀속, work_id?, author_id?, gross, settle, basis, 매칭상태)
SettlePeriod  (id, tenant_id, period, 상태[draft|review|confirmed|published], 확정일·확정자)
AuthorStmt    (id, period_id, author_id, 플랫폼별내역, 정산액, 세액[소득·주민], 지급액, 발행일)
MatchAlias    (scope[global|tenant], title_norm→work, 근거, 감사)     # 매칭 마스터 vs 테넌트
Flag/Lab      (연구소 신고·동명이작 — scope 동일 고려)
AuditLog      (actor, tenant, action, before/after, ts)              # 이미 존재
```
- 격리: 대부분 `tenant_id` 필수. `MatchAlias`·플랫폼 스펙·연구소 마스터는 **global scope**(운영사 자산) + tenant override 허용(하이브리드).

## 5. 핵심 워크플로우 & 상태머신
### 5-1. 정산 파이프라인 (출판사 관점)
```
① 파일 업로드 → ② 형식판별·표준화(엔진) → ③ 플랫폼 식별(구분값 해결)
→ ④ 작품·작가 매칭(엔진+연구소) → ⑤ 미매칭 검토(보드) → ⑥ 정산 계산(계약 정산률·선인세·세액)
→ ⑦ 월 정산 확정(잠금) → ⑧ 작가 명세서 발행 → ⑨ 작가 포털 열람
```
### 5-2. 월 정산 상태머신
```
draft(작성중) ──검토──▶ review ──확정──▶ confirmed(잠금·수정불가) ──발행──▶ published
     ▲   │                                   │
     └───┘ (확정 전만 자유 수정·롤백)          └─▶ 정정: 원본 유지 + adjustment(정정 정산분)
```
- 확정 시기·주체 = **출판사가 선택**(월 정산 확정 시기 옵션). 확정분은 수정 불가.
- 확정 후 유통사 수정본 도착 → **정정 정산(delta)** 으로 처리(원본 훼손 금지, 감사추적).

## 6. 계약관리 모듈 (정식 버전 · 명세서 계산의 입력)
- 계약 = Work + Author(들) + **정산률**(수익배분율) + **선인세(MG)**(작가/작품 구분) + 지급정보 + 카테고리 + 선연재 플랫폼.
- **공저**: 저자별 정산률 상이 → Contract에 (author, 비율) 다중.
- **다필명**: 여러 필명 → 단일 Payee(지급처). Author↔Payee 분리.
- **일괄 등록**: 계약 후 최초 1회 CSV 업로드 양식. 이후 신규 작품은 **노티**(정산서엔 있으나 계약 없는 작품 → 출판사에 입력 요청).
- 명세서 계산식(작가 정산서 샘플 기준):
  `작가 정산액 = Σ(플랫폼 매출 × 계약 정산률) − 선인세(MG) 차감 → 세액(소득세·주민세) 차감 → 지급액`

## 7. 작가 포털 (Phase 3)
- 작가 로그인 → 월별·플랫폼별 **자기 정산내역·명세서** 읽기전용.
- **계약 조건 비노출**(출판사 부담 고려), 결과 금액만.
- 다운로드(xlsx/PDF 명세서), 이의제기 채널(선택).

## 8. 꼬이기 쉬운 지점 & 해법 (설계 리스크 대장)
| # | 위험 | 해법 |
|---|---|---|
| R1 | **유통대행 이중구조**(파일 소유 vs 정산 귀속 혼선) | §3-3 분리 원칙: 파일=소유테넌트, 정산=작품→출판사→작가 매핑. 유통대행 테넌트 별도 |
| R2 | **플랫폼 구분값**(출판사가 원본 파일명 그대로 업로드) | ①파일 내용 자동판별(파서 find_spec 확장) ②실패 시 수동지정 UI ③거래처 등록부 대조→미등록 노티 |
| R3 | **계약 의존 계산**(계약 없으면 명세서 불가) | 계약 미비 작품 노티 + 기본율 fallback(경고 표기). 명세서에 '계약미확정' 플래그 |
| R4 | **확정 후 정정** | 확정=잠금. 정정은 delta 레코드로. 원본 불변 + 감사추적 |
| R5 | **매칭 마스터 스코프**(전역 vs 테넌트) | 전역 시드(운영사 자산)+테넌트 오버라이드 하이브리드. 연구소도 동일 |
| R6 | **작가≠지급처**(다필명·공저) | Payee 엔티티 분리. 공저는 Contract 다중 (author,비율) |
| R7 | **데이터 정합**(중복 업로드·수정본) | 원본 해시로 중복 감지, 거래처×기간 유일성, 교체=버전 |
| R8 | **권한 경계**(작가 계약정보 노출) | 작가 포털 결과-only. 출판사 간 완전 격리. 운영사 접근은 감사 |

## 9. Phase 로드맵 (라이트→정식→포털)
| Phase | 범위 | 상품 티어 |
|---|---|---|
| **P0 (현재)** | 단일 세션 데모(엔진 검증) | — |
| **P1 멀티테넌트 기반** | 테넌트·계정·인증·영속 DB + 출판사 파일업로드·정산·통계·명세서 **열람** | 라이트 |
| **P2 계약·발행** | 계약관리 + 명세서 **발행**(정산률·선인세·세액) + 확정/롤백 | 정식 |
| **P3 작가 포털** | 작가 로그인·명세서 열람 | 정식+ |
| **P4 유통대행·자동화** | 유통대행 분배 모드·일매출·플랫폼 로그인 다운로드 | 별도 상품 |

- P1의 라이트 = 현 v2 기능(취합·표준화·통계·미매칭보드·연구소)에 **멀티테넌트·영속화**를 씌운 것.
- P2가 계약관리 → 이게 '정식 버전'의 핵심(2-track 가격 모델).

## 10. 기존 자산 연결 & R&R
- **재사용**: 엔진(specs·run·engine), 연구소(동명이작·오매칭), 유통대행 모드(supplier·is_distribution·출판사별정산), 감사추적, 미매칭 일괄처리.
- **R&R**: 인프라(멀티테넌트·RBAC·DB·CI/CD·모니터링) = **강수아 이사**. 도메인(데이터모델·정산로직·유통대행 모델·프론트) = **최혜윤**. **표준 스키마·API 계약 = 공동 합의 필수**(본 문서가 그 출발점).
- 마스터플랜 M3(운영화, 9~10월)와 정렬.

## 11. 열린 결정 (회의·합의 필요)
1. **유통대행 분배**를 P1에 넣을지 P4로 미룰지 (하이브마인드 유통사 겸업의 우선순위).
2. **매칭 마스터 스코프**: 전역 공유(운영사 자산화) vs 테넌트별 격리 — 비즈니스(유통대행이 진짜 목표)와 직결.
3. **구독/과금 모델** 연동 시점 (라이트/정식 티어 가격).
4. **작가 포털** 포함 시점 (P3 vs 더 뒤).
5. **플랫폼 자동 로그인 다운로드**(계정 위임)의 법적·보안 리스크 → 범위/제외 판단.
6. DB·인증 스택 선택(강수아 이사 영역) 및 엔진↔서비스 경계 API 계약.
