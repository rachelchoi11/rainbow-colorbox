## 0. 오늘 2부에서 한 일 한 문장
출판사(테넌트) 위에 **① 유통대행 배지 정합화 ② 계약 마스터(→ 작가 지급액 계산) ③ 유통사 마스터(출판사별)**를 얹었다. 이제 "작가에게 실제 얼마"가 화면에 나온다.

---

## 1. 유통대행 배지 — "마스터 vs 데이터 추정"이 어긋난 걸 고침
문제(사용자가 발견): **출판사 관리에선 유통대행 체크 꺼짐, 출판사별 정산에선 배지 켜짐.** 왜?
- 두 화면이 **다른 출처**를 봤다: 출판사 관리 = 마스터의 `is_agency`(사람 확정) / 출판사별 정산 = 데이터의 공급사 표기(추정).
- 원인: "발견 등록"이 `is_agency`를 **무조건 False**로 심음 → 데이터는 True인데 마스터는 False.

고침:
- 발견 등록 시 `is_agency`를 **데이터 추정으로 시드**(공급사 있으면 True). 기존분은 **업그레이드만**(데이터 True인데 마스터 False면 켬 — 운영자가 수동으로 켠 건 안 끔).
- 배지에 **대행 비중(%)** 표기(매드햇 5.7%). 왜 %가 필요? 공급사를 기록하는 유통사가 **모픽·알라딘 2곳뿐**이라, 배지는 "확인된 대행 근거"이지 100%가 아님을 드러내려고.

**배운 것**: 같은 개념(유통대행)을 두 곳에서 다른 출처로 계산하면 반드시 어긋난다. **진실은 하나(마스터), 데이터는 힌트.** 그리고 신호가 불완전하면 그 불완전성을 UI에 드러내라(%로).

## 2. 계약 마스터 — 여기서 "작가에게 실제 얼마"가 나온다 ★핵심
1편에서 정한 정산 흐름(도메인 사실)을 코드로 실현:
> **작가 지급액 = 유통사 제공 정산액 × 계약 배분율 − 선인세(MG) 상계 − 원천징수**

- **계약 마스터**(`contracts.json`, 출판사별): 권리자(작가)명·역할·작품범위·배분율%·선인세·지급처·원천징수%.
- **payout 계산**(`contract_payout`): 테넌트 범위(tenant.labels로 df 스코프) 안에서 그 작가의 정산액을 찾아 → 배분율 곱하고 → 선인세 빼고 → 원천징수 떼기.
- 검증(실제 값): 매드햇 작가 **문찐** 정산 1.04억 × 70% = 7,274만 − 원천징수 3.3% = **payout 7,034만원**. 검산 정확 일치.

여기서 중요한 설계 판단(1편에서 왔음): **원천 인세 엔진(정가×수량×인세율)을 안 만든다.** 기준액은 유통사가 준 정산액(제공값). 계약은 그 위의 *배분율*만 공급.

**배운 것**: 도메인 사실(2단계 흐름)을 먼저 못박아 두니, 계약 계층 구현이 "무엇을 계산하고 무엇을 안 하는지"가 자명해졌다. **먼저 진실을 정의하고, 코드는 그걸 따라간다.**

## 3. 유통사 마스터 — 출판사별로, 운영자 전역과 별개
- 출판사(테넌트)마다 **자기가 거래하는 유통사**가 다르다. 그래서 유통사 관리는 **per-tenant**(테넌트 스코프).
- `tenant_distributors(df, tenant)`: 그 테넌트의 labels로 df를 걸러 유통사별 정산 집계 + 저장된 확정 설정(정산율·수집방식·거래여부) 병합.
- 저장은 `tenant_distributors.json` = `{tenant_id: {유통사: {rate, collect, active}}}`.
- **운영자의 "유통사 설정"(전역 파서 스펙)과 별개.** 운영자 = "카카오 파일을 어떻게 읽나"(전역), 출판사 = "나는 카카오와 70%에 거래"(개별).

**배운 것**: 같은 단어(유통사 관리)라도 **누구 관점이냐**로 갈린다. 운영자 전역 vs 출판사 개별. 역할로 나누면 각자 가볍다.

## 4. 반복된 패턴 — 마스터 3종이 다 똑같이 생겼다
테넌트·계약·유통사 마스터가 **구조적으로 동일**하다:
1. `data/*.json` 영속 저장(`load_*` / `_save_*`) — `save_dist_cfg` 관용구 복제
2. `create/update/delete` CRUD
3. 정산 데이터와 **read-only 조인**(tenant.labels로 스코프, df 안 건드림, 요청마다 재계산)
4. API: 세션 없이 마스터 CRUD, 세션 있으면 수치 보강
5. 프론트: 목록 + 등록/수정 드로어 + 빈 상태

**배운 것**: 좋은 패턴 하나를 잡으면 다음 마스터는 *빠르고 안전하게* 복제된다. 새 걸 만들 때마다 새 방식 쓰지 말고 **선례를 따르라**(코드 일관성 = 유지보수성).

## 5. 오늘의 버그 교훈 (운영) — "계속 불러오는 중"
증상: 출판사 탭 전환 시 로딩에서 멈춤.
원인 2개:
1. **백엔드 미재시작** — `app.py`/`engine.py`를 고쳤는데 서버를 안 껐다 켰다. 파이썬 코드는 **재시작해야 반영**(프론트 `static/`은 no-cache라 자동). 그래서 새 API(`/api/tenant_dist` 등)가 실행 중 서버엔 없었음.
2. **onclick 메서드 미노출** — `App.openTDist(...)`를 화면에서 부르는데, `return {...}` 블록에 안 넣어서 `App.openTDist`가 undefined.

**배운 것(체크리스트)**:
- 파이썬 고치면 → **서버 재시작**. 프론트만 고치면 → 새로고침.
- `onclick="App.X"`를 새로 쓰면 → **return 블록에 X 노출** 잊지 말기.
- "계속 로딩"은 대개 *fetch가 없는 엔드포인트를 침*(→ 재시작) 또는 *JS가 깨짐*(→ `node -c`로 문법 확인).

## 6. 데모 토글 vs 실서비스 로그인 (개념 구분)
사용자 질문: "출판사로 돌리면 로그인 나오고 그 출판사 페이지?"
- **지금**: [운영자|출판사] 토글 = 운영자가 "이 출판사로 보면 뭐가 보일지" **미리보기(시뮬레이션)**. 로그인 없음. 스코프는 **클라이언트가 보내는 값** = 보안 아님.
- **실서비스**: 출판사 본인이 **자기 로그인**(`/service/{slug}/login`) → 자기 페이지만, 서버가 격리 강제. = GPT 스펙 §4·§6·§7·§17, **강수아 후속**.
- 토글은 실서비스에서도 남는다(운영자 고객지원용 "이 출판사 입장에서 보기"). 단 실제 출판사 접근 = 별도 로그인.

**배운 것**: "화면이 나온다"와 "인증·격리가 됐다"는 다른 문제. 지금 보이는 건 *운영자 권한으로 필터한 뷰*이지, *격리된 출판사 세션*이 아니다.

## 7. 개념 사전 (오늘 추가)
- **payout(지급액)**: 작가에게 실제 줄 돈. = 정산액 × 배분율 − 선인세상계 − 원천징수.
- **배분율(share rate)**: 출판사가 받은 정산액 중 작가 몫(%). ↔ 인세율(정가 기준)과 다름.
- **선인세(MG, Minimum Guarantee)**: 작가에게 미리 준 돈. 이후 정산에서 상계(차감).
- **원천징수(WHT)**: 지급 시 세금을 미리 떼는 것(사업소득 3.3%).
- **per-tenant 스코프**: 데이터를 특정 테넌트(출판사)의 labels로 걸러 그 테넌트 것만 보는 것.
- **시뮬레이션(미리보기) vs 실인증**: 운영자가 필터로 보는 것 ≠ 사용자가 로그인해 격리된 것.
